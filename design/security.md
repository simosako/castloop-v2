# セキュリティと安全境界

castloopは実資源と公開コンテンツを変更する管理ツールである。本書は認証、公開経路、機密情報、変更時の保護条件を整理する。開発作業の許可範囲は[AGENTS.md](../AGENTS.md)、脆弱性の報告先は[SECURITY.md](../SECURITY.md)を参照する。

## 認証と対象の識別

| 境界 | 認証・検査 |
| --- | --- |
| CLIからCloudflare REST API | `CLOUDFLARE_ACCOUNT_ID` と `CLOUDFLARE_API_TOKEN`。設定のアカウントと一致させる |
| CLIから管理API | `X-Castloop-Key` とWorkerの `CASTLOOP_ADMIN_KEY` を照合 |
| 管理操作の対象 | サービスID、設定ハッシュ、Show ID、更新元、世代、必要な配備証拠を照合 |
| 公開配信 | 許可したオリジン・パス・メソッド、Show/Episodeの公開可否と準備状態、承認済み素材参照 |

管理者キーはサービスの管理権限を持つ共有秘密で、利用者別ロールやShowごとの権限を提供しない。認証に成功しても、別サービス・別Show・古い更新元への要求は許可しない。

キーはSHA-256で固定長化し、Workersの `timingSafeEqual` で比較する。標準Web Crypto環境ではHMACの検証を使う。暗号処理を利用できない場合は認証を拒否する。呼び出し元は非同期の認証結果を待ち、成功前に管理要求の本文処理や変更を行わない。管理応答はキャッシュせず、独自ドメイン側の管理パスも拒否する。

## 秘密と診断情報

- 管理者キーは初期化時に乱数32 bytesから作り、ローカルの `.castloop/secrets.json` とWorkerのsecret bindingへ保存する。サービスTOMLやGitには保存しない。
- APIトークンは環境から受け取り、サービス設定・ローカルジャーナルへ永続化しない。管理者の環境に別のR2資格情報は要求しない。
- ローカル管理記録は原則ディレクトリ0700、ファイル0600で作る。ワークスペースの `.gitignore` に `.castloop/` と `*.mp3` を追加する。Git除外はアクセス制御ではないため、端末自体も保護する。
- 診断ログには許可したイベント・理由コード・対象識別子・数値を使い、任意の例外、入力本文、email、キー、トークンを転載しない。
- 公開メタデータに必要な所有者emailと、診断へ記録してよい情報は別である。統計にはIP、Cookie、User-Agent原文を保存しない。

管理者キーの再発行操作は提供していない。キーを含むワークスペースと、バックアップのパスフレーズを保全する。

## 公開経路とコンテンツ

R2は非公開のまま使い、Workerが[許可パス](components/delivery.md)だけを配信する。`system/` や任意のR2キーを外部へ公開しない。素材を配置しただけでは公開できない。

公開可否はキャッシュ参照前に確認する。非公開化は404、未準備は503とし、拒否応答をキャッシュしない。変更時の必要なパージが完了するまでSQLiteの公開内容を確定しない。

内蔵サイトは次を適用する。

- 入力文字列をエスケープし、説明文のHTMLは安全なテキスト・リンク・段落へ再構成する。
- スクリプト、フォーム、埋め込みコンテンツ等をそのまま取り込まない。
- カスタムCSSのサイズ・文字列を検証し、CSPでは実際のスタイルハッシュだけを許可する。
- `script-src 'none'`、同一オリジンの画像・音声、`nosniff`、`no-referrer` 等を適用する。

サイト表示時の加工は、保存済み説明文やRSSメタデータを無断で書き換えるものではない。

## 外部取得とローカルファイル

RSS取り込みはURLとDNSを検査し、非公開アドレスへの取得を拒否する。検査済みアドレスへ接続し、リダイレクト時も再検査する。サイズ・時間・リダイレクト回数を制限し、HTTPSの格下げと圧縮応答を拒否する。詳細は[RSS取り込み](components/rss-import.md)を参照する。

ローカルの設定・素材・記録は通常ファイルとして、親は実ディレクトリとして扱う。読み取り時のリンク拒否、サイズ制限、素材のハッシュ検査を各入力経路で行う。同じ保存先の変更は1プロセスに限定し、実行中の素材編集を前提にしない。

バックアップはファイル内容を暗号化するが、ヘッダーのサービスID・件数等は平文である。復元では不正パス・重複・既存保存先を拒否し、リモート操作を自動継続しない。

## 変更・保持の安全境界

- 作成・プレビューと公開を分け、実行対象を明示する。
- 通信エラーだけを理由に変更系HTTPを自動再送しない。確認済みのキャッシュレート制限への有限待機は[配信設計](components/delivery.md)に定義する。
- 内容の確定はShow内でアトミックに行う。ドメイン変更のような複数DO・外部資源をまたぐ処理を、全体が同時確定するものとして扱わない。
- 公開済みメディア・履歴・ローカル原本を保持する。物理削除、他形式への移行、不明資源の採用を管理機能へ追加しない。
- 対象・設定・更新元の不一致では、記録を保全してエラーにする。別の対象へ切り替える暗黙の回復処理を設けない。

## 非公開の実機試験

実環境の作成・配備・公開・DNS変更・削除等には、対象と範囲を指定した別の明示承認が必要である。コード変更やローカルテスト、過去の承認は実環境操作の許可にならない。

試験用コンテンツは、明示承認された確認者だけに公開するのが既定である。

1. アップロード・公開の前に、HTML、Feed、画像、音声の全経路をCloudflare Accessで保護する。
2. 確認者の正確なIDを指定したポリシーで、bypassがないことを確認する。
3. R2を非公開に保ち、別ホスト名やpreview URLから迂回できないことを確認する。
4. 管理者キー認証を維持し、配備・公開後は匿名のGET、HEAD、条件付き要求、Rangeが拒否されることを再確認する。

未掲載URLや `noindex` はアクセス制御にならない。保護を確認できなければ公開しない。CPU超過等の回避策としてPaidへの変更を要求しない。料金・CPU上限の変更や、試験対象外のDNS・証明書・ローカル証拠の変更も承認範囲外では行わない。

### 保護設定と実施順序

試験は専用の新規サービスとワークスペースを使い、既存サービスの管理記録・キー・資源識別情報を流用しない。サンプル原本は変更せずコピー側で準備する。

1. 対象アカウント、未使用の資源名、確認者ID、Access設定、公開するサンプルの範囲を確定して承認を得る。
2. サンプルを持たない空のサービスを初期化する。この時点ではサンプルを配置・公開しない。
3. 試験ホストの `/podcasts/*` 全体にAccessを設定し、実際のパス一致と匿名拒否を確認する。`/admin/*` は既存のキー認証を維持する。CLIはAccessのservice tokenヘッダーを送らないため、管理通信を通す目的で認証を無効化しない。
4. 保護確認後にだけ通常のCLIでShowとEpisodeを明示公開する。確認者がキャッシュを温めた後も匿名拒否を再検査し、本人に表示・再生・シークを確認してもらう。
5. 確認結果と未確認事項を記録する。レビュー待ちを理由にAccessを緩めず、試験後の資源削除も別承認なしに行わない。

Cloudflareログインによる本人確認を使う場合は、同一のAllow policyで「正確なメールアドレス」をInclude、「対象アカウントのメンバー」と「Cloudflareログイン」をRequireにする。これらを別のIncludeやAllow policyに分けて許可範囲を広げない。他のAllow・Bypassから迂回できないことも確認する。DashboardへのログインだけではAccess保護の設定やセッション確立の代わりにならない。

アカウント全体の保護設定や共有ログイン元は試験のために変更しない。R2の公開ホスト名を作らず、別ホスト・preview経路からの迂回も確認する。必要な権限がなければ管理者へ設定を依頼し、勝手に権限やプランを拡張しない。本人以外の認証を代行せず、CookieやトークンをURL・共有資料・Gitへ含めない。

本人限定のFeedは一般のPodcastアプリやSNSから取得できない。非公開の画面・再生確認と、一般公開の購読・SNS連携の確認は別の試験である。
