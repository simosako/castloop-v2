# セキュリティの設計

castloopは、管理者の認証、操作対象の照合、公開経路の制限を組み合わせて、サービスとコンテンツを保護します。本書では実装上の仕組みと、非公開の実機試験で必要な保護条件を説明します。脆弱性の報告は [SECURITY.md](../SECURITY.md)、共通の作業規則は [AGENTS.md](../AGENTS.md)、実環境操作の承認と保護対象は[実環境操作の注意事項](live-operations.md)を参照してください。

## 認証と操作対象

| 通信・処理 | 認証・照合内容 |
| --- | --- |
| CLI → Cloudflare REST API | 環境変数 `CLOUDFLARE_ACCOUNT_ID` と `CLOUDFLARE_API_TOKEN`。設定のアカウントと一致させる |
| CLI → 管理API | `X-Castloop-Key` とWorkerの `CASTLOOP_ADMIN_KEY` |
| 管理操作 | サービスID、設定ハッシュ、Show ID、更新元、世代番号。配備・ドメイン操作では配備情報も照合 |
| 公開配信 | オリジン、パス、メソッド、Show/Episodeの公開状態、準備状態、素材参照 |

管理者キーは、サービス全体の管理権限を持つ共有秘密です。認証に成功した要求でも、対象や更新元の照合を行います。

キーはSHA-256で固定長にし、Workersの `timingSafeEqual` で比較します。標準Web Crypto環境ではHMAC検証を使います。認証処理を完了してから本文の処理へ進み、暗号処理を利用できない場合は認証を拒否します。管理応答は `no-store` とします。

## 秘密情報の保存

| 情報 | 保存・取り扱い |
| --- | --- |
| 管理者キー | 初期化時に乱数32バイトから生成。`.castloop/secrets.json` とWorkerのsecret bindingに保存 |
| Cloudflare APIトークン | 環境変数から読み、設定や進捗記録には保存しない |
| ローカル管理記録 | 原則としてディレクトリ0700、ファイル0600で作成 |
| Git除外 | ワークスペースの `.gitignore` に `.castloop/` と `*.mp3` を追加 |

管理者キーを含むワークスペースと、バックアップのパスフレーズを安全に保管します。管理者キーの再発行コマンドは現在ありません。端末へのアクセス制御も管理者が行います。

### ログと診断

診断は、許可したイベント・理由コード・対象識別子・数値に限定します。任意の例外や入力本文、email、キー、トークンをそのまま記録しません。RSSの所有者emailなど、公開メタデータに含む情報も診断ログとは分けて扱います。

配信統計はHTTP応答のカウンタを保存し、IP、Cookie、User-Agentの原文を保存しません。

## 公開経路の保護

R2は非公開に保ち、Workerが[定義した公開ルート](components/delivery.md)から配信します。素材は、Show DOに保存した参照と公開状態によって配信対象になります。

`system/` と `staging/` は配信対象に含めません。

公開状態はキャッシュの参照前に確認します。非公開化した内容には404、未準備の内容には503を返し、拒否応答はキャッシュしません。公開内容を変えるときは、必要なキャッシュ消去後にSQLiteへ確定します。

管理APIは管理用オリジンで受け付けます。独自ドメインの `/admin/*` は404を返します。

### 内蔵サイト

HTML生成では次の処理を行います。

- 入力文字列をエスケープし、説明文を安全なテキスト・リンク・段落に整形する。
- スクリプト、フォーム、埋め込みコンテンツを除いた表示用HTMLを作る。
- CSSのサイズと内容を検証し、CSPで実際に使うスタイルのハッシュを許可する。
- `script-src 'none'`、同一オリジンの画像・音声、`nosniff`、`no-referrer` などを設定する。

整形はサイト表示時に行い、保存済みメタデータは保持します。

## 外部取得とファイルの読み書き

RSS取り込みは、公開アドレスであることを検査した接続先へ通信します。リダイレクト時も同じ検査を行い、取得サイズ・時間・リダイレクト回数を制限します。詳しくは[RSS取り込み](components/rss-import.md)を参照してください。

ローカルの設定・素材・記録は通常ファイルとして扱い、各入力経路でリンク、サイズ、素材ハッシュを検査します。入力を固定し、同じローカル保存先への変更を直列に実行する運用と、追加の防御処理を判断する基準は、[ローカル入力と直列操作の契約](../docs/development/constraints.md#local-inputs-and-serial-operations)に定めます。

バックアップはファイル内容を暗号化します。復元先は新規ディレクトリとし、不正パスや重複を検査します。平文ヘッダーに含む情報と暗号化方式は[バックアップ設計](components/workspace-backup.md)で説明しています。

## 変更処理の整合性

各操作で定めた確定単位の整合性を維持します。複数の確定単位にまたがる操作では、完了済みの結果を保持し、現在状態を確認して、個別の設計で定めた方法で再実行・継続します。

復旧のためだけに細かな状態と遷移を増やしたり、`blocked`・`*_requested` 状態による操作禁止や段階別の復旧コマンドを追加したりしません。サービス設定を変更する操作では変更前の設定を保存しますが、それだけで途中取消しや変更前の状態への復元を提供するものではありません。

作成・プレビュー・素材アップロードと、公開の確定を分けています。内容の確定はShow DO内のトランザクションで行い、公開済み素材と履歴を保持します。

変更系HTTPで通信エラーが起き、結果が不明な場合は自動再送しません。現在状態を確認し、該当する操作の継続条件に従います。既存のキャッシュ消去における明示的なレート制限への対応は、[配信設計](components/delivery.md#更新時のキャッシュ消去)に従います。

複数DOと外部リソースを更新するドメイン変更では、保存した対象・設定・要求ハッシュと現在状態を照合して進めます。不一致があれば記録を保全してエラーにします。各保存先の確定順序は[制御DO](components/control-do.md)を参照してください。

## 非公開の実機試験

[実環境操作の承認と保護対象](live-operations.md)を確認してから、承認された対象・操作範囲で実施します。エージェントは準備・実施の前に `castloop-live-trial` skillを読み込み、検証目的に合う手順を選びます。

以下はすべての非公開実機試験に共通する保護条件です。具体的な機能確認、素材、実行コマンドは試験ごとの手順で定めます。新規サービスでShowと3件のEpisodeを公開する場合は、[標準シナリオ](live-trial.md)を使えます。

### 共通の保護条件

- 今回の対象アカウント、リソース、確認者ID、Access設定、使用するサンプルと操作範囲を特定して承認を得ます。新規作成する場合は未使用のリソース名を選びます。
- 試験用ワークスペースを使い、サンプルは原本を保全してコピーを準備します。
- 試験用コンテンツは、承認された確認者だけが取得できるようCloudflare Accessで保護します。試験ホストの `/podcasts/*` 全体を対象とし、HTML・Feed・画像・音声の各パスが保護されていることを確認します。
- 確認者の正確なIDだけを許可し、他のAllowやBypassから迂回できないことを確認します。R2は非公開とし、別ホスト名・Workerのpreview URLからの迂回も防ぎます。
- アップロード・公開前に保護を確認し、匿名のGET・HEAD・条件付き要求・Rangeが拒否されることを検査します。配備・公開後と、確認者がキャッシュを温めた後にも匿名拒否を再確認します。
- 管理APIのキー認証を維持します。コンテンツを公開する試験では、通常のCLIを使って明示的に公開します。
- 機能確認は試験目的に合わせて行い、結果と未確認事項を記録します。確認者による表示・再生・シークの確認が必要な場合は、その結果も区別して記録します。試験後のリソース削除にも承認を得ます。

保護を確認できなければ、アップロード・公開の前に停止します。未掲載URLや `noindex` はアクセス制御の代わりにはなりません。CLIはAccessのservice tokenヘッダーを送らないため、`/admin/*` は既存の管理者キー認証を維持する構成にします。

### Cloudflareログインを使う場合

同じAllow policyで、正確なメールアドレスをIncludeに、対象アカウントのメンバーとCloudflareログインをRequireに設定します。条件を別のAllow policyやIncludeへ分けると許可範囲が広がるため、1つのポリシー内で組み合わせます。Dashboardへのログインとは別に、Accessの保護とセッションを確認します。

試験には専用の保護設定を使い、アカウント全体の保護や共有ログイン元を維持します。設定権限がなければ管理者へ依頼します。本人の認証は本人が行い、CookieやトークンはURL・共有資料・Gitへ含めません。性能上の問題が出た場合も、Paidプランへの変更を回避策として要求せず、許可範囲内で原因と結果を記録します。

本人限定のFeedは、一般のPodcastアプリやSNSからの取得試験とは分けて確認します。
