# CLI操作の簡素化に関する検討

対象: [Issue #119: castloop CLI利用時の操作を簡素化する](https://github.com/simosako/castloop-v2/issues/119)

調査対象: コミット `28262c5`、2026-11-01時点

この文書は改善案の比較です。Issueではワークスペースの指定とハッシュ値の引き継ぎを例に、Show作成から日常の公開・管理までの操作全体を見直すことが求められています。「案」の節にある新しいCLIオプションは仮称で、まだ実装されていません。

ここでのShowは番組、Episodeは個々の配信回、ワークスペースはサービス設定や編集ファイルを置くローカルディレクトリです。lifecycleは公開状態の停止・再開、revisionは保存済みの公開内容の版を指します。

案Aは採用され、初回公開・更新ガイドに反映済みです。案Bも、現在地から上位5階層までを探索する上限で採用されていますが、CLIへの実装はまだ行っていません。案C・Dは引き続き検討案です。

## 現状と課題

### ワークスペースはすでに省略できる場合がある

調査時の初回公開・更新ガイドでは主な例で毎回 `--workspace /path/to/workspace` を渡していました。案Aの適用後は、次の既存の使い方を基本例として案内しています。

| 実行場所・指定 | 現在の動作 |
| --- | --- |
| `init` の保存先を省略 | カレントディレクトリを使う。`init` はローカル作成だけでなくCloudflareのリソース作成・配備も行う |
| ワークスペース直下で `create-show`、`preview-show`、`publish-show`、`verify` などを実行 | `--workspace` を省略できる |
| ワークスペース直下でEpisodeの作成・プレビュー・公開などを実行 | `--workspace` を省略できるが `--show my-show` が必要 |
| `my-show/` 直下でEpisodeの作成・プレビュー・公開などを実行 | `--workspace` と `--show` を省略できる。ディレクトリ名をShow ID、親をワークスペースとして扱う |
| `--workspace` を指定してEpisodeの作成・プレビュー・公開などを実行 | カレントディレクトリによらず、別途 `--show` が必要 |

たとえば、ワークスペース直下でのEpisode作成から公開までのコマンドは、現行仕様のまま次のように書けます。作成後にTOMLを編集して音声をShowディレクトリに配置し、プレビュー後に内容と音声を確認して、結果の `input_fingerprint` を `REVIEWED_HASH` に置き換えます。

```sh
cd /path/to/workspace
castloop create-episode first --show my-show
castloop preview-episode first audio.mp3 --show my-show --remote
castloop publish-episode first audio.mp3 --show my-show --expect-preview REVIEWED_HASH
```

音声の相対パスはShowディレクトリ基準です。上の `audio.mp3` は `my-show/audio.mp3` を指します。プレビューと公開では同じ入力指定を使います。

一方、現行CLIは上位ディレクトリからワークスペースを探しません。たとえばShowディレクトリ内で `preview-show my-show` を実行しても、そのディレクトリをワークスペースとして扱います。Episodeでも、Showディレクトリのさらに下に移動すると、現在のディレクトリ名をShow IDとして扱います。また `doctor`、`backup-create`、`preview-schedule-time` などにもカレントディレクトリを使う既定がありますが、`import-rss`、`validate` などはそもそもワークスペースを必要としません。すべてのコマンドに一律の規則を当てることはできません。

相対パスの基準も一様ではありません。Episode音声はShowディレクトリ基準、lifecycle・revisionのプランファイルはワークスペース基準、`validate` の入力はカレントディレクトリ基準です。音声の絶対パスについて、調査時の初回公開ガイドと更新ガイドには説明の不一致がありました。案Aでは、実装と[保存構造](data/storage.md)に合わせ、[初回公開ガイド](../docs/getting_started.md)と[更新ガイド](../docs/publishing.md)の説明を統一しています。

根拠: [CLI入口](../packages/cli/src/index.ts)、[引数とヘルプ](../packages/cli/src/help.ts)、[音声パスの解決](../packages/cli/src/draft-preview.ts)、[CLI入口テスト](../packages/cli/src/sqlite-cli-entrypoint.test.ts)。

### ハッシュや版の引き継ぎには用途の違いがある

| 操作 | 現在の確認と引き継ぎ | 利用者の負担 |
| --- | --- | --- |
| 通常のShow/Episode公開 | プレビューの `input_fingerprint` を `--expect-preview` に渡せる。ガイドは確認後の引き継ぎを案内 | 64桁の値と、対象・音声引数を次のコマンドへ写す |
| 予約の作成 | 内容と時刻をプレビューし、`approval_sha256` を必須の `--expect-preview` に渡す | ハッシュに加えて時刻や音声を再指定する |
| 予約の変更・取消・再承認 | プレビューの承認ハッシュと予約の `version` を指定する。再承認のプレビュー自体にも現在の版が必要 | 予約ID、版、ハッシュを区別して写す |
| 非公開化・再公開 | プランをJSONに保存し、`request_sha256` と `confirm` を指定する | ファイル保存とハッシュの転記が必要 |
| 過去版の採用 | 履歴IDでプレビューし、プランの `request_sha256` と `confirm` を指定する | 履歴ID、プラン、ハッシュの転記が必要 |

通常公開の `--expect-preview` は**任意**です。省略してもCLIは公開時に入力と現在のリモート状態を読み直し、更新元などを検査しますが、以前に人が見たプレビューとの一致は確認しません。指定した場合は再計算した値と照合し、異なれば原則として公開を拒否します。すでに同一内容が公開済みの場合は、現行どおり再実行を `unchanged` として扱う例外があります。

ハッシュは確認した入力と実行時の入力を結び付ける値であり、それ自体が人間による承認の証拠ではありません。`--local` のプレビューではリモートの更新元を確認していないため、リモート確認を含む公開前レビューの代わりにはできません。予約、lifecycle、過去版採用では、それぞれ別の対象・版・時刻を含む値を使うため、単一の「ハッシュを省略する仕組み」に無条件でまとめるべきではありません。

根拠: [CLI設計](components/cli.md)、[通常公開](../packages/cli/src/sqlite-publish.ts)、[予約](../packages/cli/src/sqlite-schedule.ts)、[lifecycle](../packages/cli/src/sqlite-lifecycle.ts)、[過去版採用](../packages/cli/src/sqlite-revision-commands.ts)。

### 利用フロー全体での改善余地

| 段階 | 現状と負担 | 改善の方向 |
| --- | --- | --- |
| 初期設定 | `init` は不足項目を端末で質問できるが、調査時のガイドは長いパスと複数の値を例示していた。`service-status` の結果も確認する必要がある | 既存の対話入力とカレントディレクトリの例を案内し、リモート作成が始まる操作だと明示する |
| Show作成・編集 | `create-show` はリモート登録とローカル雛形の作成を行うが、公開はしない。TOMLとカバーの編集が必要 | 生成ファイル、次の編集・検証、未公開であることを分かりやすく案内する |
| Episode作成・公開 | `create-episode` 後にTOMLと音声を用意し、プレビューしてから公開する。長いJSONやハッシュ転記が負担 | 対象と差分を読みやすく示し、確認済みの値を手で写さずに公開できるようにする |
| 予約・公開停止・過去版採用 | 内容に加え、時刻、版、実行プランを確認する必要がある | 通常公開とは別の確認事項を表示し、それぞれの既存照合を残して転記を減らす |
| RSS移行 | ダウンロード後に内容を編集し、別コマンドでShowとEpisodeを順次公開する。途中まで公開される場合がある | 件数・不足項目・途中まで公開され得ることを明示し、確認と公開を別のまま分かりやすく案内する |
| 公開後・中断時 | `verify` で配信を確認できる。結果不明時は操作別に状態確認が必要 | 結果の意味と、対象に応じた状態確認を案内する。変更操作を自動再試行しない |

## 比較の前提

- **小**: 主に既存文書の変更。**中**: CLIの対象解決や表示・テストに変更が必要。**大**: 確認・永続化・複数操作の契約にまたがる。相対的な技術難易度であり、作業日数の確約ではありません。
- いずれの案でも、素材の準備やプレビューだけで公開しません。公開の操作は対象を確認したうえで明示的に実行します。
- 既存のサービス設定・対象・更新元・世代の照合、素材のサイズ・ハッシュ検証、公開前のキャッシュ消去、原本と公開済み素材の保持を維持します。
- `--workspace`、`--show`、`--expect-preview` を使う既存の明示的な操作と、`--json` / `--non-interactive` の非対話契約を維持します。機械向けの出力を対話文で汚さず、エージェントは従来どおり対象と承認済みハッシュを明示できます。
- Cloudflare上の操作をこの検討から実行すること、新しい依存関係を導入すること、入力内容や公開の意思をCLIが勝手に決めることは対象外です。

| 案 | 主に減らす負担 | 難易度 | 主なトレードオフ |
| --- | --- | --- | --- |
| A. 既存機能の案内を改善 | 不要な `--workspace`・`--show` の指定、パスの迷い | 小 | CLI自体は変わらず、ハッシュ転記は残る |
| B. ワークスペースの上位探索 | ディレクトリ移動や、場所に応じた `--workspace` の指定 | 中 | 暗黙の対象選択が増え、誤ったサービスを選ばない規則とテストが重要 |
| C. 対話式の確認付き公開 | 通常公開時のハッシュ転記と2コマンド間の引数再入力 | 中〜大 | 端末専用。表示・明示確認と再検証の設計が必要 |
| D. プレビュー情報をファイルに保存 | 別コマンド間でのハッシュ転記 | 大 | ローカルファイルの管理が増える。保存だけでは承認にならない |

A・Bは対象の指定方法、C・Dは確認内容の引き継ぎ方法に関する案です。組み合わせ可能ですが、CとDは同じ転記の問題を異なる方法で解決するため、最初から両方を実装する必要はありません。

参考として、ワークスペース直下で準備済みのEpisodeを確認して公開する場合の違いは次のとおりです。いずれも内容・音声の確認と、明示的な公開操作は残ります。

| 方法 | プレビュー・公開のCLI起動 | 利用者が引き継ぐもの |
| --- | --- | --- |
| 調査時のガイド例 | 2回 | 両方の `--workspace`、Show・音声指定、確認したハッシュ |
| 案A適用後のガイド例 | 2回 | Show・音声指定、確認したハッシュ |
| 案C | 1回 | ハッシュの転記は不要。表示を確認して端末で公開を指示 |
| 案D | 2回 | Show・音声指定と保存ファイルのパス。ハッシュの転記は不要 |

## 案A: 既存機能を人間向けの手順として案内する

初回利用・更新ガイドの基本例を、ワークスペース直下での操作に統一しました。Episodeでは `--show` を使う例を基本とし、Showディレクトリ直下からの省略方法も補足しています。別の場所からの操作やエージェント向けには、明示的な `--workspace` / `--show` の例を残し、音声の絶対・相対パスの説明も実装に合わせて統一しました。

- **メリット**: 実装を変えずにすぐ操作を短くできる。対象を明示したい利用者や自動化の手順も維持できる。
- **デメリット**: ワークスペース外や深いサブディレクトリでは引き続き指定・移動が必要。ハッシュや予約の版の転記は減らない。
- **難易度: 小**。主に `docs/getting_started.md`、`docs/publishing.md` と関連ガイドの例・パス説明を見直す。記載した例が現行CLIの引数規則に合うことを確認する。

## 案B: ワークスペースを上位ディレクトリから検出する

ワークスペースを使う通常の管理コマンドでは、明示指定がない場合、カレントディレクトリから親方向へ `castloop.toml` を探します。子ディレクトリを走査したり、複数のサービスから「最後に使ったもの」を選んだりしません。

対象の決定規則:

1. `--workspace` 指定時はそのパスだけを使い、上位を探索しない。Episodeでは現在どおり `--show` を必要とする。
2. 指定がなければ現在地から親を最大5階層たどり、最も近い `castloop.toml` を使う。現在地と上位5階層を含めて最大6ディレクトリを調べ、6階層目の親は調べない。途中でファイルシステムのルートに達した場合はそこまでとする。見つからなければ `--workspace` の明示指定を案内する。見つかった設定が不正・未対応なら、その場所でエラーにし、さらに上のサービスへ切り替えない。
3. Episodeの `--show` がない場合は、選択したワークスペース直下のShowディレクトリ内にいるときだけ、そのディレクトリと `show.toml` のIDを確認して対象を決める。それ以外は `--show` を求める。明示した `--show` は優先する。
4. `init` は新規作成先なので親を探索せず、現行どおり指定先またはカレントディレクトリを使う。ワークスペース不要のコマンドも探索しない。`doctor` や `preview-schedule-time` のように設定がない場所でも意味を持つコマンドは、初回対象から外し、現行の動作を維持する。
5. 人間向けの確認画面には選択したワークスペースとサービス・Showを表示する。音声やプランなど各引数のパス基準は変えず、説明を明確にする。

次は**案Bを実装した場合の例**です。現行CLIでは、Showディレクトリ内からのShowプレビューはワークスペースを自動検出しません。

```sh
cd /path/to/workspace/my-show
castloop preview-show my-show --remote
```

- **メリット**: Show内からShowとEpisodeの両方を扱え、より深いディレクトリからも同じワークスペースに戻れる。明示指定はそのまま使える。
- **デメリット**: これまで設定が見つからず失敗していた場所で操作が成立し得る。入れ子のワークスペースや誤った作業場所では、選択された対象の確認が従来以上に重要になる。ワークスペース直下ではEpisodeの `--show` は残る。
- **難易度: 中**。`packages/cli/src/index.ts` の対象解決、`help.ts` の説明、CLI入口テスト、利用・設計ガイドを更新する。明示指定、Show内、さらに下の階層、入れ子、不正な設定、`init` と対象外コマンドを検証する。

## 案C: 対話式の確認付き公開

通常の `publish-show` / `publish-episode` に、人間が明示的に選ぶ `--review` オプションを設けます。リモートプレビューを表示して同じプロセス内で確認を受け、そのプレビューの `input_fingerprint` を内部で公開処理へ渡す案です。

**以下は提案する操作例で、現行CLIでは使えません。**

```sh
cd /path/to/workspace
castloop publish-episode first audio.mp3 --show my-show --review
```

1. リモート状態を含むプレビューを取得し、ワークスペース、サービス、Show/Episode、変更前後の差分、音声・カバーの確認先、警告を表示する。利用者は必要に応じてファイルを開いて確認する。
2. 公開を行うことを明示する確認を端末で求める。拒否・入力終了ならアップロードも公開も行わない。
3. 確認済みフィンガープリントを使い、アップロード前に入力とリモート更新元を再照合してから、既存の公開処理へ進む。変更を検出したら再確認を求めるエラーにする。すでに同一内容が公開済みの再実行は現行の `unchanged` の扱いを維持する。
4. 未来の `published_at` を即時公開する場合の既存の専用確認または明示指定を維持する。日時の警告を一般的な確認文の中に隠さない。

このモードは端末でのみ使い、`--json`、`--non-interactive`、端末以外の入力と組み合わせた場合はエラーにします。自動的に確認なしの公開へ切り替えません。既存の `preview-*` と `publish-* --expect-preview HASH` は変更せず残します。省略されるのはハッシュの手作業による受け渡しであり、利用者による差分・素材の確認ではありません。

- **メリット**: 通常の公開は1コマンドで確認と実行ができ、ハッシュ・引数の転記が不要。最新の対象と差分を確認した直後に公開できる。
- **デメリット**: 長い差分や音声を確認する間プロセスを開いたままにする。確認後の再検証で素材を再度読むコストがある。端末を使わない自動化には別の既存手順が必要。
- **難易度: 中〜大**。`index.ts` の引数・端末処理、プレビュー表示、`sqlite-publish.ts` の既存照合の受け渡し、`help.ts` とCLI入口・公開テストが中心。確認拒否、非端末、入力やリモート状態の変更、同一内容、未来日時、既存JSON出力を検証する。

予約やlifecycle・過去版採用に広げる場合も、内容・対象・操作を示して端末で明示確認し、既存の `approval_sha256` / `request_sha256` と予約版を内部で渡す方法が考えられます。予約では現地時刻・UTC・タイムゾーンを表示し、停止や過去版採用では配信への影響を表示します。ただし各操作の確認対象が異なるため、通常公開とは別に設計・検証します。初回の案Cには含めません。

## 案D: 確認対象のプレビュー情報をファイルに保存する

プレビュー時に明示的な `--save-preview FILE` を指定した場合だけ、対象と `input_fingerprint` など、後で同じプレビューを特定するための最小限の情報をローカルファイルに保存します。公開時は `--review-file FILE` を明示して読み込み、現在のリモートプレビューと照合してから、内容と対象を端末に表示して公開の確認を求めます。

**以下は提案する操作例で、現行CLIでは使えません。**

```sh
cd /path/to/workspace
castloop preview-episode first audio.mp3 --show my-show --remote --save-preview .castloop/first-review.json
castloop publish-episode first audio.mp3 --show my-show --review-file .castloop/first-review.json
```

保存するのはリモート状態を確認したプレビューに限ります。保存ファイルは明示されたものだけを読み、暗黙に「最新」を選びません。対象サービス・Show/Episodeの不一致は拒否します。同じ対象でも現在の入力や更新元が変わっていれば、原則として再プレビューを求めます。ただし同一内容が公開済みの場合の `unchanged` は現行どおり扱います。新しいファイルとして保存し、別のレビュー情報を上書きしない扱いを想定します。保存を指定しないプレビューは現行どおりで、`--rss-output` を明示した場合を除きファイルを書き込みません。

ファイルの存在やハッシュの一致だけを承認とは見なさず、実行時の端末で対象と差分を再表示して明示確認します。確認後、アップロード前に案Cと同様の再照合を行います。`--review-file` は非端末・`--json`・`--non-interactive` では使わず、自動化は従来の `--expect-preview` を使います。保存する情報には管理者キーや本文を含めず、`.castloop/` 内の情報も非公開として扱います。この案ではレビュー情報を一時的なものとしてバックアップ対象に加えず、復元後は再プレビューします。

- **メリット**: プレビューと公開を別のコマンド・時間に分けても、64桁の値を手で写さずに済む。保存を明示した場合だけローカルに情報が残る。
- **デメリット**: ファイルの場所を指定・管理する手間が増え、案Cより操作が長い。ファイルを失った場合や入力が変わった場合は再プレビューが必要。ファイル自体は人が以前に確認した証拠や、改ざんを防ぐ仕組みではない。
- **難易度: 大**。案Cの確認・再検証に加え、保存形式と対象照合、ファイルの作成・読み取り、プレビューの `describe` 上の副作用、バックアップでの除外、テストとガイドが必要。ファイルの欠落・対象違い・古い入力の拒否と、明示しない場合に保存しないことも検証する。

## 採用状況と今後の検討

1. **案Aは採用・反映済み**。ガイドを短い操作例に更新し、エージェント向けの明示指定は残した。
2. **案Bは採用済み、未実装**。現在地と上位5階層を探索し、明示指定の優先、対象表示、誤選択を防ぐ既存の照合を維持する。階層数の上限だけで誤選択を防げるわけではない。
3. **案Cは検討案**。`--review` によりプレビューと公開を1コマンドにまとめるが、表示内容の確認・明示承認・実行前の再照合は省かない。通常公開のハッシュ転記を減らす場合、追加ファイルを要しない選択肢である。
4. **案Dは必要性が確認された場合の代替案**。端末で確認したまま操作を続けられず、プレビューと公開を別コマンドに分けたい利用形態が必要なら検討する。Cと両方を最初から実装しない。
5. 予約・非公開化・過去版採用は、通常公開向けの操作感を評価した後に個別検討する。各操作固有の対象、日時、版、プランを省略せずに確認・照合できることを条件とする。

実装する場合は、採用した案に応じて `bun test` と `npm run check` を実行し、CLIのヘルプ・`describe`・利用ガイド・設計と必要なSkillを同時に更新します。実環境への配備や公開は、その実装やテストとは別の明示的な許可が必要です。
