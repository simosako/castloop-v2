2026-10-26。**管理者が承認した既存Episode個別ページ方式を実装した。HTML解析は小検証の結果、第二候補の`htmlparser2`を採用した。その後の別承認で、本人限定の既存試験環境へ配備・再公開し、本人から表示と全文への移動が正常との報告を得た。後続のHTTP(S)リンク復元・フッター削除はローカル実装のみで、まだ配備していない。** §6.1〜6.2に生成範囲とFree制約、§11〜12にローカル検証、[実機確認記録](show_website_description_trial_verification_20261026.md)に非公開配備の結果と未確認範囲を記載する。[CSSカスタマイズの採用方針](show_website_customization_options.md)を維持し、固定HTMLとブラウザ標準機能の範囲で改善する。

## 1. 推奨する利用体験

**一覧ではHTMLタグを除いた先頭160文字を表示し、その説明文またはEpisodeタイトルをクリックすると、既存のEpisode個別ページで全文を読む。個別ページでは元の`<p>`による段落と`<br>`による改行を表示する。**

- 一覧は最新順20件と、その場で再生できる標準playerを維持する。
- 説明文をクリックできることが分かるように、「全文を読む」を同じリンク内へ添える。説明文全体をリンクとし、キーボードのfocusも表示する。
- 個別ページにも標準player、番組トップとRSSへのリンクを置く。URL・公開判定・音源参照は変更しない。
- 管理者用の新しい表示切替設定や、テンプレート・ブラウザJavaScriptは追加しない。

ここで「オリジナルのまま」は、**文章全文と段落・改行の意味を維持する**という意味とする。任意のHTML・属性・scriptを元のbytesのまま挿入する意味ではない。元の説明文自体は変更せず、Webサイト向けの表示だけを変える。

## 2. 現状と必要な変更

第1段の[`src/site-renderer.ts`](../src/site-renderer.ts)は、説明文字列をそのまま160文字へ短縮してからHTMLの特殊文字をescapeしていた。このため、タグも文字数に含まれ、`<p>`等が画面に現れた。個別ページも全文をescapeするだけで、段落タグを描画しなかった。`meta description`とOGP（SNS等へページの概要を伝える情報）の説明も同じ影響を受けた。今回、この部分を以下の表示ルールへ変更した。

escapeとは、例えば`<`を`&lt;`へ置き換え、本文をHTMLタグとして解釈させない処理を指す。以下の表示改善でも、本文のescapeは維持する。

一方、**Episode個別ページはすでに事前生成している**。新しいページ種別・API・R2公開パスを作る必要はない。タイトルはすでに個別ページへのリンクなので、説明文にも同じ行き先を設定できる。

また、[`stripHtmlTags`](../packages/shared/src/metadata-limits.ts)は入力上限の計測用の簡易処理であり、安全なHTML生成用の処理ではない。これを変更して既存の入力上限・RSS受け入れ条件を変えることはしない。

## 3. 全文を読む方法の比較

| 方式 | メリット | デメリット | 推奨 |
| --- | --- | --- | --- |
| **1. 既存の個別ページへ移動** | 既存の生成・URL・公開制御を再利用。一覧へ全文を重複保存しない。通常のリンクなので操作・共有が分かりやすい。JS不要 | 同じタブで移動すると一覧の再生は終了する。全文を読むためにHTMLを1回取得する | **第一推奨**。小さく保つことと、Free枠の生成・転送量を優先 |
| **2. 一覧内の`details`／`summary`で展開** | 説明文クリックでその場に全文が開く。標準HTMLだけで開閉でき、追加通信なし。一覧のplayerを開閉領域の外へ置けば、再生中に読める | 閉じていても20件分の全文をHTMLへ含める。既存の個別ページとの重複が増える。開いた分だけ一覧が縦に伸びる | 再生を続けながら読むことを優先する場合の有力な第二案 |
| 3. JSで全文を取得して展開／modal表示 | 初回HTMLを小さくして、同じ場所で全文を読める | script・CSP変更・追加通信・取得失敗やfocusの扱いが増える。現要件には過剰 | 採用しない |

方式2は複雑なフレームワークを必要とする案ではなく、十分シンプルな選択肢である。ただし、**非表示にするだけではHTMLの生成量・保存量・転送量は減らない**。1件の説明が10,000文字なら、20件では全文だけで最大200,000文字となり、さらにタグ・escape・CSS等が加わる。実際には既存のmetadata全体・HTML容量制限も適用される。

方式2を選ぶ場合も、Episodeタイトルから既存の個別ページへ移動できるようにする。抜粋を`summary`、安全に整形した全文を展開領域へ置き、playerはその外に残す。独自JSや表示方式を切り替える設定項目は追加しない。

方式1では、別タブで開けば一覧の再生を続けながら全文を読めるが、通常クリックでの連続再生を保証する仕様にはしない。再生継続を必須にする場合は方式2が適する。

## 4. 説明文の表示ルール

### 4.1 一覧の160文字

次の順序で処理する。

1. 説明文をHTMLとして解析し、表示する本文だけを取り出す。タグ・属性・コメントは抜粋に含めない。
2. 本文内の`&amp;`、`&nbsp;`、数値文字参照などを文字へ戻す。`&amp;`は`&`という1文字として数える。この変換は一度だけ行い、変換で現れた`<p>`等を再びHTMLとして解釈しない。
3. 段落・改行・箇条書き等の区切りを空白へ変換し、前後の空白を除去し、連続する空白を1つにまとめる。例えば`</p><p>`を削除して前後の単語を連結しない。文字参照から得た空白も同じ正規化に含める。
4. 正規化後の本文を先頭160文字に短縮する。160文字を超える場合だけ末尾に`…`を追加する。
5. 最後にHTMLの特殊文字をescapeして、リンクの本文へ出力する。

文字数は既存コードと同じUnicode code point（1つのUnicode符号）単位とし、日本語や通常の絵文字をUTF-16の途中で分割しない。「全文を読む」のラベルと省略記号は160文字の枠外とする。

160文字以下でも、元の段落を読めるように個別ページへのリンクを置く。タグ等を除くと本文が空になる入力では、空の説明リンクを作らず、タイトルのリンクを残す。

例:

```html
<p>最初の段落</p><p>次の段落<br>続き &amp; 補足</p>
```

一覧の本文は`最初の段落 次の段落 続き & 補足`になる。HTMLタグや`&amp;`という記法は表示しない。

### 4.2 個別ページの全文

| 元データの要素 | 表示 |
| --- | --- |
| `<p>`、`</p>` | 段落として表示。元の属性は引き継がない |
| `<br>`、`<br/>`、`<br />` | 改行として表示 |
| 通常の文章・文字参照 | 全文を維持し、文字参照を一度解いてから安全にescape。本文中のHTTP(S) URLは§12の規則でリンク化 |
| HTMLタグのない文章の改行 | 改行を維持する。HTMLを知らなくても説明を書ける |
| `<strong>`、`<em>`、`<span>`等 | タグは除き、本文を残す。初期範囲では装飾を再現しない |
| `<a>` | 安全なHTTP(S)の絶対URLだけをリンク先として復元。元の属性全体はコピーせず、表示文字列と検証済み`href`から作り直す。詳細は§12 |
| `<ul>`、`<ol>`、`<li>`、`<div>`等 | 本文を残し、項目・ブロックの境界を改行にする。箇条書きの装飾等は再現しない |
| script・style・埋込み・フォーム等の非本文要素 | 対応する要素とその内容を除く。説明欄に別playerや外部画像を挿入できないようにする |
| コメント、DOCTYPE、属性全般 | 引き継がない |

**初期実装の許可タグは`p`と`br`だけ**だった。本人レビュー後、§12のHTTP(S)リンクに限って固定の`a`を追加した。これは原本のHTML全体を忠実再現する機能ではなく、元の属性・装飾等は引き継がない。

HTMLの文章では`p`／`br`を段落・改行の基準にし、HTMLソースの字下げ用改行まで追加の`br`にはしない。タグのないプレーンテキストでは元の改行を維持する。閉じタグの省略等は採用するHTML解析処理の規則で正規化し、壊れた入力を文字列の継ぎ足しで修復しない。

出力は`<div class="cl-description cl-description-full">`の内側へ生成する。現在の説明用`p`の中へ、さらに`p`を入れる無効なHTMLにはしない。カスタムCSS用の既存class `cl-description`は維持し、段落の余白と表示の区別に必要なclassだけを追加する。

### 4.3 Show説明・meta情報

- Showの説明も同じ安全な段落・改行の表示処理を使う。番組紹介を全文表示する現在の構成は維持し、Show用の折り畳みUIは追加しない。
- `meta description`とOGPの説明は、一覧と同じタグなしの短い本文を使う。属性へ埋め込む直前のescapeは維持する。
- title、author、copyright等はこれまでどおりテキストとしてescapeする。説明以外へHTMLの許可範囲を広げない。

## 5. 安全な変換と依存の選び方

RSS由来の説明文は、第三者が作った文字列を含む。元のHTMLをそのまま挿入すると、リンク・画像・CSS・イベント属性等を通して固定ページへ影響できる。**CSP（ブラウザへ読み込み・実行の制限を伝える応答header）でscriptを止めることだけを理由に、生HTMLを許可しない。**

変換では、解析したテキストと段落・改行の区切り、安全と検証したHTTP(S)リンク先だけを取り出し、castloop側が固定の`<p>`・`<br>`・`<a href="...">`とescape済み本文から表示を作り直す。元の開始タグ、属性全体、HTML断片を流用しない。例えば`<p onclick="..." style="...">`からは、属性のない`<p>`だけを生成する。

| 解析方法 | メリット | デメリット | 推奨 |
| --- | --- | --- | --- |
| 正規表現でタグ削除・一部タグだけ差し戻す | 依存追加なし | 引用符内の`>`、コメント、文字参照、script内の文字列等の処理を独自に増やすことになる。入力上限用の簡易処理では不足 | 採用しない |
| **Cloudflare標準の`HTMLRewriter`＋文字参照decoder** | WorkerのHTML解析機能を使え、新しいHTML parserやDOM構築ライブラリは不要。Node.jsも不要 | 非同期処理への接続が必要。文字参照を戻すdecoderは別途必要。Bunと実Workerの挙動差を検証する必要がある | **第一候補**。追加依存は文字参照用の`entities` 1件に限定する案 |
| `htmlparser2`のイベントAPIで解析・再構成 | 同期処理で既存rendererへ接続しやすい。文字参照のdecodeを含められる。DOM全体を作らずに済む | 新しいparserとその推移依存が増える。ブラウザと完全に同じHTML解析ではない | 第二候補。第一候補を実装するための独自処理がかえって大きくなる場合に再評価 |
| 既存の`saxes`を流用 | 既存依存を使える | XML parserなので、通常の`<br>`や閉じタグ省略、HTMLの文字参照をそのまま扱えない | RSS外側のXML解析だけに使い、説明のHTMLへ転用しない |

この比較は実装前の候補である。検証後は第二候補を採用し、`htmlparser2@10.1.0`だけを直接依存に追加した。文字参照はparser内のdecoderで一度だけ処理し、`entities`の直接依存や別のHTMLRewriter変換を併用しない。ライセンスとbundle差分は§11に記載する。

ローカルのBunで、`HTMLRewriter`が存在し、`<p>`・`<br>`の要素イベントを受け取れることを小さな読取実験で確認した。同じ実験でtextイベントの文字列に`&amp;`・数値文字参照が残ることも確認したので、「標準parserだけで表示文字数まで数えられる」とは仮定しない。テキストイベントは複数chunkに分かれ得るため、文字参照を途中で切ってdecodeしない。**これは変換機能の完成や実Cloudflareでの検証ではない。**

小検証では`<p>one<p>two`のように閉じタグを省略すると、HTMLRewriterの`onEndTag`は呼ばれなかった。また、要素を`remove()`してもdocument text handlerから本文を取得できた。本文の再構成・除外領域の追跡を独自に増やすより、暗黙の閉じタグを通知する`htmlparser2`のイベントAPIで同期的に処理する方が小さいと判断した。これはBun上の観察であり、Cloudflareでの挙動を測定した主張ではない。自作の汎用HTML sanitizerやDOM構築処理は追加しない。

## 6. Cloudflare Freeと処理の分担

```text
保存済みの元説明文
  → 明示公開／復元／domain保守でのShow DOのHTML生成
  → 説明文を解析し、抜粋と安全な全文表示を生成
  → HTMLをprivate R2へ保存・検証
  → 必要なpurgeと既存の原子的な公開切替

閲覧
  → 既存の公開判定とCDN配信
  → 完成済みHTMLを表示。閲覧時のHTML解析・全文取得用APIは設けない
```

- HTML生成の担当をCLIへ移す変更はしない。サーバーだけで行う復元やdomain変更にも、保存済みの元説明文から対応できる。
- 音源・画像の解析、uploadとreadback照合は従来どおりCLI。音声の取得・再生経路は変更しない。
- 解析は公開時に行い、同じページ内で本文・抜粋・meta情報を別々に繰り返し解析しない。巨大なDOMや汎用テンプレート処理系は導入しない。
- metadataの既存入力予算、1 HTMLの1,000,000 bytes、1 batchの最大20 HTML／合計4,000,000 bytesを維持する。説明文の見える文字数だけで実際の解析入力sizeを見積もらない。
- HTMLの解析や生成に失敗したときは、既存の失敗・停止契約で扱う。元の生HTMLへfallbackしたり、公開書込をやり直して成功扱いにしたりしない。
- 新しいWorker・DO・R2 bucket・有料サービス・CPU上限変更は不要。ただし解析分の生成CPUは増えるため、**Free枠内で必ず完了するという実測結果はまだない**。採用する処理と実データで検証する。

方式1では全文を含めるのは従来どおり個別ページだけで、一覧への全文の追加保存はない。方式2なら、その追加分もHTMLの容量・履歴・R2操作・転送の予算へ含める。

### 6.1 Episode追加時の生成範囲：現行実装

**すべてのページを再生成する方式でも、変更した1ファイルだけを書く方式でもない。全一覧ページと、追加・更新したEpisodeの個別ページを生成し、他の個別ページは以前のHTMLを再利用する。** 今回の説明表示改善でも、この生成範囲を増やさない。

| 操作 | 一覧ページ | Episode個別ページ | RSS・音源 |
| --- | --- | --- | --- |
| Episodeを1件追加 | 20件区切りの全一覧を再生成 | 新しい回の1ページだけ生成。既存の個別ページは再利用 | RSSは全体を再生成。新音源だけを保存し、既存音源は再処理・再uploadしない |
| Episodeの説明・タイトル・音源を更新 | 全一覧を再生成 | 対象の1ページだけ再生成 | RSSは全体を再生成。音源差し替えがなければ既存音源を利用 |
| Episodeを非公開化・復元 | 全一覧を再生成 | 非公開化は対象ページの公開参照を外す。復元は対象ページを生成。他の個別ページは再利用 | RSSを再生成し、既存の配信制御を適用 |
| Showの説明・CSS等を更新、Show復元、domain変更 | 全一覧を再生成 | 全公開Episodeのページを再生成 | 共通情報・URLをRSSへ反映。既存MP3の解析や再uploadは不要 |

先頭へ新しい回を追加すると、1ページ目の20件目が2ページ目へ押し出され、以後も内容がずれる。現在の番号付きページでは、それに合わせて一覧を作り直す。内容が同じページかどうかを比較して書込を省略する処理は、現時点では設けていない。

1件追加後の公開Episode数を`N`とすると、生成するHTML数は**`ceil(N / 20) + 1`**（0件のShow一覧は別扱い）。`ceil`は割り算の端数を切り上げることを意味する。

| 追加後のEpisode数 | 一覧HTML | 新規個別HTML | 合計 |
| ---: | ---: | ---: | ---: |
| 20 | 1 | 1 | 2 |
| 100 | 5 | 1 | 6 |
| 1,000 | 50 | 1 | 51 |

HTMLの生成・R2保存はShow DOのAlarmで、1回あたり最大20 HTML・合計4,000,000 bytesに分ける。正常にbatchを完了して続行情報と次のAlarm予約を保存できた場合だけ、次回へ進む。51 HTMLならファイル数だけでも最低3回のbatchとなり、bytesの上限に達すればさらに分かれる。中断・結果不明の書込を再実行する仕組みではない。

コード上の対応は、[`withSitePublication`](../src/site-publication.ts)が対象Episode IDを渡し、[`SqliteSiteContent.prepare`／`batch`／`commit`](../src/sqlite-site-content.ts)が入力固定・分割生成・未変更個別ページの参照維持を行う。[Alarm実行部](../src/sqlite-publication-alarm.ts)は正常な続行と未知の中断を区別する。

### 6.2 「分割しているからFreeで保証できる」とは言えない理由

HTMLファイル数以外にも、次の全件処理がある。

- 公開済みEpisodeのmetadataをSQLから読み、順序を決め、新しい生成処理の固定入力として**全件をSQLへ保存**する。この準備は現状、Episode単位のbatchへ分割していない。未変更の個別HTMLを再利用しても、このSQL処理は残る。
- RSSは公開済みEpisode全件を含む1ファイルとして再生成する。これもHTMLの20ファイルbatchとは別で、一括生成して保存する。現行コードでは最初の公開検証時に生成し、Alarmをまたぐ場合は最終batch後の再検証時にも生成する。
- R2のHTML・Feed世代、SQLの生成入力や必要な履歴は保持するため、公開を重ねれば容量も増える。batch化は合計のCPU・SQL操作数・R2操作数や保存量を一定にする仕組みではない。

公式のDO SQLite Free枠は、2026-10-26確認時点で**read 500万rows／日、write 10万rows／日、SQL保存容量はアカウント合計5 GB**。index更新や削除等もwriteへ算入されるため、「Episode 1件追加＝SQL 1行書込」ではない。これらは他のShow・サービスとの合計であり、Worker／DO要求・duration・R2にも別の無料利用枠がある。

通常の閲覧要求で全文のHTML解析・全ページ生成を行わず、DO Alarmで事前生成する点は維持する。DOのCPU制限と通常WorkerのHTTP CPU制限は区別し、どちらも上限拡張・有料化を前提にしない。ただし、**現在の実機証拠は通常サイズ音源3件の公開までであり、数百〜数千Episodeや、今回追加する説明解析を含むFree適合はまだ確認していない。**

開発ではまずこの部分再生成方式を維持し、20件・100件・1,000件等のローカル試験で、生成HTML数・既存個別ページの再利用・実際のSQL処理量を確認する。大きい音源を再uploadする必要はなく、metadataと短い試験音源で生成規模を評価できる。実CloudflareでのCPU・日次消費は別途承認された試験で測り、準備処理・RSS・HTML生成を分けて評価する。そこで問題が確認された箇所に限って、分割や入力の保存方法等を見直す。測定前に「無料枠で問題ない」と断言したり、今回の改善を理由に全個別ページの毎回再生成へ広げたりしない。

## 7. 保存内容・更新・CSSへの影響

- 元のShow/Episode説明文、RSS、GUID、公開日時、音源identity、revision履歴は変更しない。新しい派生metadata fieldを保存しない。
- 保存形式の変更は不要の見込みで、queue/content schema変更や旧環境のDB変換を今回の表示改善へ混ぜない。
- **Worker更新だけでは既存の保存済みHTMLは変わらない。** 更新後、対象Showの明示公開で全一覧・個別ページを再生成する。Show更新を使うため、音源の再uploadは不要。
- Worker更新に必要なPause・drain・検証・明示再開等の既存手順は省略しない。今回の設計検討は、現在の試験環境への更新・再公開の許可ではない。
- 過去revision採用・復元・domain再生成でも同じ表示処理を通す。以前のHTMLは上書き・削除せず、新しい世代を保存する。
- 標準CSSと任意CSS 1ファイルの方式を維持する。新しいCSSのhashも既存のCSP保存・配信経路へ接続し、script禁止・外部素材の制限を緩めない。

## 12. 本人レビュー後のリンク復元とフッター削除

この節は後続のローカル実装。前節までの814試験と、配備済み世代5のHTMLとは区別する。実環境の更新・再公開は行っていない。

- Showの`copyright`を置くだけのフッターを削除する。番組紹介の`author`、元metadata、RSSの著作権情報は維持する。
- Show紹介とEpisode個別ページの全文に、本文中のHTTP(S) URLをリンクとして生成する。日本語の句読点・括弧などを区切りにし、末尾の英文句読点や対応しない閉じ括弧をURLへ含めない。URLに含めたい曖昧な記号は、元データで`a href`を明示すると正確に指定できる。
- 元の`a`も、HTTP(S)の絶対URLと表示文字列に限って復元する。URL parserで検証し、認証情報・制御文字・backslashのあるURL、相対URL、他schemeは不許可。検証はリンクの構文に対するものであり、リンク先サイトの安全性や信用を保証しない。サーバーからリンク先を取得しない。
- `href`の文字参照はHTML parserで一度だけ解く。生成時にはURLと表示文字列を別々にescapeし、`onclick`・`style`・`target`などはコピーしない。同じタブで移動するため、ページを離れると再生は終了する。
- 一覧の抜粋とmeta／OGPは従来どおり本文だけから作る。抜粋内に外部リンクを入れて、全文リンクの中へ別の`a`を入れることはしない。元のリンク先が表示文字列と異なる場合、その文字列から追加のリンクは生成しない。
- 依存・JS・API・保存形式・HTML生成範囲を増やさない。リンク検出は公開時の本文変換へ追加するだけで、閲覧時のCPU負荷や外部通信を追加しない。生成CPUのFree適合は引き続き未測定。

URL短縮は[別の検討案](show_website_site_slug_proposal.md)であり、この実装には含めない。後続レビューで手動`site_slug`案を取り下げ、自動ハッシュ方式を推奨している。
