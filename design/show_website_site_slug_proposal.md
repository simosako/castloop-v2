# Issue #70: Episodeページの自動短縮URL検討案

2026-10-26。**採用方針をローカル実装。管理者がEpisodeごとに`site_slug`を指定する前案は、作業負担と付け忘れを避けるため取り下げる。長いページURLとの併存案と`e/`という中間パスも取り下げ、Show直下の短いURLだけをEpisodeページの正式な入口とする。** castloopは未実運用のため、過去デプロイとの互換性・マイグレーションは設計対象外とし、新規環境向けに実装する。短いページ識別子はシステムが自動生成し、TOML項目・CLIオプションを増やさない。HTTP(S)リンク復元・フッター削除も同じ開発版へ含める。

## 1. 推奨する方式

**Episode ID全体のSHA-256を計算し、小文字16進数の先頭16文字をページ専用の短い識別子にする。** SHA-256は一定の入力から一定のハッシュ値を得る処理であり、Web標準の暗号APIを使えるため追加依存は不要。タイトル・説明・公開順・音源からは生成しない。

RSS取り込みのIDは現在`ep-`＋GUIDのSHA-256だが、通常のCLIで作るEpisode IDはハッシュとは限らない。両方を一つの規則で扱うため、既存IDの先頭を直接切り出すのではなく、すべてのEpisode ID全体を同じ方法でハッシュ化する。

```text
Episode ID
  ep-8cc15ae4c2a0628ca3db2113afd7315c79299e865e8108b68d57042d726cd652

SHA-256(Episode ID)の先頭16文字
  db0a48404cdf5c53

ページURL案
  /podcasts/site70-normal/db0a48404cdf5c53/
```

管理者による命名・設定は不要。タイトル変更・説明更新・音源差し替えでもEpisode IDは維持されるため、短いURLも維持できる。hostnameとShow IDは変わらず、試験用の長い`workers.dev` hostnameまで短くする機能ではない。

`/podcasts/<showId>/<shortId>/`をEpisodeページの唯一の入口とする。`e/`や`episodes/<episodeId>/`というページ入口、互換用の別入口・転送は設けない。一覧・RSS・canonical・OGPはすべて同じ短いURLを指す。内部Episode IDから別の公開ページURLを作る必要はない。

ページ識別子は16〜64文字の小文字16進数で、衝突時は4文字ずつ延ばす。この形式だけをEpisodeページとして受け付けるため、既存の番組トップ`/podcasts/<showId>/`、一覧の`page/2/`、`feed.xml`、`cover.jpg`等と区別できる。ページ種別を示すためだけの中間パスは不要である。

一方、`episodes/<episodeId>/<revisionId>.mp3`は音源ファイルのURLであり、ページURLとは別である。公開済み音源の不変性を保つため、こちらは変更しない。「1 Episodeに1 URL」はWebページの入口についての方針であり、音源・Feed・画像のURLをなくす意味ではない。

## 2. 候補の比較

| 方式 | メリット | デメリット | 判断 |
| --- | --- | --- | --- |
| 管理者が別名を入力 | 意味のある名前にできる | Episodeごとの作業・付け忘れ・命名の重複 | 取り下げる。任意設定としても初期範囲へ残さない |
| 既存IDをそのまま切り詰める | 実装が短い | ハッシュ以外のIDにも適用すると共通接頭辞等で衝突しやすい | 採用しない |
| **SHA-256の先頭16文字（64 bit）** | 小文字英数字だけで扱いやすい。全Episodeに同じ規則を使える | 短縮なので衝突確認は必要 | **推奨** |
| SHA-256の先頭9 bytesをBase64url化（12文字・72 bit） | より短く、URLに使える | 大文字小文字・`-`・`_`を区別し、目視・手入力が少し難しい | 短さを最優先する場合の第二案 |
| ランダムな短い識別子 | IDからの計算が不要 | 固定結果を入力から再現できず、生成結果の保存が必須。衝突確認は同様に必要 | 今回は決定的なハッシュを優先 |

16文字を推奨するのは、短さと扱いやすさの折り合いである。現在のRSS由来IDの67文字から16文字になる。8文字の16進数では32 bitしかなく、Episode数が増えた場合の衝突確率が相対的に高いため採用しない。

## 3. 衝突とURLの安定性

短縮ハッシュが絶対に重複しないとは扱わない。推奨する割り当て規則は次のとおり。

1. Episodeを初めて公開する準備時に、Show内で16文字の候補を予約する。外部サイト方式でも、後の内蔵方式への切替に備えて予約する。
2. 同じEpisodeの予約なら再利用する。他Episodeがすでに使っていれば、新しく割り当てるEpisodeだけ20文字、24文字と4文字ずつ延ばす。
3. 最大64文字でも別Episodeと衝突すれば、公開前の確定エラーで停止する。既存ページへの誤配信や他Episodeの予約の奪取はしない。
4. 割り当て済みの対応を保存し、一度公開した短いURLは変更・削除・再利用しない。後からEpisodeが増えても、先に公開したページのURLは変えない。

64 bitが均等に分布するという前提では、1万Episodeで少なくとも一組が衝突する確率は概算約3,700億分の1（約`2.7 × 10^-12`）。ただし確率の小ささは一意性検証の代わりではない。割り当てはShow内の既存の逐次公開・transactionへ接続し、一意制約で保証する。

衝突時の長さは予約順で決まるので、別環境へ同じEpisode群を逆順で新規登録した場合まで同じ短縮結果になるとは保証しない。同じサービス内の更新・非公開化・復元・過去revision採用では保存した割り当てを維持する。

## 4. 変わるもの・変わらないもの

| 対象 | 推奨する扱い |
| --- | --- |
| 一覧タイトルと「全文を読む」の行き先 | 自動生成した短いURLへ |
| ページのcanonical／OGP URL | 短いURLを代表として指定 |
| 内蔵サイトのRSS item link | 短いページURLへ |
| 元の長いページURL・`e/`付きURL | 提供しない。アクセスは404とし、互換用の別入口・転送を設けない |
| Episode ID、RSS GUID、公開日時 | 変更しない |
| MP3 URL・R2音源・音源identity | 変更しない。再upload不要 |
| 管理者のTOML・CLI操作 | 命名用の追加項目・手順なし |
| 公開・停止制御 | 短いURLから内部Episode IDを解決し、既存のShow／Episodeの公開・Pause判定を使う |

HTMLは従来と同じく1 Episodeあたり1ページを生成し、短いURLだけから配信する。R2の非公開snapshotの保存keyに内部Episode IDを使うことは妨げない。保存keyは内部の識別方法であり、もう一つの公開URLではない。非公開化した回はページの配信を止める。

過去の試験デプロイで作成したURLや保存形式との互換性は考慮しない。旧URLの転送・旧DBの変換・移行手順は作らない。既存試験環境の更新・削除や証跡の整理はこの設計とは別の操作であり、本書の変更をその許可とは扱わない。

## 5. Cloudflare Freeと実装への影響

- 追加のWorker・DO・外部サービス・ライブラリは不要。既存Show DOで新しいEpisodeのページ識別子を割り当てる。
- ハッシュ計算はIDに対して割り当て時に行い、閲覧時には行わない。Show内の小さな対応表を索引検索し、元IDの既存配信判定・HTML cache経路へ接続する。全Episodeの走査や閲覧時HTML生成はしない。
- 通常のEpisode追加で全個別ページを再生成する方式には変えない。対応表の保持・更新によるSQL保存量・操作は増えるので、無負荷になるという意味ではない。
- RSS link、URL解析、予約・公開の原子的確定、revision復元、cache・purgeを整合させる必要がある。必要な保存形式は新規環境向けに確定する。旧形式への対応・DB変換・移行は実装しない。
- 未公開の予約や結果不明の公開があっても、別のEpisodeへ名前を再割り当てしない。過去revisionだけに依存せず、必要な小さい予約を保持する。
- **短いURLやハッシュはアクセス制御ではない。** テストサイトの本人限定Access保護は短い入口へ適用し、保護を検証する。

**採用方式は、手動`site_slug`を設けず、自動16文字ハッシュ＋衝突時だけ延長＋公開済みURL固定。Episodeページの公開URLはShow直下の短いもの一つだけとし、互換性・移行の仕組みは追加しない。** Free性能の実測は今後の検証事項である。

## 6. 実装

- `src/sqlite-site-ids.ts`のShow内対応表で予約する。SHA-256はtransaction外で計算し、予約の再確認・衝突確認・INSERTは同期transactionと一意制約で確定する。結果不明や未公開の予約も削除しない。
- 外部方式で公開した回にも予約を保持する。将来そのShowを内蔵方式へ切り替える場合とRSS previewに同じ予約を使えるためであり、外部方式でHTMLを生成するものではない。
- HTML生成時は対応を入力snapshotへ固定し、RSSも同じ対応を使う。部分更新は一覧と対象個別ページだけを置き換え、ページ種別をSQL列で区別して無関係な個別ページを保持する。
- 公開参照の切替はFeed・media・HTML両cacheのpurge成功後の既存transactionで行う。予約しただけの回は公開Episodeがないため404になる。非公開回は同じ短いURLでも404、Show停止・readiness不一致は従来どおり503となる。
- RSS previewの一覧応答に各回の予約を含め、新規対象の内容照会は未予約候補を返す。照会は予約を作らず、公開完了の証拠にもならない。
- 内部queue/content形式を**10/11**、health／inspectionのサイト識別を`static-show-v2`に更新。旧`static-show-v1`はCLIの能力照会で拒否し、旧DBはWorkerでも拒否する。サービス設定version 2・metadata version 1・DOとcacheのクラス名・bindings・compatibility date・音源保存形式は変更しない。DB変換は提供しない。

- 普通のID・RSS由来の長いIDのSHA-256、保存後の再読込、Show間の独立性、16／20文字衝突後の24文字への延長、64文字まで衝突する場合の確定エラーを確認した。衝突は試験用DBへの予約挿入で再現し、ハッシュ関数の差し替え設定は製品へ追加していない。
