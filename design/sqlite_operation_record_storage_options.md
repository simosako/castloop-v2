# Issue #40: サーバー側の操作記録をどこに保存するか

更新日: 2026-10-19。案Bを具体化するための比較資料。
料金と上限は、同日時点のCloudflare公式資料に基づく。

2026-10-20追補: Issue #48では[Show単位DO](do_show_separation_options.md)を採用した。本書の「公開状態と同じDO SQLiteに操作記録を置く」方針をShow内で維持し、容量表示もShow DB単位とする。アカウント共通の容量・日次枠は増えない。以下の比較・旧見積もりは新layoutの実機計測ではない。

保存先は既存DO内のSQLiteで検討を進める。作業と要求の区別、要求元クライアントの記録方法、具体的なDDLは、[操作記録のIDとテーブル設計](sqlite_operation_records_schema.md)を参照する。

## 1. 推奨する構成

**操作の状態と履歴は既存DOのSQLiteに保存し、障害調査用の情報はWorkers Logsにも出力する構成を推奨する。**

- **DOのSQLite**：CLIからの状態確認、再開、取消、削除の判断に使う。
- **Workers Logs**：操作IDから関連する実行を検索し、エラーや所要時間を調べる。
- **R2**：大量の診断情報を長期間残す必要が出た場合の保存先とする。

D1も有力な候補である。ただし、現在は公開状態をDOのSQLiteで管理している。操作記録も同じ場所に置くと、公開状態の変更と操作の記録を一度に確定できる。今回の用途では、この利点が大きい。

記録機能だけであれば、週〜日数件程度のPodcast運用は無料枠内に収まる見込みである。初期構成は、必要な小さい記録を保持し、容量を表示・監視する方式とする。費用の見積もりは[4節](#4-上限とコスト)、記録の保持・整理は[6節](#6-容量管理と記録の保持)に記載する。

## 2. 保存する情報を分ける

「記録」には用途の異なる情報がある。まず、この三つを分けて考える。

| 種類 | 内容の例 | 必要な性質 |
| --- | --- | --- |
| 操作の現在状態 | 対象、処理段階、アップロード結果、公開処理との対応、取消状態 | 最新の状態を確実に取得でき、関連する状態とまとめて更新できる |
| 操作の履歴 | 開始、保存成功、検証完了、公開受付、取消、削除結果 | 操作ごとに順番を追え、後日も結果を確認できる |
| 障害調査用のログ | エラーコード、HTTP status、所要時間、Workerの実行情報 | 条件検索や集計がしやすく、必要な期間を調査できる |

前二つが、再開や取消の判断に使う記録である。例えば「アップロード済み」というログを一行出すだけでなく、どの操作のどのファイルが保存されたのかを、後から照会できる形にする。

主な検索は、次を想定する。

- 操作IDを指定して、現在状態と履歴を調べる。
- RSS取り込みIDを指定して、各エピソードの進捗を一覧にする。
- 番組・エピソード・処理状態・期間で操作を絞り込む。
- エラーコードや所要時間から、複数の操作に共通する問題を調べる。

現時点では、一つのサービス内での検索を中心に考える。複数サービスを横断する長期的な検索が主目的になった場合は、D1の価値が高くなる。

## 3. 保存先の比較

| 候補 | 更新時の性能・整合性 | 検索性 | 今回の用途への適性 |
| --- | --- | --- | --- |
| 既存DO内のSQLite | 処理とDBが同じ場所にあり、公開状態と一つのトランザクションで更新できる | SQL、索引、Data Studio。CLI向け検索APIも作れる | 操作の現在状態と履歴に最適 |
| D1 | DBへの通信が加わる。D1内の更新はまとめられるが、DOの更新とは別になる | SQL、HTTP API、管理・入出力ツールが充実 | 独立した管理DBや、サービス横断検索に向く |
| Workers Logs | アプリから出力し、別系統で収集する。DB更新とログ保存は別になる | DashboardとREST APIで検索・集計できる | 障害調査に向く |
| R2 | ファイル単位で保存する。複数ファイルやDOの状態との一括更新は別途設計が必要 | キーによる取得・列挙。内容による検索には索引などが必要 | 大量の診断情報の長期保存に向く |
| Workers KV | 読取中心の用途に適する。変更の反映に遅延がある | キーと接頭辞による検索が中心 | 頻繁に更新する操作記録より、設定や表示用キャッシュに向く |

### 3.1 既存DO内のSQLite

最大の利点は、操作記録と公開処理を同じデータベースで管理できることにある。

例えば公開要求の受付時に、要求の登録、登録済みファイルの参照状態の確認、操作履歴の追加を一つのトランザクションで行える。削除時も、対象ファイルを今後の公開で使えなくする処理と、削除操作の登録をまとめて確定できる。

SQL実行のために別DBへ通信する必要はない。ただし、CLIからDOへの通信や、書込みを確定する待ち時間は発生する。

検索にはSQLの索引を使える。また、現在はCloudflareの**Durable Objects Data Studio**から、指定したDOのSQLデータを閲覧・検索できる。DOを使うと必ず独自の閲覧ツールが必要になるわけではない。通常のCLI操作には、操作IDや検索条件を受け取る専用APIを用意する。

注意すべき点は、公開・配信判定・記録検索が同じDOの処理能力を使うことである。大きな集計や履歴全件の読出しは避け、索引とページ分割で検索範囲を絞る。Data Studioの検索も実際のDOへ要求を送るため、同じ負荷と利用量が発生する。

また、DO自体に障害があると、操作記録の照会も影響を受ける。Workers Logsを併用すると、DOとは別の経路で直前の実行状況を調べられる。Data Studioは実DOへ問い合わせるため、この意味での独立した検索先にはならない。

記録用のDOを別に作る方法もあるが、その場合は公開状態と操作記録をまとめて更新できなくなる。今回は、既存DOに小さい記録を追加する方が適している。

### 3.2 D1

D1は、アプリケーションから独立したSQLデータベースとして使いやすい。HTTP API、データの入出力、スキーマ管理、クエリ分析などの機能が揃う。

複数サービスの記録を一つに集め、番組・期間・エラーなどで横断検索する場合には、DOごとに問い合わせる構成より扱いやすい。読取レプリカを使えば、読取負荷の分散もできる。

公開処理用DOと履歴検索の負荷や障害を分けられることも利点となる。

一方、現在の構成に操作記録だけを追加すると、次のように保存先が二つになる。

```text
DOのSQLite：公開要求と公開状態を更新
D1：       操作状態と履歴を更新
```

片方だけ成功する場合への対応が必要となる。D1内では複数のSQLを一括実行できるが、DOのSQLiteまで含めたトランザクションにはならない。

採用方法は二つある。

1. **操作の実行判断も含めてD1中心に組み直す**：状態を一か所に集められるが、公開処理全体の設計変更になる。
2. **DOの履歴をD1へコピーして検索に使う**：現行構成を維持できる。検索結果には反映の遅れがあり、再開・取消の実行時にはDOで最新状態を確認する。

今回追加するなら、後者が現実的である。ただし、一つのサービスの操作を検索する段階では、DOのSQL検索で足りると考える。

性能面でも、D1に移すだけで書込みが並列化されるわけではない。一つのD1データベースのクエリ処理も直列であり、書込み先はプライマリとなる。復旧判断のための読取には、最新状態を読む方法を選ぶ必要がある。

### 3.3 Workers Logs

操作ID、処理段階、エラーコード、所要時間を構造化して出力すると、DashboardのQuery Builderで条件検索・集計できる。同じ検索はWorkers Observability REST APIからも実行できるため、将来CLIからログ検索を提供することも可能である。

例えば、次のような調査に向く。

- ある操作が、どのWorkerバージョンで実行されたか。
- 検証処理の所要時間が、他の操作と比べて長いか。
- 同じエラーコードが、他のエピソードでも発生しているか。

操作状態の更新後に、同じ操作IDと履歴番号をログにも出す構成にする。DBには結果と重要な履歴を残し、ログには実行時の詳しい情報を出す。

再開判断に必要な情報をログだけに保存すると、保持期間、収集の遅れ、サンプリング、上限の影響を受ける。また、`console.log`から、操作状態とログが両方保存されたという確認は得られない。したがって、**ログ検索は調査用、DB照会は再開判断用**と役割を分ける。

長期保存の方法としてWorkers LogpushやTail Workersもある。ただし、これらはWorkers Paid向けであり、転送先の保存・検索も別途必要となる。現在のFree構成では、DOの履歴と通常のWorkers Logsを組み合わせる。

### 3.4 R2とWorkers KV

R2は、診断情報をJSONなどにまとめて長期間保存する用途に向く。保存単価が低く、既存のバケットを利用できる。操作ごとにファイルを作ることも可能だが、状態別や期間別の検索には、別の索引か多数のファイルの読出しが必要になる。

R2は保存成功後の読取が強整合であり、単に「古い値が返るから不向き」という理由ではない。今回の課題は、公開状態との一括更新と条件検索をどう実現するかにある。現在のDOにSQLを追加する方が、その実装は簡潔になる。

Workers KVは読取中心の用途では高速だが、変更が他の拠点へ反映されるまで60秒以上かかる場合がある。操作直後の再開・取消判断には、この性質が合わない。無料枠の書込み回数も、DOのSQLiteやD1より小さい。

### 3.5 その他のDB・分析サービス

外部のPostgreSQLなども、SQL検索とトランザクションを備えた候補になる。ただし、既存DOとの更新をまとめられない点はD1と同じで、外部サービスの接続・認証・料金・保守も加わる。既に外部DBを利用している場合や、Cloudflare外のデータと結合したい場合に検討する。

Cloudflare Analytics Engineは、操作件数や所要時間の集計に向く。書込み時・検索時のサンプリングがあるため、個々の操作結果を漏れなく保持する用途はSQLに任せる。

## 4. 上限とコスト

### 無料枠で比較する

現行のWorkers Freeで利用することを基本とする。以下は記録機能だけの専用枠ではなく、アカウント内の既存利用も考慮する必要がある。

| 保存先 | 主な無料枠 | 容量・保持期間など |
| --- | --- | --- |
| DOのSQLite | 読取500万行/日、書込10万行/日。別途DO要求10万回/日、実行時間13,000 GB-s/日 | 保存容量は合計5GB。1DOの容量計画はFree向けFAQの1GBを前提とする |
| D1 | 読取500万行/日、書込10万行/日 | 合計5GB、1DB 500MB、最大10DB |
| Workers Logs | 20万イベント/日 | 現行Freeの保持期間は3日 |
| R2 Standard | 保存10GB-month、書込等100万回/月、読取等1,000万回/月 | アプリで保持期間を決める |
| Workers KV | 読取10万回/日、書込・削除・一覧はそれぞれ1,000回/日 | 保存1GB |

DOとD1は、索引の更新や削除も書込み行数に含まれる。Freeの上限を超えると操作が制限されるため、記録の追加でどれだけ使用量が増えるかを確認する。D1を追加しても、既存DOの要求数や実行時間は別に残る。

Workers Logsのイベント数には、操作のログに加えて、公開配信や状態確認の実行ログも含まれる。ログの利用量は、管理操作だけでなく通常のアクセスも合わせて見積もる。

DOの容量については、公式上限ページの一般表に10GB、Free向けFAQに1GBという記載がある。この比較では、Free向けの値で容量計画を立てる。

有料プランの単価も参考にすると、DOのSQLiteとD1は、読取100万行あたり$0.001、書込100万行あたり$1で共通する。保存の追加単価はDOが$0.20/GB-month、D1が$0.75/GB-month。DOには要求と実行時間の料金もある。R2 Standardの保存は$0.015/GB-monthだが、細かい記録を多数保存するとリクエスト数と検索処理の負担も増える。

Workers Logsには、**2026-12-01からの料金体系変更**が予告されている。新しいFree枠は0.5GB/日、保持期間7日となる予定。保持期間が延びても、長期の操作記録をSQLに置くという判断は変わらない。

### 記録機能の費用は無料枠に収まるか

通常規模では収まる見込みだが、サービス全体については、既存の公開・配信処理や同じアカウントの利用量と合算して判断する。Freeでは、枠を超えた分が自動的に従量課金へ移るのではなく、該当する操作がエラーになる。

ここでの「1操作」は、素材更新や公開など一つの作業であり、HTTP要求1回やエピソード1件とは異なる。MP3本体はR2に置き、このDBには対象・検証値・処理状態などを保存する。

まず、記録機能の追加分を次の仮定で計算する。

- 1操作につき10回、状態と履歴を保存する。
- 1回の保存で、要求の登録・結果更新・状態・履歴・索引を含めて12行を書き込む。
- 1操作の状態・要求・履歴・索引に、**20KBの容量を見込む**。

容量については、現在のDDLに1操作あたり要求10件・履歴10件・音源の識別情報1件を入れ、ローカルSQLiteで確認した。1,000操作時の増分は約9.3KB/操作だった。これはCloudflare上の測定ではないため、内部管理データや記録項目の違いも考え、設計上は20KBを使う。書込み12行は仮定であり、本番の課金行数の実測値ではない。

| 操作頻度 | 記録分の書込み行数 | 記録分の年間増加量 |
| --- | --- | --- |
| 週5操作 | 実施日にまとめて約600行 | 約5.2MB |
| 5操作/日 | 約600行/日 | 約36.5MB |
| 100操作/日 | 約12,000行/日 | 約730MB |
| 1,000操作/日 | 約120,000行/日 | 約7.3GB |

例えば、準備・素材更新・公開などを合わせて1エピソード5操作と仮定すると、週1件の公開は表の「週5操作」、毎日1件なら「5操作/日」に相当する。公開日の記録分の書込みは約600行で、日次書込み枠10万行の約0.6%となる。

一方、100操作/日を長期間続けると、記録だけでも1DOの容量が課題になる。1,000操作/日は、この仮定では日次書込み枠も超える。取り込みや更新が多いサービスでは、実際の使用量を基に実行量と容量計画を調整する。

### サービス全体で確認する利用量

| 項目 | 記録以外に合算するもの | 設計上の対応 |
| --- | --- | --- |
| SQL書込み行数 | 公開キュー、コンテンツ索引、Alarm予約、記録整理 | 状態と履歴をまとめて保存し、索引の更新も計測する |
| SQL読取り行数 | 配信判定、状態照会、一覧・履歴検索 | 索引とページ分割を使い、実際に読んだ行数を確認する |
| DO要求数 | 公開アクセスに伴うDO呼出し、管理要求、状態確認、Alarm | 記録専用の余分な通信や頻繁な監視を増やさない |
| DO実行時間 | DOが実行中、または待機できずに動き続けた時間 | 許可を返した後のCLIアップロード待ちを、DO内の待機処理にしない |
| 保存容量 | 既存の公開状態、要求、コンテンツ索引、内部管理データ | 記録テーブルだけでなくDO全体とアカウント全体を確認する |

SQLカーソルの`rowsRead`と`rowsWritten`で処理ごとの行数を確認し、アカウント全体の消費量はCloudflareの利用量表示と照合する。DO実行時間はCPU時間とは別であり、要求ごとの所要時間を単純に足した値とも異なる。

**古い記録の削除は容量対策であって、日次の読書き枠を取り戻す方法ではない。** 削除自体も書込み行数に含まれる。日次枠が足りない場合は、処理量を分けることと、要求・検索・書込み回数の削減で対応する。

## 5. 推奨構成の具体案

### 保存するテーブル

既存DOのSQLiteに、次の情報を追加する。列と制約、索引の定義は[DDL案](sqlite_operation_records_schema.md#ddl)にまとめた。

| テーブル案 | 内容 |
| --- | --- |
| `operations` | 操作ID、RSS取り込みID、対象、現在状態、設定とWorkerのバージョン、開始・更新時刻 |
| `operation_requests` | 要求ID、要求元クライアント、CLIの版、受信時刻、内容のハッシュ、処理結果 |
| `operation_assets` | 操作とファイルの対応、保存先、サイズ、ハッシュ、確認済みの保存結果 |
| `operation_events` | 操作ID、履歴番号、処理段階、時刻、結果、定義済みのエラーコード |

現在状態は更新し、重要な状態変化は履歴へ追記する。操作結果と必要な履歴は完了後も保持する。記録する項目はID・状態・検証値などに絞り、本文や秘密情報はコンテンツや設定と分けて扱う。

### 保存とログ出力の順序

1. DOで現在状態と関連する公開状態を確認する。
2. 状態の更新と履歴の追加を、同じSQLトランザクションで確定する。
3. 保存が確定した操作ID・履歴番号をWorkers Logsへ出力し、CLIへ結果を返す。

ログ出力が欠けた場合も、SQLの履歴から処理結果を確認できる。CLIが応答を受け取れなかった場合は、同じ操作IDでDOへ問い合わせる。

CLIからR2へ直接アップロードする案Bでは、サーバーが把握できるのは、受け付けた操作とCLIから報告された結果である。報告前にCLIが止まった場合は、DBでも「結果不明」として残る。保存先の選択と、通信断後に何を確認できるかという問題は分けて扱う。

### 性能と検索の設計

- 操作ID、取り込みID、対象、状態、更新時刻を使って索引付きで検索する。
- 一覧をページ分割し、指定された範囲だけを読む。
- 履歴を追加するのは処理段階が変わったときとし、状態確認のたびには追加しない。
- 短いSQL処理で状態を保存し、音源の転送や検証はDBトランザクションの外で行う。

追加の待ち時間は、SQL自体だけでなく、CLIとサーバーの通信回数にも左右される。既に行う管理要求の中で状態と履歴をまとめて保存し、記録のためだけの通信を増やしすぎない設計にする。

検証では、記録を追加する前後の所要時間、DOのCPU・実行時間、要求数、SQLの読書き行数を比較する。検索負荷をかけたときの公開・配信判定への影響も確認する。

## 6. 容量管理と記録の保持

### 初期構成の方針

通常規模では、記録の自動削除を前提にする必要はない。今回のDDLは復旧や結果照会に使う小さい記録が中心なので、初版は**必要な記録の保持と、容量の表示・警告**を実装する。

詳細な調査ログはWorkers Logsへ出し、その保持期間で管理する。DBには状態確認に必要な情報を残す。この分担によって、DB内に大きなログを蓄積することを避ける。

### 何を保持し、何を整理できるか

| 記録 | 保持方針 |
| --- | --- |
| 未完了・再開可能な作業、結果不明の要求やアップロード | 再開と確認に必要な記録を保持する |
| 完了した作業と要求 | ID、内容のハッシュ、要求元、時刻、結果などの小さい記録を保持する |
| ファイルの識別情報、参照、削除結果 | 公開状態や他操作との照合に必要な情報として保持する |
| 作業の開始・現在状態・保存成功・検証・公開・取消・削除の履歴 | 結果の根拠として保持する。要求の`expected_version`が指す履歴も含む |
| 詳細な計測値、繰り返しの進捗表示などの補助情報 | 通常はWorkers Logsへ出す。将来SQLに追加する場合は、必要な記録と分けて整理可能にする |

現在の`operation_events`は重要な状態変化を記録する表なので、古いという理由だけで一括削除する対象にはしない。特に版番号1の履歴は作業を開始したクライアントの確認に使う。[既存の記録保持方針](m6_review_queue.md#承認済みの削除後記録保持2026-10-01)と合わせ、必要な小さい記録を残す。

したがって、今回の5テーブルだけで運用している場合、整理候補がほとんどないことも想定する。必要な記録自体が増えている場合は、消して空けるのではなく、記録サイズや保存構成を見直す。

### 容量の表示と警告

状態確認で`ctx.storage.sql.databaseSize`を読み、DO全体の容量と目安の上限を表示する。これを読むためだけに、新しい操作記録や定期的な監視行を追加する必要はない。アカウント全体の残容量は、Cloudflareの利用量表示で別に確認する。

初期の警告基準は次を候補とする。割合は、Free向けの容量計画に使う1GBに対する値である。

| 使用量 | 表示と対応 |
| --- | --- |
| 50%以上 | 容量の注意を表示し、増加傾向を確認する |
| 70%以上 | 記録・コンテンツ索引など、増加している項目を調べる。補助情報があれば整理を検討する |
| 85%以上 | 新しい大量取り込みの開始前に、予測増分と残容量を確認する。余裕が不足する処理は開始を見合わせる |

日次利用量も、無料枠の80%を目安に実行量の調整を検討する。全体の利用量が取得できない場合は「不明」と表示し、そのサービスの件数だけから残り枠を推測しない。

大量取り込みの見積もりは、「予定する操作数×20KB」に、既存の公開処理で増えるデータと、進行中の処理を完了させる余裕を加える。警告は上限到達前の計画に使い、進行中の操作の結果保存を優先する。

### 整理が必要になった場合

SQLに調査用の補助情報を追加した場合は、次の条件で行単位の整理を設計する。

1. 対象は、あらかじめ整理可能と定義した補助情報に限定する。新しい記録は、初期値では保持対象とする。
2. 関連する作業・要求・アップロードの結果が確定し、再開・重複防止・参照確認に使わないことを確認する。
3. 表、対象行、件数、保持する情報を事前に表示し、利用者の確認後に再検証して削除する。
4. 1回100行までを目安に分割し、読書き行数とDO実行時間を確認しながら進める。

削除後の空き領域の再利用と、表示上のDB容量の減少は分けて確認する。公式資料では、書込みに伴う内部管理データも残るとされており、行の削除量だけから容量削減を保証しない。整理は、同じDBにある公開状態や必要な管理記録を保持したまま行う。

初期段階では、容量と利用量の計測結果から、整理が有効な補助情報の有無を判断する。対象が定まった段階で、その情報の保持期間とDDLを追加する。

## 7. 選択のまとめ

| 重視すること | 適した方法 |
| --- | --- |
| 現在の公開処理と整合した再開・取消 | 既存DOのSQLiteに状態と履歴を保存する |
| エラーや所要時間を調べる | Workers Logsへ構造化ログを出す |
| 複数サービスを横断して長期間検索する | DOの記録をD1へコピーして検索する構成を検討する |
| 大量の診断情報を長期間残す | 必要な診断情報をR2へまとめて保存する |

今回は、**既存DOのSQLite＋Workers Logs**から始めるのが、整合性・性能・検索性・追加コストのバランスがよい。D1は、複数サービスの横断検索や分析用DBが必要になった時点で追加を検討する。

## 8. 開発版への反映

DO SQLiteへの記録、`databaseSize`による容量表示、50/70/85%の警告を実装した。85%以上での新規RSS取り込みは、予定操作数×20KB、コンテンツJSON量の2倍を使った概算、10MBの余裕を加えて事前確認する。アカウント全体の日次利用量は取得していないため、`unknown`と表示する。

SQLの自動整理は追加せず、必要な記録を保持する。R2の未公開素材は別の明示操作で削除する。[利用方法](../docs/sqlite_operation_recovery.md)と[ローカルでの記録量の確認](sqlite_operation_records_verification.md)を参照する。
