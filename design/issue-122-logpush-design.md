# Issue #122：Logpushによるアクセスログと統計の設計

作成日：2026-11-04。状態：共通データ・Logpush変換・日別集計、R2読取・ローカル索引、Show DOへの保存・管理APIを実装済み。Logpush設定・CLI統合とメディア直配信は実装予定。

[実装案の比較](issue-122-r2-cdn-plan.md)で推奨した、R2・CDN直配信とHTTP Requests Logpushを組み合わせる構成を具体化する。機能・料金は公式資料に基づき、対象アカウントでの検証は導入時に行う。

## 1. 目的と実装範囲

**配信経路ごとにアクセスを収集し、その後のログ保持・集計・照会を共通の処理へつなぐ。** 初版は独自ドメインの音声・カバーをHTTP Requests Logpushで記録し、個別ログを非公開R2に400日保存する。統計はCLIで再集計し、番組ごとのShow DOに保存する。

将来、`workers.dev`で配信するWorkerにも個別ログの保存を追加する。その際は収集処理を接続し、共通の集計・照会処理を利用する。現行のWorker統計は初版でも継続するため、`workers.dev`だけのサービスの動作を維持できる。

この設計で満たす条件は次のとおりである。

- 個別アクセスログを最低12か月参照できるよう、R2で400日保持する。
- CDNのキャッシュヒットを含めて収集し、メディア要求によるWorker・DOの呼び出しを減らす。
- UTCのアクセス発生日で集計し、再実行や遅着ログの反映でも同じ要求を重複計上しない。
- 取得できる指標とその定義を明示し、既存の統計も引き続き参照できるようにする。
- 400日分のデータとメディアの保存量を含め、Cloudflareの無料枠内で運用できる量を評価する。

## 2. 構成と責務

```text
リスナー ── サイトの独自ドメイン ── Worker ── Feed・HTML
         └─ メディアの独自ドメイン ── CDN ── 公開メディアR2

HTTP Requests Logpush ──────────────── 非公開ログR2
                                                │
将来のWorker側収集 ───────────────────┘
                                                ↓
                       CLI：ログ読取 → 共通アクセス記録 → 日別集計
                                                ↓
                                     Show DO：集計の保存・照会
                                                ↓
                                          CLI：統計の表示
```

管理APIは、現在と同じ`workers_dev_base_url`で受け付ける。既存の非公開R2は、音声・カバーの原本と`system/service.toml`の保存先として維持する。

| 担当 | 責務 |
| --- | --- |
| Logpush | 設定したホスト・パスのアクセスを収集し、圧縮ログをR2へ保存する |
| 非公開ログR2 | 個別ログの正本を400日保持する |
| CLIのLogpush読取処理 | Cloudflare固有のフィールドを共通アクセス記録へ変換する |
| CLIの共通集計処理 | 発生日による振り分け、重複除去、日別カウンタの計算を行う |
| Show DO | 自分のShowの集計を更新・照会する。ログ本文の処理はCLIが担当する |
| 制御DO | 現行どおりShow登録・一覧・ドメイン状態を管理する |

### 配信経路ごとの収集方法

| 配信経路 | 収集方法 | この設計での扱い |
| --- | --- | --- |
| 独自ドメイン → CDN → R2 | HTTP Requests Logpush | 初版の対象 |
| 独自ドメイン → Worker | HTTP Requests Logpush | 同じ読取・集計処理を利用できる。直配信への切替前の検証にも使える |
| `workers.dev` → Worker | Worker側で生成する個別ログ | 将来、共通アクセス記録へ接続する。初版は既存DO統計を継続 |

HTTP Requests Logpushは、アカウントで管理するゾーンのアクセスを扱う。ゾーン単位のジョブと、アカウント内の全ゾーンを扱うジョブがある。`workers.dev`は管理ゾーンに含まれない。Workers Trace Events Logpushは別のデータセットで、Workers Paidが必要になる。[C1][C2]

初版は、対象サービスのメディアを配信するゾーンごとにジョブを設定する。収集対象をそのサービスのホストに絞り、同じアカウントの別サービスから分離する。

## 3. メディア配信との接続

初版の配信構成はIssueの4aとする。音声・カバーの公開用コピーを専用R2バケットへ配置し、Feed・HTMLのURLをメディアホストへ向ける。GUID、公開日時、音声リビジョンID、非公開原本と履歴は維持する。

| 保存先 | 保存するもの | 公開範囲 |
| --- | --- | --- |
| 既存バケット | 原本、履歴の復元元、サービス設定 | 非公開 |
| 公開メディアバケット | 公開中の音声・カバーのコピー | メディア用カスタムドメインのみ |
| ログバケット | Logpushから届いた個別ログ | 非公開 |

公開メディアのキーは、現在の公開URLから先頭の`/`を除いた形式にする。音声は`podcasts/<show_id>/episodes/<episode_id>/<audio_revision_id>.mp3`、カバーは`podcasts/<show_id>/cover.jpg|png`となる。

クライアント向けの`Cache-Control`は`public, max-age=0, must-revalidate`とする。CDNの保持期間はメディアホスト限定のCache Ruleで設定し、音声は1年、カバーはFreeで設定できる最小値の2時間とする。カバー更新・非公開化では対象をパージする。CSPには設定済みのメディアオリジンを追加し、ブラウザでRange再生を確認する。

### 直配信の開始条件

ログ機能の採用と、公開操作の保証変更は別に判断する。現行はSQLiteの確定状態を基準に配信するが、直配信ではR2へのコピー・削除とSQLiteの確定に時間差が生じる。

新規公開時の先行配信、削除後の確定失敗による欠配信、ドメイン変更準備中の配信など、許容する状態について合意を得てから直配信を開始する。詳細は[実装案比較の公開操作に関する採用条件](issue-122-r2-cdn-plan.md#7-公開操作とドメイン変更の採用条件)を参照する。本書の作成やLogpushの選定は、現行の保証を変更する承認としては扱わない。

## 4. Logpushの収集設定

### 対象と出力形式

| 項目 | 設定 |
| --- | --- |
| データセット | `http_requests` |
| 対象ホスト | サービスが管理するメディアホスト。継続配信する旧ホストも含む |
| 対象パス | `/podcasts/`配下の音声とカバー |
| メソッド・応答 | GET・HEADに対する200・206・304 |
| 要求元 | `ClientRequestSource = eyeball`かつ`WorkerSubrequest = false` |
| サンプリング | `sample_rate = 1` |
| タイムスタンプ | `rfc3339` |
| 出力先 | `r2://<log_bucket>/http/<service_id>/<zone_id>/{DATE}/`と認証パラメータ |

フィルターはホスト、メソッド、応答状態、パスの接頭辞・末尾で構成する。正確なShow・Episodeとの対応付けは読取時に行う。Logpushのフィルターには約30演算子・1,000バイトの制限があるため、Episodeごとの条件は列挙せず、サービス単位で設定する。[C3]

外部リスナーの要求を収集することで、Workerの内部取得による二重計上を防ぐ。CDNヒット・ミスの両方を対象にする。[C4]

### 保存するフィールド

| フィールド | 用途 |
| --- | --- |
| `EdgeStartTimestamp` | アクセス日時 |
| `RayID` | 同じ要求の重複除去 |
| `ClientRequestHost`、`ClientRequestPath` | サービス・Show・素材の特定 |
| `ClientRequestMethod`、`EdgeResponseStatus` | 応答の分類 |
| `EdgeResponseBodyBytes` | エッジから返した本文バイト数 |
| `CacheCacheStatus` | キャッシュ別の内訳 |
| `ClientRequestSource`、`WorkerSubrequest` | 集計対象の照合 |

IP、Cookie、User-Agent原文、Referer、クエリ文字列、任意のヘッダーは保存対象外とする。`ClientRequestPath`を使うことで、クエリ文字列を含むURIの保存を避ける。[C5]

初版は標準フィールドで構成する。Bot判定用の変換や応答ヘッダーの追加収集は、必要な指標と無料枠への影響を別途確認して判断する。

## 5. 共通アクセス記録と統計の定義

### 共通化するデータ

収集元固有の形式は、CLIの読取処理で次のアクセス記録へ変換する。R2には収集元のログを正本として保存し、CLIでは変換した記録を1行ずつ共通の集計関数へ渡す。

| 項目 | 意味 |
| --- | --- |
| `source_id` | 収集元と配信ホストを識別する値 |
| `event_id` | 収集元での要求ID。Logpushでは`RayID` |
| `occurred_at_ms` | アクセス日時。Logpushでは`EdgeStartTimestamp`をミリ秒へ変換 |
| `host`、`resource_path` | 配信ホストと正規の公開パス |
| `show_id`、`resource_kind` | 対象Showと`audio`・`cover`の区別 |
| `episode_id`、`audio_revision_id` | 音声の対象。カバーでは`null` |
| `method`、`status` | GET・HEADと200・206・304 |
| `response_bytes` | 収集元が計測した本文サイズ。意味は収集元の定義に従う |
| `cache_status` | キャッシュの状態。将来の収集元で取得できない場合は`null` |

Logpushの`source_id`は`http_logpush:<zone_id>:<hostname>`とする。ジョブを作り直しても同じ値を使うため、同じ要求を再配送した場合も重複除去できる。

収集元には、ホスト、収集開始日時、指標の定義、バイト数の計測方法を対応付ける。初版の計測方法は`edge_body`である。将来Worker側で`Content-Length`を記録する場合は、それを別の計測方法として追加する。

### 日別指標

集計単位は**収集元 × Show × UTC日付 × 公開素材パス**とする。音声パスにはEpisode IDと音声リビジョンIDが含まれるため、Episode別・リビジョン別にも集計できる。カバーはShow単位の統計になる。

| 指標 | 初版の定義 |
| --- | --- |
| GET 200件数 | GETに対する200。Botを含む |
| GET 206件数 | GETに対する206。Botを含む |
| HEAD件数 | 対象ステータスのHEAD |
| 304件数 | GETに対する304。HEADはHEAD件数へ分類 |
| 応答バイト数 | GET 200・206の`EdgeResponseBodyBytes`の合計 |
| キャッシュ内訳 | 対象応答を`CacheCacheStatus`別に集計 |

HEAD・304の本文バイト数は0として扱う。取得開始、微小Range、既知Bot除外は初版の提供指標から外し、未対応として表示する。標準ログには206の開始位置がなく、要求のRangeヘッダーもLogpushのカスタム収集に対応していないためである。[C6]

新しい統計形式は`access-daily-v1`とする。既存の`episode-daily-v1`はBot除外や宣言`Content-Length`に基づくため、別の定義として保持する。表示では収集元・計測方法・期間を添え、意味が同じ指標を集計する。

共通データでは、日別値の`format`に`access-daily-v1`を入れる。カウンタ名は`get_200_requests`、`get_206_requests`、`head_requests`、`not_modified_requests`、`response_bytes`とする。`cache_status_requests`はキャッシュ状態をキーにした件数の内訳で、合計は対象応答の総数と一致する。将来の収集元がキャッシュ状態を取得できない場合は、`unavailable`に分類する。これはCloudflareの`unknown`とは別の区分である。

### 将来のWorker側収集との接続

Worker側では、公開応答の確定後にアクセス日時と要求IDを付けた個別記録を生成し、R2へ保存する収集処理を追加する。そのログを上記のアクセス記録へ変換すれば、日別集計、Show DOへの保存、照会・表示を利用できる。

1つの配信ホスト・期間には1つの収集方法を選ぶ。独自ドメインのWorkerをLogpushで収集する場合は、それとWorker側ログを合算して同じ応答を二重計上しない。既存のDO統計も別の収集元として表示する。

初版はLogpush読取関数から共通集計関数を直接呼ぶ構成とする。Worker側の収集方式とまとめ書きの方法は、追加する時点で選ぶ。これにより、共通化の境界を保ちながら、初版を小さい構成で実装できる。

## 6. ログの400日保持と読み出し

### R2での保持

Logpushはgzip圧縮されたNDJSON（1行1件のJSON）をログバケットへ保存する。[C7] `http/<service_id>/`を対象に、オブジェクト作成から400日後に削除するlifecycleルールを設定する。保存クラスはStandardとする。

400日保持は、Episodeの非公開化、ドメイン解除、DO側の集計整理とは独立して続ける。公開メディアの削除対象とログバケットを分離し、12か月分以上を保持できる容量を確保する。ログバケットには公開ドメインを設定せず、`r2.dev`も無効にする。

### 発生日とファイルの保存先

`{DATE}`はログファイルを整理するフォルダであり、集計日を決める情報には使わない。集計日は必ず各記録の`EdgeStartTimestamp`から求める。

CLIは、保持中のログファイルをページ単位で一覧する。日付フォルダだけで取得対象を限定すると、配送が遅れた記録を見落とすおそれがあるため、ファイル内のアクセス日時で対象日を判定する。

実装済みの読取処理は、Cloudflare RESTのList Objectsを使い、`http/<service_id>/<zone_id>/`配下を1ページ最大1,000件で列挙する。続きのカーソルをたどって一覧を取得した後、そのキー・ETag（オブジェクト内容の照合に使う識別値）・圧縮サイズの集合を今回の入力にする。以後に追加されたファイルは次回の一覧で見つける。[C15]

Get Objectでは、応答のETagを一覧の値と照合し、圧縮された本文の読取サイズも確認する。gzipを展開しながら、UTF-8のNDJSONを1行ずつ解析する。BunのHTTP自動展開を無効にすることで、R2の`Content-Encoding: gzip`による二重展開を防ぐ。[C16]

### 読取用のファイル索引

400日分を毎回ダウンロードする処理を避けるため、CLIは`.castloop/access-log-files.sqlite`にファイルの索引を保存する。単一バイナリに含まれるSQLiteを使い、外部ツールの導入は不要とする。

索引には、アカウント・バケット・オブジェクトキー・ETagと、ファイル全体のアクセス日時の最小値・最大値を保存する。日時範囲はShowで絞り込む前に求めるため、同じファイルを別Showの照会にも使える。索引は再作成可能なデータで、ログや集計の正本はR2・Show DOにある。

1. R2の一覧と索引を照合し、新しいファイルを読み出す。
2. 読み出しと解析に成功したファイルの日時範囲を、索引へ一括保存する。
3. 指定日と日時範囲が重なるファイルを読み出し、アクセス日時で絞り込む。
4. 新しいファイルに過去日の記録があれば、その日を再集計の対象として知らせる。指定範囲内の遅着分は今回の計算に含める。

索引の有無によって集計結果は変わらない。別端末や索引の再作成時は初回読取量が増える。通常の再集計では、新規ファイルと対象日に関係するファイルを読む。索引の書き込みは1ファイル分を単位に確定し、途中終了後も同じ一覧から再実行できる。

索引は派生データとしてワークスペースバックアップの対象から分離する。ローカルでは既存の`.castloop/`と同じアクセス制限を適用し、APIキーなどの認証情報は保存対象外とする。

索引の日時範囲は、ホスト・Show・素材で絞る前のファイル全体から求める。空のファイルは最小・最大日時をともに`null`として記録する。正常に読み終えたファイルごとに1行を確定するため、後続のファイルで失敗しても、先に保存した索引は再利用できる。失敗したファイルは次回も読み直す。

読取処理は、対象ShowとUTC期間に合う共通アクセス記録を順に渡し、完了時に対象期間と重なるファイル一覧と、新規ファイルにあった期間外の日付を返す。期間外の日付はファイル全体の記録に基づくため、別Showのアクセスも含む。索引を作り直した場合は、同じ日付が再び現れることがある。1回の指定期間は1〜366日とし、400日分は期間を分けて読み出す。

アクセス記録は読取中に渡される。集計の保存を行う呼出側は、対象日の全ファイルの解析完了を待ってから反映する。これにより、後半の解析失敗による途中までの値をShow DOに保存せずに済む。

## 7. 再集計とShow DOへの反映

### 集計の手順

1. CLIがサービス設定とShowの識別情報を照合し、収集元・承認済み素材・現在の集計版を取得する。
2. R2の入力ファイルを一覧し、今回使うキーとETagの集合を固定する。ファイルの解析に失敗した場合は、その日について保存済みの集計を維持してエラーを返す。
3. ログを共通アクセス記録へ変換し、対象ホスト・公開パス・Show・承認済み音声参照と照合する。過去のアクセスも扱うため、現在の公開状態ではなく保存済み素材参照を使う。
4. UTC日付ごとに`source_id`と`event_id`の組で重複を除き、素材別のカウンタを再計算する。
5. 収集対象の期間について、承認済み素材ごとの集計をShow DOへ送り、保存済み値を置き換える。記録がなかった素材も観測0件として反映し、集計済みかどうかを区別できるようにする。

同じログを再読込しても、遅着ファイルを加えて再集計しても、この手順を使う。既存の`stats.record()`は記録時刻による加算処理なので、新しい集計の反映とは分ける。

### 保存単位と同時更新

**1回の更新単位は、収集元・UTC日付・素材パスの1組**とする。要求サイズを小さく保ち、各更新を1回のSQLiteトランザクションで確定する。

更新には現在の集計版`expected_version`を含める。未作成の行は期待版を0とし、初回保存時に1へ進める。同じ入力・同じ結果が保存済みなら`unchanged`を返す。内容が変わる場合は期待版を照合してから置き換え、版を進める。これにより、別の再集計結果を古い読取結果で上書きすることを防ぐ。

収集元の情報にも版を持たせ、`expected_source_version`で照合する。日別値の版だけでは、別の日を同時に再集計した際に、古い収集元情報で新しい中断情報を上書きできてしまうためである。収集元の登録・更新と日別値の更新は同じトランザクションで確定する。収集開始時刻は登録後も維持し、終了時刻・中断・最終配送時刻を更新できる。

同じ入力ハッシュ・カウンタ・入力日時範囲を再確認した場合、日別値の版を維持したまま`read_at_ms`を新しい読取時刻へ進める。たとえば、アクセスが0件のまま翌日に再確認した場合も、前日の読取完了を表示できる。古い読取時刻の再送で、この時刻を戻すことはない。`changed`は収集元情報または日別内容の変更を表し、読取時刻だけの更新は`unchanged`となる。

CLIは対象日の入力ファイルをすべて正常に読んでから、その日の更新を開始する。日付範囲全体の更新は素材・日付ごとに進むため、照会では各行の反映日時を返す。途中終了時は現在の集計を照会し、同じ範囲を再計算して再適用する。

### 保存する表

Show DOは次の3表を使い、既存のWorker統計も引き続き保持する。

| 表 | 主な内容 |
| --- | --- |
| `publication_access_stats_schema` | 新しい統計表の形式版1を保存。既存の公開・内容・Worker統計の形式版は維持 |
| `publication_access_stats_sources` | `source_id`を主キーに、収集方法、ゾーン、ホスト、収集開始・終了日時、中断情報、最終配送時刻、指標定義、計測方法をJSONで保存。情報の版と更新時刻を併記 |
| `publication_access_daily_stats` | `(source_id, date_utc, resource_path)`を主キーに、素材種別、Episode・音声リビジョン、カウンタJSON、版、入力ハッシュ、入力日時範囲、読取・反映日時を保存 |

カウンタは0以上の整数とし、素材の識別は既存の公開パス解析と素材参照を利用する。入力のハッシュには、対象のファイル集合、収集元、日付、素材、指標定義、集計結果を対応付ける。

日別値は400日保持し、期限切れの行を更新時に整理する。初版の期間合計は保持中の日別値から計算する。既存Worker統計の通算値・保持設定は、引き続き既存の仕組みで管理する。

保持範囲は当日を含む400のUTC日付とする。取込時に期限切れの行を最大200行ずつ削除し、整理待ちの行も照会・期間合計から外す。日別照会用と期限整理用のインデックスを使い、それぞれ必要な範囲を読み出す。無料枠の評価では、このインデックスへの書き込みも含める。

### 計測範囲の表示

Logpushは配送失敗などにより欠損が生じる場合がある。CLIがジョブの構成・状態確認で得た収集開始・終了や中断情報を保存し、最終受信・今回読めた入力範囲とともに表示する。中断情報は日時と許可した理由コードで記録する。400日保持の対象はR2に到着したログである。[C8]

対象日にログがなくても、正常に走査した範囲の観測件数として0を返すことはできる。その場合も、収集方法はbest effort（配送による欠損があり得る方式）であると表示する。収集開始・終了で日全体を計測できない日や、確認済みの中断がある日は部分的な値として扱う。未集計・解析失敗・保持期限後は、0件とは区別する。

管理APIの日別照会では、各日を次の区分で返す。

| 区分 | 意味 |
| --- | --- |
| `observed` | その日の読取結果を保存済みで、収集開始・終了、中断、読取時刻による部分計測の条件に当たらない。配送方式は引き続きbest effort |
| `partial` | 収集開始・終了が日中、中断と重なる、またはその日の終了前に読み出した値 |
| `unmeasured` | 保存済みの集計がない。日別値は`null` |
| `pruned` | 400日の保持範囲より前。日別値は`null` |

保存済みの0件にはカウンタを返す。期間全体に保存済みの値がなければ期間合計も`null`とし、0件と区別する。解析失敗時は取込を行わず、呼出側のエラーと既存値の読取日時で状況を確認する。

## 8. 管理APIとCLI

### 管理API

新しい集計の経路は`/admin/sqlite-access-stats/`とする。現在と同じ管理オリジン、`X-Castloop-Key`、`X-Castloop-Show-Id`を使い、サービスID・設定ハッシュ・Showを照合する。応答は`no-store`とする。

| 経路 | 用途 |
| --- | --- |
| `GET sources` | 現在・過去の収集元と指標定義を照会 |
| `GET resources` | 対象Showの承認済み音声リビジョンとカバーの公開パスを取得。非公開化済み音声も含む |
| `GET daily` | 収集元・期間・素材を指定して日別値と集計版を取得 |
| `POST daily` | 1つの素材・日付の集計を期待版付きで置換 |

`POST daily`には、サービス識別とShow ID、`source`（収集元情報）、`expected_source_version`、`daily`（共通の日別値）、`expected_version`、`input_sha256`、`read_at_ms`、`input_min_at_ms`、`input_max_at_ms`を送る。入力日時の最小・最大値は、その素材で観測した発生時刻を表し、観測0件ではともに`null`とする。Show DOは対象の素材参照と収集元を照合し、トランザクション内で版を確認する。

設定・対象・版の不一致は409、入力不正は400、認証失敗は401、未準備・保存完了を確認できない場合は503とする。保存確認の応答だけが失われた場合も、同じ要求を再適用して日別件数を増やさずに結果を確認できる。

収集元は初回の集計取込時に登録する。CLIは保存済みのLogpush設定からホスト・ゾーン・収集開始などを取得し、Show DOは現在のサービス設定または保存したドメイン変更情報と照合する。既存の登録情報はドメイン変更後も保持するため、旧ホストのログも取り込める。

現行のサービス設定との照合には公開ホストを使う。現行設定はゾーンIDを持たないため、ゾーンは管理者が保存したLogpush設定から受け取る。過去のホストを初めて取り込む場合は、完了済みのドメイン変更記録のホスト・ゾーンと照合する。登録済みの収集元は、旧ホストでの配信終了後も照会・再集計に使える。

一覧はページ分割し、要求・応答を既存管理APIのサイズ上限内に収める。期間は最大366日を単位とし、より長い保持ログの読取は期間を分ける。カーソルにはサービス、設定、Show、収集元、検索条件を対応付ける。

GETには`service_id`・`service_config_sha256`をクエリで指定し、Showはヘッダーで選ぶ。`GET daily`ではさらに`source_id`・`resource_path`・`from`・`to`を必須とする。1素材ずつ照会し、各ページに指定期間全体の合計と計測範囲を返す。

要求は12 KiB、応答は16 KiBを上限とする。収集元・素材は最大20件、日別値は最大31日で、収集元の中断情報などが大きい場合は、応答の実際のバイト数に合わせて件数を減らす。カーソルは経路と保持境界にも対応付け、日別照会では収集元情報の版にも結び付ける。途中で対応する設定や収集元情報が変わった場合は409を返す。

### CLIの操作

以下は追加するコマンド名の案である。Show選択と`--from`・`--to`のUTC日付指定は、既存の`stats`に合わせる。

| コマンド | 動作 |
| --- | --- |
| `stats refresh` | ログを読み出して指定期間を再集計し、Show DOへ反映する。新たに見つかった範囲外の遅着日も結果に示す |
| `stats access` | Show DOに保存された新形式の日別値・期間合計・反映日時を表示する |
| `stats logs` | R2から対象Show・期間の個別ログを読み、共通アクセス記録をNDJSONで出力する |

`stats access`は保存済みの値を表示する操作、`stats refresh`は値を更新する操作として分ける。個別ログの保存はLogpushが継続するため、管理端末の起動頻度にかかわらず400日保持できる。

既存の`stats`と`stats retention`はWorker統計用として維持する。新形式の表示・JSON出力には収集元と指標定義を含める。`stats logs`で書き出したファイルは管理者が保管するアクセス記録となり、通常の診断出力から分離する。

## 9. 設定・認証・ドメイン変更

### サービス設定

追加する設定は、メディア基底URL、公開メディアバケット名、メディアのゾーンID、非公開ログバケット名とする。TOMLのキー名はそれぞれ`media_base_url`、`media_bucket_name`、`media_zone_id`、`access_log_bucket_name`を案とする。

初版では、直配信を利用するサービスに4項目を一式で設定する。現在のWorker配信の設定は引き続き利用する。`public_base_url`はFeed・HTML、`workers_dev_base_url`は管理APIに使う。追加項目も正規化と`service_config_sha256`の計算に含める。

現行の`schema_version = 2`、`storage_layout = "show-v1"`、公開プロトコルは維持する。Workerの既存バインディング・DOクラス名・Compatibility Dateも維持し、公開メディア用のR2 bindingと限定したパージ用secretを追加する。ログ本文はCLIが読むため、集計のためのログR2 bindingは初版のWorkerには不要である。

### Logpushの設定と秘密情報

CLIは`CLOUDFLARE_ACCOUNT_ID`と`CLOUDFLARE_API_TOKEN`を使ってRESTで管理する。Logpushジョブにはゾーンの`Logs Write`、ログ保存先にはR2の権限が必要になる。直接R2へ保存する際のaccess key / secretは、CLIがAPIでログバケットに限定したトークンを作成し、その応答から生成して設定する。[C7][C9]

このトークンはLogpushのR2接続用である。CLIによるバケット管理・ログ読出しは従来のCloudflare RESTを使う。R2のバケット単位のObject Read & Write権限はS3互換API用で、REST管理の権限とは区別する。[C9]

トークン作成を含む追加権限は、導入時に明示承認を得る。認証値は設定時にメモリ内でのみ扱う。管理記録に残すのは、ジョブID・トークンID・保存先・収集条件・収集開始日時などの安全な項目とする。秘密情報を含む`destination_conf`とAPI応答全体は記録対象から外す。

再実行では保存済みのサービス・リソースIDとAPIの現在状態を照合する。同じ設定なら既存の管理対象を利用し、更新前後の設定を保全する。変更系APIの結果が不明な場合は、状態を確認してから同じ承認済み入力を再適用する。

### ドメイン変更

- 変更前後の設定に、メディアホスト、公開用バケット、Logpushの収集ホストを含める。
- 旧ホストで配信を続ける間は、そのホストも収集・非公開化・パージの対象にする。
- 新旧ホストを別の`source_id`として保持し、過去ログを元のホストへ対応付ける。ドメイン解除後も、保持期間内の旧ログを再集計できる識別情報を残す。
- 配信を終了したホストは収集を終了し、到着済みログは400日の保持方針で管理する。
- `workers.dev`へ戻すときは非公開原本から現行配信を再開する。Worker側ログを追加するまでは、以降のアクセスを既存DO統計で確認する。

公開コピーの作成・削除とパージは、即時公開と予約Alarmの両方から呼ばれるShow DOの公開処理へ接続する。原本、公開済み音声の履歴、ログの保持はそれぞれ独立して扱う。

## 10. 無料枠と利用量

無料枠はアカウント全体で共有する。保存済みメディアや他サービスの使用量を差し引いて評価する。

| 対象 | 評価する枠 |
| --- | --- |
| Logpush → R2 | 非圧縮の転送量25GB/月。超過は$0.03/GB。[C10] |
| R2 Standard | 保存10GB-month、Class A 100万回/月、Class B 1,000万回/月。[C11] |
| SQLite DO | 保存5GB、読取500万行/日、書込10万行/日。要求10万回/日・実行時間13,000 GB-s/日も確認する。[C12] |
| Workers | 10万要求/日。Feed・HTML・管理要求を含む。直配信のメディア要求は対象外。[C13] |

1日の対象要求数を`N`、非圧縮ログ1件のサイズを`b`バイト、圧縮後の比率を`c`とすると、転送量は概ね`N × 30 × b`、400日分のログ保存量は`N × 400 × b × c`となる。

例として`b = 600バイト、c = 0.2`なら、10万要求/日で転送は月約1.8GB、400日ログは約4.8GBになる。残り約5.2GBに原本・履歴・公開コピーなどが収まるかを確認する。これらは未測定の仮定であり、採用時には実際のフィールドと圧縮率で計算する。

Logpushのファイル数は配信量によって変わる。無料枠の確認には、ファイル保存・一覧のClass A、ログとメディア読出しのClass B、素材・日付ごとの管理要求とDO更新を含める。DOの書き込みには期限切れ行の整理も含まれる。CLIのファイル索引は読取量を抑えるために使うが、初回構築や別端末からの実行では全ログの読取量を見込む。

Cloudflare RESTにはアカウントあたり1,200要求/5分の制限がある。[C14] 代表的なログ量で索引構築・日次更新・12か月分の照会にかかる時間と操作数を確認する。400日保持を固定条件とし、使用可能な容量・操作枠から対応できるアクセス量を求める。

実装は次の順で進める。

1. **共通データと集計を作る（実装済み）。** Logpushの記録を入力とし、日時・指標・重複除去・再計算をローカルで検証する。
2. **ログの保存・読取・照会をつなぐ。** R2、CLI、Show DOへの置換、管理APIと表示を実装する。独自ドメインのWorker配信でも収集を検証できる。
3. **直配信へ接続する。** 公開操作の採用条件に合意したうえで、メディアURL、コピー、パージ、ドメイン変更を実装する。
4. **将来のWorker側収集を追加する。** 個別ログの生成・保存を実装し、共通アクセス記録へ接続する。この段階は別の実装範囲とする。

初版の成果物は1〜3で、Worker側の個別ログ保存は将来の追加となる。

工程2は、次の単位に分けて実装する。

- **2a：R2読取・ファイル索引（実装済み）。** gzip・NDJSONを読み、期間・Showで抽出する。索引を再利用し、遅着ログを発生日へ対応付ける。

- **2c：Logpush設定・CLI統合。** 非公開ログバケットと400日の保持ルール、Logpushジョブの管理を実装し、読取・集計・保存をCLIコマンドへ接続する。

工程2aのテストは、[R2・gzip・NDJSON](../packages/cli/src/http-logpush-r2.test.ts)、[索引・保護・バックアップ除外](../packages/cli/src/access-log-file-index.test.ts)、[Show・期間・遅着・索引再作成](../packages/cli/src/http-logpush-read.test.ts)にある。12か月分の読取はローカルのログデータで検証し、実環境の保持設定と容量評価は導入時に行う。

工程2bは、[共有スキーマ](../packages/shared/src/sqlite-access-stats.test.ts)、[置換・保持・計測範囲](../src/sqlite-access-stats.test.ts)、[管理HTTP・Show分離](../src/sqlite-access-stats-http.test.ts)で検証する。Workerを埋め込むCLIのビルドと単一バイナリのスモーク試験も行う。

### 承認を得て確認すること

試験の対象・操作範囲・確認者を指定して、[非公開実機試験の手順](security.md#非公開の実機試験)に従う。新しいメディアホストはCloudflare Accessで指定確認者だけに許可する。原本・ログは非公開に保ち、`r2.dev`・別ホスト・preview URLを含む迂回経路を閉じる。

サンプルを置く前と、配備・公開・キャッシュ利用後に、匿名GET・HEAD・条件付き要求・Rangeの拒否を確認する。そのうえで次を検証する。

- Freeゾーンで必要なデータセット・フィールド・権限とR2への保存を利用できること。
- CDNのHIT・MISS・206・304が記録され、内部サブリクエストと区別されること。
- メディア直配信でWorker・DO呼び出しが減り、Feed・HTMLは既存経路を使うこと。
- 非公開化・カバー更新・ドメイン変更が、合意した公開仕様とパージ方針に従うこと。
- 実際のログサイズ、圧縮率、ファイル数、R2・DO操作数から、400日後の保存量と費用を評価できること。

設計上の採用条件は、公開操作の許容範囲への合意と、対象アカウントでの機能・無料枠への適合確認である。これらは実装・導入時に確認する項目として残し、検証結果と条件を記録する。
