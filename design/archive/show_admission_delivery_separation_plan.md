# Issue #66: 公開受付の停止とリスナーへの配信停止を分ける

作成日: 2026-10-24。改訂日: 2026-10-25。

**全項目を管理者承認済み。変更番号とサーバーへの操作結果保存を両方追加する案を採用し、コードを実装した。実環境への配備・公開・再開は行っていない。**

- 対象: [Issue #66](https://github.com/simosako/castloop-v2/issues/66)
- 実装前の調査基準: `627c887f633142e6a3fed451fee4a767f4492004`（package version `0.7.3`）。Issue本文が参照する版より新しく、独自ドメイン対応とIssue #65のCLI日時設定を含む。
- 以下は未リリース開発版の採用仕様。配布済み版や既存環境へ自動適用されるものではない。操作は[利用ガイド](show_availability.md)を参照する。

## 1. 今回作るもの・作らないもの

**公開内容の変更を一時的に受け付けなくても、既に公開しているPodcastはリスナーが取得できるようにする。** これが前稿の「A」であり、今回の対応範囲として合意した。

一方、緊急時には従来どおり、変更の受付とリスナーへの配信を両方停止できるようにする。

| 今回作るもの | 今回作らないもの |
| --- | --- |
| リスナーへの配信を続けながら、新しい公開依頼の受付を止める操作 | Workerプログラムの更新中も配信し続ける機能（前稿の「B」） |
| 受付と配信の両方を停止した後、配信だけを再開する操作 | 独自ドメインの変更中も配信し続ける機能 |
| 何を停止しているかの表示、再開条件、操作結果の記録 | 異常停止した公開処理の再実行、強制解除、旧環境のデータ移行 |

### なぜ作る価値があるか

現在の`show-pause`は、管理者からの新しい公開依頼だけでなく、リスナーによるFeed・カバー画像・音声の取得も止める。しかし、管理者が新しい変更を止めたいだけなら、既に公開済みの内容まで取得不能にする必要はない。

例えばWorker更新の準備では、次の手順に変えられる。

1. 新しい公開依頼の受付だけを止める。リスナーへの配信は続ける。
2. 既に受け付けた公開処理が終わるのを待つ。
3. Worker更新を始める直前に、配信も止める。
4. 従来の手順でWorkerを更新し、動作確認する。
5. 配信だけ、または受付と配信の両方を、管理者が明示的に再開する。

**手順2の待ち時間を、配信停止の時間から外せる。手順4の更新中は引き続き配信を止める。** 今回の変更を「無停止でWorkerを更新できる」とは説明しない。

通常のShow/Episode編集では、Issue #50によって更新前の公開内容を配信する仕組みが既にある。本件はそれを作り直すものではない。また、停止時間が何秒短くなるかという実測値はない。

## 2. 本書で使う言葉

| 言葉 | この設計での意味 |
| --- | --- |
| Show | 1つのPodcast番組。停止・再開の対象は番組ごとに指定する |
| 公開依頼 | 管理者がサーバーへ送る、Show/Episodeの公開・更新・非公開化・復元の依頼 |
| 公開処理（job） | サーバーが受け付けた公開依頼を実行する処理。受付順に実行する |
| 公開済みの内容 | 保存・検証・必要なキャッシュ削除が終わり、サーバーが公開対象として記録したFeed・画像・音声。アップロードしただけの素材は含めない |
| 既受付処理の終了（`drained`） | 実行待ち・実行中・異常停止中の公開処理がすべてなくなった状態。すべてのアップロードが終わったことを意味しない |
| サーバーの動作確認済み（`ready`） | 実行中のWorkerプログラムと保存された設定が一致し、データベース・処理の起動機能・ファイル保存先・キャッシュの確認に成功している状態。公開依頼を受け付けているかどうかとは別 |
| 保守中 | Worker更新やドメイン変更の準備を開始し、途中で受付を再開できないようサーバーに記録している状態 |

内部の識別子や保存項目は§9にまとめる。運用上の判断は、まず§3〜§6を読めばできる構成とする。

## 3. 番組の状態を3つに分ける

### 3.1 既存の`show-pause`は何を止めるのか

`show-pause`の動作は変更しない。

- 管理者からの**新しい公開依頼を受け付けない**。
- リスナーへの**Feed・カバー画像・音声の配信を止める**。
- 既に受け付けた公開処理は取り消さず、終了まで実行する。

ここでいう停止は、受付と配信を両方止めることであり、既受付の公開処理を強制終了することではない。

### 3.2 追加する状態

| 保存する値 | 管理者向けの表示 | 新しい公開依頼 | リスナーへの配信 |
| --- | --- | --- | --- |
| `open` | 受付中・配信有効 | 受け付ける | 公開済みの内容を配信する |
| `admission_paused` | 受付停止・配信有効 | 受け付けない | 公開済みの内容を配信する |
| `paused` | 受付停止・配信停止 | 受け付けない | 配信しない |

真ん中の`admission_paused`だけが新しい状態である。

「配信有効」は、どんな状況でもファイルを返すという意味ではない。非公開化したEpisodeは返さず、サーバーの動作確認に失敗した場合や保守中も配信しない。詳しくは§7に示す。

新しいShowの登録直後は、従来どおり`paused`とする。登録だけで公開や配信を始めない。

### 3.3 他の状態の持ち方との比較

| 案 | メリット | デメリット |
| --- | --- | --- |
| 現状の2状態のまま | 変更が不要 | 受付だけを止めることができない |
| 受付の可否と配信の可否を、別々の値として保存する | それぞれを自由に変更できる | 独立に変更すると「公開依頼は受け付けるが配信は止める」という4つ目の組合せもできる。これを禁止するなら、別途組合せの検査が必要になる |
| **上表の3状態のどれか1つを保存する（採用）** | 必要な組合せだけを扱える。既存の`paused`を見れば、今までどおり両方停止していると判断できる | 状態を読むプログラムを、新しい3状態に対応させる必要がある |

## 4. 停止・再開の操作と、その条件

### 4.1 採用するコマンド

対象のShowと操作IDを指定する。操作IDはUUID形式の一意な番号で、後からどの操作だったか確認するために使う。

| コマンド | 何が変わるか | 何が変わらないか |
| --- | --- | --- |
| 新規: `show-admission-pause SHOW OPERATION_UUID` | `open`から`admission_paused`へ。受付だけを止める | 配信は止めない。既に`paused`なら、そのまま両方停止を維持する |
| 既存: `show-pause SHOW OPERATION_UUID` | `open`または`admission_paused`から`paused`へ。受付と配信を両方止める | 受け付け済みの公開処理は取り消さない |
| 新規: `show-delivery-resume SHOW OPERATION_UUID` | `paused`から`admission_paused`へ。配信だけを再開する | 公開依頼の受付は再開しない |
| 既存: `show-resume SHOW NEW_WINDOW_UUID` | `paused`または`admission_paused`から`open`へ。受付と配信を両方有効にする | 非公開のShow/Episodeを公開状態へ変更することはない |

停止操作は、既受付処理が終わるのを待たずに返る。停止後の処理状況は`show-status`で確認する。

同じ状態への停止操作は、その状態を維持する。配信だけの再開を`admission_paused`へ行った場合も状態は変えないが、`open`へ行った場合は不要な操作として拒否する。既に`open`のとき、新しい受付期間IDへの切替は認めない。

**配信を停止中に「受付だけ停止」を実行しても、配信が再開されることはない。** 配信を再開するには、再開用のコマンドを明示的に実行する。

### 4.2 なぜ新しいコマンドを2つ追加するのか

メリットは、コマンド名から「受付を止める」「配信を戻す」を区別でき、既存`show-pause`の利用手順を変えずに済むことである。デメリットは、管理者が覚えるコマンドと、実装・試験する操作が増えることである。

代案として、既存コマンドに`--keep-delivery`などのオプションを追加する方法もある。この方法ならコマンド名は増えないが、履歴や操作手順を読む際に、オプションを見落とすと停止範囲を誤解しやすい。今回は、目的別にコマンドを分ける案を採用する。

### 4.3 配信だけの再開にも、既受付処理の終了を求める

次の2つの条件を**両方満たすまで再開を認めない**方針で合意した。この2つは理由が異なる。

| 条件 | 求める理由 | 不便になる点 |
| --- | --- | --- |
| 既受付処理が終了していること（`drained`） | 公開・非公開化・復元の途中や異常停止中に、配信を再開してよいかという追加判断を避けられる | 安全に旧内容を読める公開処理でも、終了まで配信を戻せない。異常停止中の処理が残ると、そのままでは配信を再開できない |
| サーバーの動作確認が成功していること（`ready`） | 別のプログラムや設定、未確認の保存先・キャッシュから配信することを防ぐ | Worker更新後の確認などが終わるまで待つ必要がある |

どちらの場合も、保守中の再開は認めない。

比較したのは「配信再開前に既受付処理の終了を待つか」である。サーバーの動作確認は、どちらの案でも既存の安全条件として省略しない。

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| **既受付処理がすべて終わってから配信を再開する（採用）** | 条件が単純で、既存の受付再開条件とも揃う。実装・試験する場合分けが少ない | 公開処理が長い場合は再開が遅れる。異常停止が解消されない場合は再開できない |
| 公開処理が残っていても、更新前の公開内容を安全に読める場合は配信を再開する | 配信を早く戻せる場合がある | 安全に読める処理か、初回公開・非公開化・復元の途中ではないか、異常停止の原因が何かを再開時にも区別する必要がある。条件を満たさない場合は結局再開できない |

例えば「Episode更新中に配信を止めたが、更新終了前に配信だけ戻したい」という運用では、後者に利点がある。ただし今回は、前者の待ち時間を許容する方針で合意した。

受付だけを停止し、配信を一度も止めなかった場合には、この再開待ちは発生しない。既存の配信条件を満たす間は、処理中でも配信を続ける。

### 4.4 停止と再開で共通して守ること

- 再開しても、非公開化した番組やEpisodeを勝手に公開しない。
- 保守の終了や時間経過を理由に、自動で再開しない。
- 配信だけの再開では、受付期間IDを変更しない。受付期間IDについては§6.3で説明する。
- 認証と番組・プログラム・設定の照合が可能な範囲で、`show-pause`は保守中にも受け付けられるようにする。ただし、保守作業の解除や未確認のプログラムでの再開は認めない。
- 保守中に管理者が配信停止を記録した場合、その後に保守が完了しても配信停止を取り消さない。

## 5. 受付停止中の編集・アップロードはどうなるか

### 5.1 公開とアップロードは別の操作

現在も、音声や画像をアップロードしただけでは公開されない。例えば`update-episode-audio`は音声をサーバーへ保存し、`publish-episode`が明示的な公開依頼になる。

ただし現在の実装では、`show-pause`中は公開依頼だけでなく、新しいアップロードや、その素材を公開準備に登録する操作も制限する。前稿で説明が不足していた点は、**新しい「受付停止・配信有効」の状態でも、この管理操作の制限をそのまま適用するか**という選択である。

### 5.2 採用する制限

| 操作 | 受付停止中の扱い |
| --- | --- |
| 手元のTOMLや音声ファイルを編集する | できる。サーバーには変更を送らない |
| 公開状態や処理結果、一覧を確認する | 既存の照会条件に従ってできる |
| 新しい音声・画像・番組やEpisodeの情報をアップロードし、公開準備に登録する | できない。受付再開後に行う |
| Show/Episodeの公開・更新・非公開化・復元を新しく依頼する | できない |
| 既に受け付けられた公開処理 | 引き続き実行する |
| リスナーが公開済みの内容を取得する | 配信停止や保守中でなく、既存の配信条件を満たせばできる |

**「リスナーには配信を続けるが、管理者からの新しい変更は受け付けない」方針で合意した。** 公開依頼だけを止めて、アップロードは受け付ける別の状態は追加しない。

### 5.3 アップロードも止める案・止めない案の比較

| 案 | メリット | デメリット |
| --- | --- | --- |
| **アップロードや素材登録も止める（採用）** | 現在の停止中の制限を再利用できる。保守中に新しい素材操作が増えず、今回の変更を小さくできる | 停止中に次回分の音声をサーバーへ準備しておくことはできない。手元での編集に限られる |
| 公開依頼だけを止め、アップロードは許可する | 配信内容を変えずに、次回分を準備できる | アップロードの許可を公開受付と分けて判定し、再開後に素材を使えるかの確認も設計・試験する必要がある |

アップロードを許可すること自体が直ちに危険という意味ではない。既存実装の変更範囲と、停止中にどこまで準備できると便利かの比較である。

### 5.4 停止前に始まった処理への注意

停止コマンドは、既に送信中のファイルを強制的に中断したり、送信が終わったと保証したりするものではない。ファイル転送後の結果登録が拒否された場合も、手元の操作記録を保持し、不明な転送をやり直さない。

素材の取消・削除については、既存の「未使用であることの確認」と明示承認を引き続き必要とする。本件を理由に削除できる対象を増やさない。

## 6. 停止・再開の結果をどう記録するか

変更番号とサーバー側の操作結果保存を両方追加する案を採用した。目的は2つあり、**古い再開要求による停止の取り消しを防ぐこと**と、**返答を受け取れなかった操作の結果を確認できるようにすること**を分けて説明する。実際に障害が発生したという報告ではなく、変更前のコードから想定した状況への対策である。

### 6.1 古い状態を見て行った再開を拒否するための変更番号

各Showに、新しい停止・再開操作を適用するたびに増える番号を持たせる。保存項目名の案は`availability_version`とする。製品のリリース番号とは関係しない。

想定しているのは、別端末からの操作や、コマンドの同時実行で次の順序になる場合である。

1. Showは受付も配信も停止中で、既受付の公開処理は終わっている。
2. 管理者が端末1で`show-resume`を実行する。CLIが停止状態を確認し、再開要求を準備するが、サーバーへ届くまでに時間がかかる。
3. その間に、別の管理者が端末2で`show-pause`を実行する。「引き続き止めておく」という操作が、サーバーで先に完了する。
4. その後、端末1の再開要求が届く。

変更前の実装の再開条件は、停止中であること、既受付処理が終わっていること、サーバーの動作確認が済んでいることなどである。この例では手順4でも条件を満たすので、先に準備した再開要求が、後から行った停止を取り消し得る。各操作をデータベースで順番に実行するだけでは、この確認と適用の間の行き違いは防げない。

変更番号を追加すれば、端末1が確認した番号7と、端末2の停止後の番号8が違うため、古い再開要求を拒否できる。

**この目的には、すでに停止中のShowへ改めて停止を指示した場合も番号を増やす必要がある。** 状態が変わらない操作で番号を増やさない方式では、この例を防げない。新しい操作IDの停止・再開が適用されたら番号を増やし、適用済みの同じ操作IDの照会・重複受信では増やさない。

CLIは確認した変更番号を操作に含める。番号が違う場合は現在の状態を確認し直し、新しい操作として実行する。CLIが勝手に新しい番号へ置き換えて再送することはしない。

この仕組みは、管理者同士の判断や承認手順を代わりに行うものではない。停止後の新しい状態を確認して、意図的に別の再開操作を行うことは引き続き可能である。

### 6.2 通信が切れても、その操作が適用されたかを確認するための記録

変更前のCLIも、停止・再開を送る前に手元へ操作記録を保存し、返答が不明な操作を同じIDで再実行しようとすると拒否していた。**自動でやり直さず止まる対策は既にあり、今回は保存結果を読み取って確認できるようにする。**

そのうえで、次のような状況では、その操作の結果を確認する情報が不足する。

1. CLIが配信停止の要求を送り、サーバーでは停止に成功する。
2. 成功の返答をCLIが受け取る前、または成功を手元へ保存する前に、通信断やCLI終了が起きる。
3. 手元の記録は「送信したが結果不明」のままになる。

状態照会で`paused`が返っても、「その操作が成功した」のか「別の操作によって停止している」のかは区別できない。サーバーへ操作IDごとの結果を保存すれば、**元の操作をやり直さず、その操作が適用されたかを問い合わせられる**。これが操作結果の保存を追加する主な利点である。

保存するのは、停止・再開の操作ID、依頼内容、適用後の状態、変更番号、時刻である。公開コンテンツや全APIの詳細な履歴を保存する提案ではない。

- 同じ操作ID・同じ内容が再び届いても、保存済みの結果を返すだけにする。その後の再開を取り消すような再適用はしない。
- 同じ操作IDで内容が違う場合は拒否する。
- 後から別の操作が行われている場合に備え、「その操作を適用した時の結果」と「現在の状態」を分けて表示する。
- 結果を取得できない場合、現在の状態が希望どおりだからという理由だけで、元の操作が成功したとは判断しない。
- 操作結果が404でも、遅れて要求が届く可能性があるため「未実行だから再送できる」とは判断しない。

状態の変更と結果の保存は、データベースの1回のトランザクションで行う。トランザクションとは、関連する書込みがすべて成功するか、すべて取り消されるかの単位である。状態だけ変わり、結果の記録だけ欠けることを避ける。

### 6.3 受付期間IDとは別の番号

既存の`show-resume SHOW NEW_WINDOW_UUID`で指定するUUIDは、新しく受付を始めた期間を識別するIDである。これは前項の変更番号とは別で、古い受付期間に準備した公開依頼を、再開後にそのまま使わせないためにある。

停止時は受付期間IDを変えない。既に受け付けた公開処理が、元のIDで最後まで実行できるようにする。受付再開時だけ、未使用の新しいIDへ変える。

### 6.4 記録を追加する利点と費用

| 案 | メリット | デメリット |
| --- | --- | --- |
| 変更前のCLI側の記録だけを使う | サーバーへの追加実装が少ない。結果不明なら止まる既存の対策は維持できる | §6.1の古い再開要求を拒否する追加確認も、§6.2の操作IDごとの結果照会もできない |
| 変更番号だけを追加する | §6.1の行き違いを拒否できる。操作結果の保存表や照会APIは不要 | 通信断後は、現在と同じく、その操作の結果を特定できず止まる場合が残る |
| **変更番号と操作結果の保存を両方追加する（採用）** | 古い再開要求を拒否でき、通信断後も保存済みの操作結果を確認できる | 保存項目と結果照会用APIが増える。操作ごとの小さい記録が蓄積する |

この記録追加は「受付と配信を分けること」そのものに不可欠ではない。操作が1人・1端末から順番に行われる運用では、§6.1の問題が起きる機会は少ない。ただし、同じ管理者でも複数のCLIを並行実行すれば起き得る。通信断による§6.2の問題は、1人での運用でも起き得る。

比較の結果、変更番号による古い再開要求の拒否と、操作ID別の結果照会を両方採用した。結果不明の書込みを推測で再実行することは認めない。

現行の確認箇所は、`packages/cli/src/sqlite-commands.ts`の停止・再開用の手元記録と、`src/sqlite-service-http.ts`、`src/sqlite-publication-queue.ts`の停止・再開処理である。

## 7. 公開済みの内容だけを配信する方法

### 7.1 既に受け付けた公開処理はどうなるか

新しい公開依頼の受付と、受付停止の保存を、同じShowのデータベースで判断する。

- 公開依頼の受付が先に完了した場合、その処理は停止後も実行する。
- 受付停止が先に完了した場合、その後の新しい公開依頼は拒否する。

**受付停止時のFeedを固定する機能ではない。** 既受付処理が正常に完了した場合は、新しく確定した公開内容に切り替わる。

| 既受付処理の状況 | 配信の扱い |
| --- | --- |
| 通常のShow/Episode更新中 | 既存の検証条件を満たせば、更新前の公開内容を配信する |
| Showの初回公開中 | 公開済みの旧内容がないため、処理中の配信は拒否する |
| 非公開化・復元の実行中 | 従来どおり処理中の配信を拒否する |
| 非公開化が完了 | 非公開になった対象は返さない |
| 公開処理が異常停止 | 更新前の内容が安全に読めると記録・確認できる場合だけ、既存の範囲で配信する。それ以外は拒否する |

異常停止した公開処理がある場合、`drained`にはならない。Feedを取得できることと、公開処理が成功・終了したことを混同しない。

### 7.2 キャッシュがあっても停止を回避させない

リスナーからの要求ごとに、次の順で処理する。

1. URLから対象Showを特定する。
2. そのShowの最新状態を読み、配信停止中・保守中でないこと、サーバーの動作確認が済んでいることを確認する。
3. Show/Episodeの公開状態、処理中の変更、配信を許可したファイルの版を確認する。
4. 許可された場合だけ、その版のキャッシュまたは保存ファイルを使って返す。

手順2〜3の判断は、同じShowのデータベースでまとめて行う。停止状態を数秒間使い回したり、別の保存先へ問い合わせた古い結果で判断したりしない。

- 配信停止中やサーバーの未確認状態では、503を返し、そのエラーをキャッシュに保存させない。
- 独自ドメインの配信と、旧workers.dev URLからの転送の両方に同じ停止判定を適用する。停止中は転送先URLも返さない。
- キャッシュが残っていても、上記の判断を省略しない。停止成功のためにキャッシュ削除の完了を待つ必要はない。
- 一方、公開処理やサーバーの動作確認に必要な既存のキャッシュ削除は、引き続き完了を確認する。
- Feed・画像・音声は、許可された同じ版のファイルを読む。遅れて終わった旧版の読込みを、新版のキャッシュとして使わない。
- 未公開素材や内部管理用ファイルは返さない。本文取得、ヘッダーだけの取得、一部分の音声取得、更新がない場合の304応答も同じ条件で扱う。

停止前に配信を許可し、既に送信を始めていた音声などは、停止後に送信が終わることがある。送信済みデータやリスナーが保存済みのファイルを取り消すことはできない。今回保証するのは、**停止が記録された後に新しく配信を判断する要求を、キャッシュや別URLで通過させないこと**である。

## 8. 保存形式の変更と、既存環境への影響

### 8.1 「新規環境専用」とは何か

前稿の「fresh専用」は、**対応版のCLIで新しくサービスを初期化した環境だけを対象にする**という意味である。

新しい状態や変更番号、操作結果を保存するには、SQLiteの表の定義を変える必要がある。今回は旧形式のデータベースを自動変換して新機能を追加する処理を作らない。対応しない形式が見つかったら、更新準備や配備を始める前に拒否する。

これは、既存環境を削除してよいという意味ではない。また、サービス設定ファイルに項目を足すだけで、旧環境を新形式として扱ってよいという意味でもない。

### 8.2 管理者にとっての利点と制限

- 利点: 過去の不完全な記録から新しい停止状態を推測したり、処理途中のデータを変換したりする必要がなく、対応する保存形式を1つに絞れる。
- 制限: 既存環境へ通常のプログラム更新を行うだけでは、新機能を追加できない。新機能を使うには別の新規環境が必要で、本件はコンテンツの移行機能も提供しない。
- 対応する保存形式で新規作成した後は、その形式を変更しない通常のプログラム更新は引き続き可能である。

旧環境の移行・旧形式との併用を作らないことは、このリポジトリの既存方針であり、本件で初めて提案した方針ではない。今回の設計では、§3の新状態と§6の操作記録を保存するために、表の定義を変更する。前稿では、**操作記録を追加するかという判断**と、**保存形式を変えた場合の既存環境への影響**を一文にまとめてしまっていた。本稿では別々に説明する。

既存サービス、非テスト用DNS、共有証明書、手元の原本・操作記録・検証記録は変更・削除しない。

## 9. 実装の詳細

ここからは実装担当向けの採用仕様である。

### 9.1 保存項目とAPI

| 対象 | 実装 |
| --- | --- |
| `publication_service.state` | `open / admission_paused / paused`の3値を保存する。受付可否と配信可否は、この値から求めて別々には保存しない |
| `availability_version` | Showの停止・再開の変更番号。新規作成時は0。新しい操作IDの停止・再開を適用した場合に1増やす。同じ状態を維持する停止でも増やすが、適用済み操作の照会・重複受信では増やさない |
| `publication_availability_controls` | 操作ID、変更できないよう固定した依頼内容とそのhash、確認時の変更番号、適用結果、受付期間ID、適用時刻を保存する表を追加する |
| 停止・再開のPOST | Show、実行プログラムの版、設定のhash、操作ID、確認時の変更番号を照合する。受付再開では新しい受付期間IDも照合する |
| 新規POST | Show向け`/admin/sqlite-service/admission-pause`と`delivery-resume`を追加する |
| 新規GET | `/admin/sqlite-service/controls/<operation_id>`で、その操作の結果と現在のShow状態を分けて返す |

操作結果の表は`operation_id`を主キーとし、`request_json`、`record_json`、一意な`opened_window_id`を持つ。`record_json`に要求、要求のSHA-256、適用結果、適用時刻を保存し、読取時はstrict schemaと元の要求の一致を検査する。`opened_window_id`は受付再開でだけ保存し、過去の受付期間IDの再利用を拒否する。公開コンテンツの本文をこの表へ保存しない。

状態・受付期間ID・操作結果を同じトランザクションで保存する。ファイル転送などの外部通信は、そのトランザクションに含めない。保存失敗時は関連する変更をすべて取り消す。

管理APIは引き続きworkers.devの管理用URLだけで受け付ける。認証、対象Showのヘッダーと本文の一致、入力サイズ・形式の検証を省略しない。

CLIは送信前に操作をディスクへ保存する。応答不明のPOSTを自動再送せず、同じ操作IDのGET照会で確認する。結果を確認できないまま、別IDで同じ変更をやり直すことも復旧手順にしない。

CLIには読取専用の`show-control-status SHOW OPERATION_UUID`を追加した。元と同じ停止・再開コマンドを同じIDで再実行した場合も、送信開始済みならGETだけで照合する。保存結果と元の要求が完全に一致した場合だけ、手元の記録をconfirmedへ更新する。手元の形式番号2の制御記録には既存のプロセスロックを使い、CLI終了時はOS側で排他を解く。未知の旧ロックを削除する処理は追加しない。`doctor --local`は未完了・不正・非対応形式の手元記録を報告するだけで、照会・変換・削除をしない。

### 9.2 JSONと画面表示

Showの状態表示には、次を併記する。

- 受付中か受付停止か（`admission_state`）。
- 配信を有効にしているか、停止しているか（`delivery_policy`）。
- サーバーの動作確認が済んでいるか（既存の`publication_ready`）。
- 既受付処理が終了したか、実行待ち・実行中・異常停止中の処理があるか。
- 停止・再開の変更番号（`availability_version`）。

配信を有効に設定しているだけで、「現在、正常に配信できる」とは表示しない。

`service-status`では、3状態それぞれのShow数を表示する。全体の参考表示は、openが1つでもあればopen、なければadmission_pausedが1つでもあればadmission_paused、すべてpausedならpausedとする。Showが0件の場合は件数0とpaused/drainedを表示する。

この全体表示は、各Showから別々に取得した結果を集めたものであり、全Showの同時点の状態ではない。配備の許可は表示だけで決めず、既存の更新準備処理で各Showを確認する。照会に失敗したShowを、停止済みとみなさない。`list-shows`では従来どおり全体状態を表示せず、Episode一覧は対象Showの3状態に対応させる。

### 9.3 保存形式の識別

| 識別対象 | 採用した形式 |
| --- | --- |
| サービス設定 | `schema_version=2`、`sqlite-sequential-v1`、`storage_layout="show-v1"`を維持する |
| 公開待ち行列などの表の形式番号 | 調査基準の6から7へ変更する。新しい状態・変更番号・操作結果の表を識別する |
| 公開コンテンツの表の形式番号 | 7のまま。Feed・画像・音声や既存の配信検証用項目は変えない |
| サーバーの対応機能表示 | `availability_controls="show-admission-delivery-v1"`を必須項目として追加し、新CLIが対応サーバーか確認できるようにする |
| CLI側の停止・再開の記録形式 | 形式番号2とし、確認時の変更番号と追加の2操作を保存できるようにする |

形式番号は実装開始時に他Issueとの変更が重ならないか確認する。サービス設定の番号、内部の表の形式番号、CLIの記録形式番号は別々に管理する。

既存DBへの項目追加による変換、過去の操作結果の推測作成、旧CLI記録の書換えは行わない。DO/cacheのクラス名・binding・compatibility dateは変更せず、Workerの入口は`src/sqlite-worker.ts`を維持する。

### 9.4 既存機能で変更しない条件

- 別のShowが停止・異常停止していても、健全なShowの通常運用や新Show登録は妨げない。通常の受付と配信判断は、そのShowのDurable Object内で行う。
- Worker更新とドメイン変更には、引き続き対象Showすべての`paused`と`drained`を要求する。`admission_paused`を`paused`として扱わない。
- 共有保守の対象Show一覧と、Showごとの準備・切替・確認・保守終了の結果は、既存のサービス制御用Durable Objectで管理する。一部だけ成功した場合は全体成功とせず、不明な操作の再送や自動的な保守終了を行わない。
- 保守中の`show-pause`も、認証と正確なShow・プログラム・設定の確認を必要とする。`selectSqliteRuntime`が保存済みの更新準備から実行対象を選択できない場合は、配信を拒否し、停止操作にも成功応答を返さない。
- Issue #65の予約公開は実装済み。受付停止時には未投入の予約を`needs_approval`へ移し、停止状態の保存と同じtransactionで記録する。配信だけを再開しても予約を実行せず、明示再承認を要求する。
- 不明な書込みの再実行、異常停止の強制解除、操作の所有権の奪取、保存記録の自動期限切れは追加しない。

## 10. 実装順序と試験

### 実装順序

1. 3状態、停止・再開の依頼と結果、変更番号、保存形式の検証を追加する。
2. `src/sqlite-publication-queue.ts`に停止・再開と結果保存を実装し、`src/sqlite-operation-runtime.ts`の素材操作の制限と揃える。
3. `src/sqlite-show-service.ts`と`src/sqlite-publication-content.ts`で、最新の停止状態から配信対象の決定までを同じトランザクションで確認する。`admission_paused`でも既存の配信検証を省略しない。
4. 管理API、CLI、結果照会を追加する。既存のPause/Resumeも新しい操作結果の保存に接続する。
5. `src/sqlite-service-control.ts`、一覧、Worker更新、ドメイン変更で、新状態を取り違えないようにする。
6. help/describe/schema/JSON/doctor、管理者Skill、README、SQLite操作ガイド、現行設計、Show分離・Worker更新の資料を実装と一致させる。

### 必須の試験

| 場面 | 確認すること |
| --- | --- |
| 停止と公開依頼が同時に来る | 先に受け付けた処理だけが残り、停止後の新しい依頼は拒否する |
| 3状態間の操作 | 受付だけの停止で配信が勝手に再開しない。配信だけの再開で受付が開かない |
| 再開前の条件確認 | 処理中・異常停止中・動作未確認・保守中の場合、合意した条件に従って再開を拒否する |
| 別端末からの同時操作 | 古い変更番号の操作が、後から行った停止・再開を取り消さない。停止中に改めて停止した場合も、先に準備されていた再開要求を拒否する |
| 受付停止後の公開完了 | 既受付処理は実行され、保存・検証・必要なキャッシュ削除が終わった内容だけに切り替わる |
| 配信継続 | Feed・画像・承認済み音声の本文、HEAD、Range、ETag・日付条件を扱え、未公開素材を返さない |
| 初回公開・非公開化・復元・異常停止 | 今まで拒否すべきだった処理中の配信を、新状態によって許可してしまわない |
| キャッシュと別URL | キャッシュの有無や旧版読込みの完了順にかかわらず、停止後の新しい判断で内容や転送先を返さない |
| 通信断・再起動・保存失敗 | 操作が二重に適用されない。保存失敗では一部分だけ変更されない。結果不明を推測で成功にしない |
| 複数Show | 一方の停止が他方の通常運用を止めない。全体表示の取得失敗を停止済みとみなさない |
| Worker更新・ドメイン変更 | 受付停止だけでは準備を開始しない。一部の保守操作の失敗後も、自動で再開・やり直しをしない |
| 旧保存形式・正式CLI | 非対応の保存形式を変更前に拒否する。正式CLIとJSON表示で各操作と結果照会を確認する |

実装後は`bun test`、`npm run check`、`npm run build:cli -- linux-x64`、`git diff --check`を実行する。新しいテストツールは追加しない。

実Cloudflare環境での試験は別の承認を必要とする。行う場合は新規の隔離環境を使い、2 Showで受付だけの停止、配信継続、両方の停止、配信だけの再開、通常の受付再開、両公開URLの停止、停止を伴う通常のWorker更新を確認する。

ローカル試験だけでCloudflare上の動作・全拠点のキャッシュ・性能を確認済みとはしない。小規模な実機試験だけで、無停止更新、300MB音声の動作、すべての無料枠への適合やIssue #13の恒久解決を主張しない。

## 11. レビューで合意したこと

### 合意済み

**今回は、受付停止と配信停止を分ける機能だけを対象にする。Worker更新中も配信を続ける機能は作らない。**

1. **状態と操作（§3〜§4）**: 既存`show-pause`は両方を止める操作のままとし、受付だけの停止と配信だけの再開を別コマンドで追加する。
2. **配信再開前の待機（§4.3）**: 配信だけを戻す場合も、既受付の公開処理がすべて終わるのを待つ。サーバーの動作確認済みで、保守中でないことも要求する。
3. **アップロードの制限（§5）**: 受付停止中は新しい素材のアップロードや登録も止める。

### 操作記録も追加する

**サーバーへの操作記録追加（§6・§8）も合意済み。** 想定する問題を§6.1と§6.2の具体例に分け、変更番号と操作結果保存を両方追加する案を採用した。

- 変更番号を追加し、状態確認後に別の停止・再開があったら、先に準備された要求を拒否する。
- 操作IDごとの適用結果も保存し、通信断後に元の操作をやり直さず結果を照会できるようにする。

変更番号だけを追加する小さい案も比較したうえで、上記を採用した。保存形式が変わる場合も旧環境を自動変換しないという既存方針と、既存環境へ新機能を通常更新だけでは追加できない制限は§8に示す。

この合意に基づき、コードの実装とローカル検証を行う。実装の承認は、実環境の配備・公開・再開、資源・ドメイン・権限・課金の変更や削除、手元の記録の削除を許可するものではない。

| `git diff --check` | 差分の空白検査に成功 |

追加した試験は、3状態と操作結果の保存、繰り返し停止による古い再開要求の拒否、過去の受付期間IDの再利用拒否、状態保存失敗時の全体取消、応答喪失後のGET照合、欠落した対応機能表示の拒否を含む。CLIをサーバー適用後にSIGKILLした場合も、プロセスの終了後にGETだけで照合し、再適用されないことを確認した。

配信では、受付停止中のFeed・画像・音声、HEAD/Range/条件付き要求、旧workers.devからの転送と独自originへの停止判定、遅い旧キャッシュ読込み、公開処理の終了待ち、初回公開・非公開化・復元・異常停止の拒否条件を確認した。既存の複数Show・Worker更新・ドメイン変更の回帰も成功した。

これらは模擬R2/キャッシュ/Cloudflare RESTと、ローカルSQLite・CLI processによる結果である。実Cloudflareへの配備・公開・再開やnative cache/rolloutの測定は行っていない。Worker更新中の継続配信、性能や全Free適合の保証にはしない。

本PRでは実機試験を省略する。Cloudflareの資源構成・binding・cache ownerを変更せず、既存の配信経路で受付状態の扱いと停止・再開記録を追加する変更であること、新規環境だけを対象にし、ローカルで公開処理・故障・再起動・CLI強制終了を検証できていることをPR作成の判断根拠とする。実Cloudflareの永続化やキャッシュ動作を確認済みという意味ではない。

依存関係の確認では、既存のZod 4.6.5にHighの[メモリー枯渇に関する勧告GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)が報告された。[依存更新のIssue #78](https://github.com/simosako/castloop-v2/issues/78)へ分離し、本PRではpackage/lockを更新しない。今回の試験成功は、この勧告の解消を意味しない。
