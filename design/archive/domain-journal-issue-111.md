# 独自ドメイン変更ジャーナルの簡素化に関する検討

対象: [Issue #111: ドメイン変更ジャーナルのフェーズ粒度の見直し](https://github.com/simosako/castloop-v2/issues/111)

調査対象: コミット `e368f34`、2026-11-02時点。2026-11-03に案Aを採用しました。この資料は当時の比較と判断の記録であり、現在の設計は[制御DO・独自ドメイン](../components/control-do.md)を参照してください。Cloudflare操作の承認ではありません。

## 結論

**6相を維持し、それぞれの意味と再開時の制約を明文化する案Aを採用しました。** `remote_ready` は他の相と異なり、同じ確定要求の再実行で代替できる可能性があり、5相に減らす案Bも検討に値します。ただし、減るのは主に1回のジャーナル保存と分岐であり、実施すべき確認や中断位置のテストはほぼ残ります。既存の進捗記録と利用者への影響もあるため、現時点では変更の便益がコストを上回るとは判断できません。

ポッドキャスト配信そのものに、Cloudflareの独自ドメインを自動管理する6相の処理が必須なわけではありません。この複雑さは、稼働中の複数のDurable Object（DO）、Worker、DNS、ローカル設定を、変更後の公開URLに整合させる現在の機能から生じています。機能を維持する限り、接続と配備の確認結果、変更前後の設定、各DOの確定、および削除前のローカル同期を区別する必要があります。一方で、`remote_ready` という独立した保存点までは必須と立証できません。

## 現状と維持すべき条件

ローカル記録は `.castloop/sqlite-domain-changes/<service_id>/<operation_id>.json` にあり、`schema_version` は `1` です。要求には変更前後の設定とハッシュ、対象ホスト、DO名前空間、Workerソース等のハッシュが保存され、別途、変更前の配備情報も保存されます。`connected` 以降は接続情報、`deployed` 以降は配備情報が必須です。各DOの変更記録は別物で、状態は `prepared` / `completed` の2つです。未完了のDO操作には一意索引があり、CLIにもローカルの未完了記録の確認があります。

根拠: [CLIジャーナル](../../packages/cli/src/sqlite-domain-journal.ts#L7-L32)、[要求の作成](../../packages/cli/src/sqlite-domain-operation.ts#L28-L60)、[ローカル記録の走査](../../packages/cli/src/sqlite-domain-local.ts#L8-L21)、[DOの表と一意索引](../../src/sqlite-domain-runtime.ts#L14-L22)。

変更案の評価では、少なくとも次を維持します。

- 同じ操作IDと固定された要求・接続・配備を照合し、無関係な設定や既存リソースを取り込まない。変更前後の設定も保持する。
- TLS待ちとWorker反映待ちは、保存済みの接続・配備を使って `domain status` / `domain continue` で確認・継続し、接続や配備をむやみにやり直さない。
- 各Showのキャッシュ消去と設定確定、その後の制御DOの確定を維持する。準備中の配信・公開の制限も変えない。
- ローカルの無関係な編集を上書きしない。同期済みと記録した後は、設定が変更前に戻っていたら最終処理しない。
- 独自ドメインの削除は、新しい `workers.dev` 側を確認し、ローカルを同期した後に行う。解除済みなら同じ解除を再送せずに最終確定できる。
- 既存の記録やバックアップの扱いを決めずに保存形式を変更しない。非対応形式の移行・互換処理や、未知のリソースの取り込みは追加しない。

### 6相が表すもの

相は、その相へ**保存する直前までに確認したこと**を示します。外部状態が後から変わっていないことの証明ではありません。

| CLIの相 | 保存時点と、次回継続での役割 |
| --- | --- |
| `prepared` | 固定した要求と変更前の配備情報をローカルに保存済み。各DOの準備や接続がまだ未完了の場合もあります。旧配備を照合し、準備と接続を行います。 |
| `connected` | 各DOの準備後、確認済みの接続情報を保存済み。TLSはまだ準備中の場合があります。接続とTLSを確認してから設定・Workerを配備します。 |
| `deployed` | Workerのアップロード応答に対応する配備情報を保存済み。Workerが全て反映済み、または各DOが確定済みとは限りません。同じ配備を照合・観測してDOを確定します。 |
| `remote_ready` | 制御DOと全Show DOの確定応答を確認済み。ローカルTOMLは未同期の場合も、同期途中で変更後になった場合もあります。DO・配備・接続を再確認し、無関係な編集を拒否してローカルを同期します。 |
| `local_synced` | 変更後のローカル設定への同期を記録済み。削除では接続解除前の場合も解除済みの場合もあります。ローカル設定を検証し、接続の最終処理を行います。 |
| `completed` | 接続の最終処理と制御DOの最終確定を確認し、完了を記録済み。継続は固定入力とローカル設定の検証後に完了を返します。 |

実際の処理順は[継続処理](../../packages/cli/src/sqlite-domain-operation.ts#L63-L141)、DOごとの確定と同一要求の扱いは[DOランタイム](../../src/sqlite-domain-runtime.ts#L51-L92)と[制御DO](../../src/sqlite-service-control.ts#L148-L204)を参照してください。

`domain status` はローカルの相とDOの状態を返すもので、TLS自体を検査するコマンドではありません。TLSの再確認は `domain continue` で行います。また、ローカル記録の作成後でもDOの準備記録がまだ存在しない場合や、Showの準備が途中の場合は、リモート状態を取得できず `status` がエラーになることがあります。TLS待ち時の `connected` とWorker反映待ち時の `deployed` は、それぞれ[既存テスト](../../packages/cli/src/sqlite-domain-operation.test.ts#L48-L61)と[既存テスト](../../packages/cli/src/sqlite-domain-operation.test.ts#L188-L214)で扱っています。

### 現状の「再開可能」と「前回設定」の範囲

- 変更前の設定は保存されますが、それだけで任意の中断位置から自動的に変更前へ戻せるわけではありません。現在の `domain continue` は保存済みの**同じ変更を完了する**処理であり、途中取消し・ロールバックのコマンドではありません。正常完了後に反対の `domain add` / `domain remove` を行う場合も、新しい操作の前提条件と外部状態の確認が必要です。以前の接続IDやWorker配備そのものを復元する保証ではありません。
- たとえばWorkerのアップロードは成功したものの、その応答や配備情報の取得が確認できないと、ジャーナルは `connected` のまま残り得ます。次の継続で旧配備の照合が合わなければ停止し、保存済みの配備情報なしに新配備を採用しません。全ての通信途絶から自動復旧できる、とは言えません。記録を消して新しい操作を始めることも、この調査では安全なやり直し方法として推奨しません。

根拠: [配備と保存の順序](../../packages/cli/src/sqlite-domain-operation.ts#L91-L101)、[配備情報の照合](../../packages/cli/src/sqlite-cloudflare.ts#L78-L103)、[操作の選択肢](../../packages/cli/src/sqlite-commands.ts#L106-L116)。Issueや作業規則の「前回設定を再適用可能」が、未完了操作の途中でのロールバックまで含むかは明確ではありません。設定の保存だけでその要件を満たすとも、満たさないとも断定できないため、意味と実現方法の確認が必要です。

## 改善案の比較

### 案A: 6相を維持し、根拠と限界を明文化する（採用）

現在の保存形式と実行順序は変えず、各相の説明と継続時の制約を[制御DO設計](../components/control-do.md)に明記します。この文書は設計上の判断材料として残します。

メリット:

- TLS待ち、配備待ち、ローカル同期後の解除・最終確定を、現行の記録とテストのまま区別できます。
- 既存の未完了・完了済みジャーナル、バックアップ、CLIの `local_phase` の意味を変えません。
- 中断位置ごとの外部状態を安全に判断する処理を、急いで別の分岐へ移す必要がありません。

デメリット:

- `remote_ready` の保存と相の分岐が残り、6相を理解する負担は減りません。
- 「6相が必要」という説明だけでは過剰設計の懸念を解消できません。特に `remote_ready` の独立した永続化は、案Bで代替できる可能性があります。

### 案B: `remote_ready` をなくし、5相にする

相を `prepared → connected → deployed → local_synced → completed` とし、`deployed` の処理でDO確定に続けてローカル同期まで行ってから `local_synced` を保存する案です。接続・配備の確認結果と変更前後の設定は今と同じように保存します。**これはコード読解に基づく候補であり、変更後の動作を実装・検証した結論ではありません。**

再開時の考え方:

1. `connected` と `deployed` の保存位置を維持し、TLS待ちとWorker反映待ちでは既存の接続・配備を再利用します。
2. `deployed` のまま中断した場合は配備・接続を照合し、同じ確定情報でDOの確定をやり直してから、全DO完了を確認します。DOは同一の確定情報なら既存結果を返し、異なる確定情報を拒否します。新しい配備は行いません。
3. ローカルTOMLが変更前なら従来どおり変更後へ同期し、既に変更後なら同期済みとして扱います。どちらでもない編集は拒否します。rename後・相の保存前に中断した場合もこの確認を通します。
4. 接続解除より前に `local_synced` を保存し、その後の解除と最終確定は現行どおりにします。`local_synced` 保存後にTOMLが変更前へ戻った場合は、現行どおり通信前に拒否します。

メリット:

- 独立した `remote_ready` の保存・分岐がなくなり、通常経路の永続化が1回減ります。DO側に既にある同一確定要求の再実行を使うため、新しい状態や復旧機構は必要ありません。
- 接続情報・配備情報・ローカル同期済みという、後続の動作を変える保存点は維持できます。

デメリット:

- ローカル同期前に中断すると、現行の `remote_ready` からの再開と異なり、配備・接続の再確認に加えてDO確定要求も再送します。利用者が明示的に継続した場合の再送であり、変更系HTTPの自動再試行ではありません。
- 確認と障害時テストはほぼ残るため、分岐数ほど検証コストは減りません。`local_phase: deployed` は「DO確定後だがローカル同期前」も含むようになり、状態出力の意味が粗くなります。リモートの `all_completed` は別に確認できます。
- 現行の `remote_ready` 記録と、その相を読む利用者・自動化の扱いを決める必要があります。下記のリリース条件が未解決のままでは採用できません。

#### なぜ `local_synced` を先に消さないか

現在の削除処理では、`local_synced` の後に接続を解除します。解除に成功したが応答が失われた場合、再開時には一覧で接続がないことを確認し、DELETEを再送せず最終確定します。一方、`remote_ready` からのローカル同期処理は接続が存在することを `inspect` で確認します。単に2相を1相へまとめてその処理を再実行すると、解除済みの場合に接続照合で止まります。

さらに `local_synced` は、同期を確認した後でローカル設定が変更前に戻された場合の拒否にも使われます。これを削るなら、解除済みの判別とローカル同期の確認済みという情報を別の形で保持・検証する必要があり、相を減らしても複雑さが移るだけです。根拠: [接続の検査と解除](../../packages/cli/src/sqlite-domain-cloudflare.ts#L226-L245)、[解除応答喪失のテスト](../../packages/cli/src/sqlite-domain-operation.test.ts#L78-L90)、[ローカル設定差し戻しのテスト](../../packages/cli/src/sqlite-domain-operation.test.ts#L237-L248)。

### 案C: `deploy` のようにジャーナルを廃止する

現状の `deploy` は設定と既知の接続を維持したWorker更新であり、同じ設定で再実行します。一方、独自ドメイン変更では設定そのものを変更し、接続・配備・複数DO・ローカルTOMLにまたがる証拠が必要です。

メリットはローカルの相とその管理をなくせることです。デメリットは、保存済みの変更前後の設定、確認済みの接続・配備と途中経過をどこか別の場所で管理する必要があることです。単に記録をなくすと、TLS待ちや配備待ちの継続、未知の接続・配備の不採用、削除後の再開を維持できません。独自ドメイン自動管理自体をやめるなら別ですが、既存の製品仕様の変更になるため本Issueでは推奨しません。比較対象: [通常のdeploy](../../packages/cli/src/sqlite-service-deploy.ts#L19-L58)。

| 観点 | 案A: 現状維持 | 案B: 5相 | 案C: 記録廃止 |
| --- | --- | --- | --- |
| 現行の動作・記録 | 変更なし | 相と状態出力を変更 | 大幅に変更 |
| 簡素化 | 説明の改善のみ | 保存・分岐を1つ削減 | 別の証拠管理や機能削減が必要 |
| 中断後の確認 | 現行どおり | 同じDO確定を再実行する場合あり | 現行保証の維持方法が未定 |
| 互換性・リリース | 対応不要 | 要判断 | 要判断、変更範囲も大きい |

## 案Bを将来採用する場合の条件

### 既存記録とリリース

現行のスキーマは相と `schema_version: 1` を厳密に検証します。`pendingLocalDomainChanges` は未完了だけでなく、**完了済みを含む全JSONを読み取ってから**未完了を選別します。このため、版を一律に変更して旧版を拒否すると、未完了操作がないワークスペースでも旧 `completed` 記録で `domain list` や新規の `domain add` / `domain remove` が失敗し得ます。`doctor` は記録検証失敗、バックアップの未完了操作走査は `scan_errors` として報告します。保存されたバックアップから古い記録が戻る場合も考慮が必要です。根拠: [記録走査](../../packages/cli/src/sqlite-domain-local.ts#L8-L21)、[doctor](../../packages/cli/src/doctor.ts#L44-L52)、[バックアップ走査](../../packages/cli/src/backup-create.ts#L103-L108)。

一方、版を `1` のまま `remote_ready` だけ拒否すれば、従来の `completed` は同じ形式で読めますが、従来の未完了記録のうち共通する相は新旧を識別できません。版を据え置くこと自体が相の意味の変更でもあり、それを許容できるとは未判断です。

したがって、実装前に次の条件を満たすリリース方針を決める必要があります。

1. 更新する各ワークスペースで旧CLIによる未完了操作の有無を確認し、確認できる操作は先に完了する。結果不明の操作は記録を保持し、安全な扱いを決めるまで更新を進めない。旧CLIとの混在や古いバックアップの復元も対象にする。
2. 完了済み記録を保持したまま、新CLIによる一覧・新規操作・診断・バックアップが使える方法と、識別できる古い未完了記録を発見した際の明確な拒否・案内を定める。旧版の自動変換、互換用分岐、記録の削除を前提にしない。
3. `local_phase` を利用する人や自動化への変更を告知する。旧版の未完了記録を新形式と区別できるかも含め、版番号の扱いを決める。

この調査では全利用者のワークスペースやバックアップの状態を確認しておらず、上記を満たす切り替え時期・方式は確定していません。単に「未完了操作がない時期を選ぶ」だけでは、完了済み記録や過去のバックアップへの影響を解消できません。

### 実装時に確認すべき振る舞い

案Bのテストでは、既存のTLS待ち・Worker反映待ち、複数Showの確定、キャッシュ消去、接続・配備の照合に加え、次の継続を確認します。

- DO確定の応答喪失後、およびDO確定後・ローカル同期前の中断後に、同じ確定情報を使って完了し、Workerを再配備しない。確定済みShowのFeed世代やキャッシュ消去を重複させない。
- ローカルTOMLのrename後・`local_synced` 保存前の中断を継続でき、変更前でも変更後でもない編集は上書きしない。
- `local_synced` 保存後の設定差し戻しを通信前に拒否し、削除の解除応答喪失後はDELETEを再送せず完了する。
- 既存の完了済み・未完了記録、状態出力、バックアップ復元について、採用したリリース方針どおりに扱う。

案Bを実装する場合は、CLIジャーナルと継続処理、関連テスト、[制御DO設計](../components/control-do.md)、[利用ガイド](../../docs/custom_domains.md)を見直し、`bun test` と `npm run check` を実行します。今回の調査ではコード変更・テスト実行・実環境操作は行っていません。
