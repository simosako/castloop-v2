# Issue #40: 中断した操作の確認・再開・取消

更新日: 2026-10-19。対象は[Issue #40](https://github.com/simosako/castloop-v2/issues/40)のSQLiteサービス。
案Bを採用し、サーバーへの記録、再開、取消・未公開素材の削除を開発版へ実装した。[利用方法](../../docs/sqlite_operation_recovery.md)と[ローカルでの確認結果](sqlite_operation_records_verification.md)を参照する。以下は比較と採用理由を含む設計書である。

## 1. 目的

CLIが通信断や強制終了で止まったとき、利用者が「どこまで終わったか」「続きから再開できるか」「取り消してやり直せるか」を確認できるようにする。

Issue #40では、36件のRSS取り込みで18件の公開後にCLIが終了し、19件目の音源アップロードの結果が分からなくなった。公開済みの処理は確認できたものの、取り込み全体の進捗や再開の判断には内部ファイルの調査が必要だった。

この問題に対し、次の三つの機能を設ける。

1. **状態の確認**：取り込み、下書き、アップロード、公開処理を関連付けて表示する。
2. **途中からの再開**：完了した処理を再利用し、残りの処理を進める。
3. **取消と不要ファイルの削除**：操作を取り消し、安全に削除できる未公開ファイルを整理する。

実現方法として、CLIの操作記録を改善する案A、サーバーでも操作を管理する案B、分割アップロードを導入する案Cを比較する。

レビューを受け、既存DO内のSQLiteへ記録する案Bを採用した。[保存先の比較](sqlite_operation_record_storage_options.md)と、[操作記録のID・テーブルのDDL](../sqlite_operation_records_schema.md)を別紙にまとめた。

## 2. 利用者の操作

どの案でも、まず状態を確認し、その結果から再開・取消・保留を選べるようにする。

### 状態を確認する

未完了の操作を一覧表示し、対象を指定すると詳細を表示する。

```text
castloop operation-list --incomplete
castloop operation-status rss-import IMPORT_ID --remote
```

手元の操作記録だけを読む`--local`と、サーバーの状態も問い合わせる`--remote`を用意する。確認操作は、記録やロックを変更せずに実行する。

RSS取り込みでは、例えば次のように表示する。

```text
公開完了                 18件
中断したエピソード       19件目
中断した処理             音源のアップロード
手元の記録               送信開始まで記録済み
サーバーの処理結果       不明
この取り込みで未着手     17件

再開の判断に必要な情報   アップロードの成功応答
```

詳細には、番組・エピソードID、最後に記録した処理段階、サーバーで確認できた結果、次に実行できる操作とその理由を表示する。取得できなかった情報も「不明」として区別する。

### 再開する

利用者が対象を指定して再開すると、CLIは保存済みの結果を照合し、続きの処理を実行する。例えば、音源の保存が成功していて内容の確認だけが残っていれば、その確認から再開する。公開済みのエピソードは既存の公開結果を利用する。

### 取り消す・不要なファイルを削除する

取消では、以後その操作を進めないことを記録する。ファイルの削除は別の手順とし、対象と削除できる理由を一覧表示して、利用者の確認後に実行する。

結果は「取消済み・ファイルは保持」「削除完了」「一部を削除し、残りは確認待ち」のように表示する。取り消した操作と競合しないことを確認できれば、新しい操作としてやり直せる。

## 3. 設計案

### 案A：CLIの操作記録を細かくし、途中から再開する

現在のアップロード方法を維持し、CLIが保存する操作記録を改善する案。変更の中心はCLIとなる。

現在は、アップロード開始前に`put_requested`を記録し、保存内容の検証まで終わると`verified`を記録している。この間に止まると、送信中だったのか、保存後の検証中だったのかを区別しにくい。

そこで、音源・画像・メタデータのファイルごとに、次の段階を記録する。

| 記録する段階 | 保存する情報 | 再開時の処理 |
| --- | --- | --- |
| 送信準備完了 | 対象、保存先、サイズ、内容のハッシュ | 入力を照合して送信を開始する |
| 送信直前 | 送信を開始する操作ID | 成功の記録がなければ、結果不明として表示する |
| アップロード成功 | サーバーの成功応答、ETag、保存されたファイルのversion ID | 保存済みファイルを読み戻して検証する |
| 検証完了 | 全体のハッシュ・サイズ・ファイル識別情報の照合結果 | 検証済みファイルを下書きに登録する |
| 下書きへの登録完了 | 登録した下書きとファイルの対応 | 次の処理へ進む |

特に、アップロードの成功応答は、読み戻しを始める前に保存する。これにより、読み戻し中の通信断から再開できる。複数ファイルを扱う場合も、ファイルごとに結果を保存する。

下書きへの登録後、操作記録の更新前に止まった場合は、同じファイルが既に登録されていることを照合して先へ進める。

RSS取り込みの記録にも、処理番号だけでなく、対象エピソード、処理の種類、アップロードID、公開処理のIDを保存する。個々の処理の完了を確認してから、取り込み全体の進捗を更新する。

**利点**：現在の構成を大きく変えずに、保存後の検証や下書きへの登録から再開できる。RSS取り込みの進捗も説明しやすくなる。

**課題**：成功応答を保存する前に停止したアップロードは、引き続き結果不明となる。また、ファイルを別のCLIが公開に使う可能性をサーバーで管理していないため、案AではR2上の不要ファイルの削除は扱わない。取消は送信前の操作に対応する。

### 案B：サーバーに操作を登録し、取消と削除まで管理する

案Aの記録に加えて、既存DOのSQLiteにも操作とファイルの対応を保存する案。保存先を比較した経緯は[別紙](sqlite_operation_record_storage_options.md)を参照する。Workers Logsは障害調査に併用する。

処理は次の順に進める。

1. CLIが、番組・エピソード・下書き・保存予定のファイルをサーバーへ登録する。
2. サーバーが、その操作の開始を記録してアップロードを許可する。
3. CLIがR2へ直接アップロードし、成功応答と検証結果を保存する。
4. CLIが結果をサーバーへ登録する。
5. 公開時には、サーバーが登録済みファイルと操作の状態を確認する。

サーバーは、開始前の操作を取り消したり、不要になった未公開ファイルを削除対象として管理したりできる。アップロードを許可した後に結果が分からなくなった操作は、確認待ちとして保持する。操作の登録だけでは、送信済みの通信が完了したかまでは分からないためである。

ファイルの削除は次の手順で行う。

1. アップロードが終了していて、公開処理や他の下書きから使われていないファイルを候補として表示する。
2. 利用者が削除するファイルを確認する。
3. サーバーが状態を再確認し、削除対象の確定と、新たな公開での利用禁止を同じデータベース処理で記録する。
4. 対象のファイルを削除し、ファイルごとの結果を保存する。

この仕組みにより、一覧を確認した後に別のCLIがそのファイルを公開に使う、といった競合を防ぐ。削除中に通信が切れた場合も、同じ操作IDで結果を確認できる。

**利点**：複数のCLIによる操作をまとめて管理でき、取消・不要ファイルの削除・やり直しまで対応できる。

**課題**：現在はアップロード前にサーバーの許可を待たないため、処理の流れが変わり、通信と管理APIが増える。CLIとWorkerの両方に変更が必要となる。削除対象は、送信の終了を確認できるファイルに限られる。

### 案C：ファイルを分割し、サーバーがアップロード全体を管理する

案Bの操作管理に加えて、音源を複数の部分に分けて送る案。Cloudflare WorkerとR2のマルチパートアップロードを使う。

1. サーバーがアップロードを作成し、操作IDを発行する。
2. CLIがファイルを分割してWorkerへ送り、サーバーが受信済みの部分を記録する。
3. 中断後は、保存を確認できた部分を再利用して続きから送信する。
4. 全部分が揃ったら、サーバーが一つのファイルにまとめる。
5. ファイル全体を検証し、下書きへ登録する。

取消もサーバーが受け付け、完成処理と取消が同時に進まないように管理する。

**利点**：大きな音源の転送途中から再開できる範囲が広がる。アップロードの開始から取消までをサーバー側で管理できる。

**課題**：転送方式そのものが変わり、三案の中で最も変更が大きい。アップロード作成直後や、ファイルをまとめる処理の応答が失われた場合について、結果を確認する方法が必要となる。分割サイズ、Workerの実行時間、ファイル全体の検証方法も実機で確認する。

## 4. 比較

| 比較項目 | 案A：CLIの記録改善 | 案B：サーバーで操作管理 | 案C：分割アップロード |
| --- | --- | --- | --- |
| 進捗・途中状態の表示 | 対応 | 対応 | 対応 |
| アップロード成功後の検証再開 | 対応 | 対応 | 対応 |
| 転送済みデータの再利用 | 保存が完了したファイル | 保存が完了したファイル | 保存済みの部分 |
| 取消 | 送信前の操作 | サーバーで状態を確認できる操作 | サーバーで状態を確認できる操作 |
| 不要な未公開ファイルの削除 | 別途対応 | 送信終了と未使用を確認できるもの | 送信終了と未使用を確認できるもの |
| 主な変更箇所 | CLIと操作記録 | 左記＋WorkerとSQLite | 左記＋転送・検証処理 |
| 向いている目的 | 再開できる場面を早く増やす | 取消・削除まで一貫して扱う | 大容量転送の再開を重視する |

## 5. 採用案と実装範囲

**案Bを採用し、次の3段階を実装する。開発版ではいずれも通常のCLI・Worker経路へ接続した。**

案Aの細かい操作記録も取り入れ、サーバーとCLIの両方で同じ操作IDと処理段階を扱う。保存先の比較は[別紙](sqlite_operation_record_storage_options.md)を参照する。

| 段階 | 実装するもの | 利用者ができること |
| --- | --- | --- |
| 1 | サーバーへの操作登録、操作一覧と詳細表示、容量表示 | サーバーに残した記録から、進捗・中断箇所と、記録容量の余裕を確認する |
| 2 | CLIの記録との連携、再開処理 | 成功済みアップロードや公開結果を使い、途中から進める |
| 3 | 取消・削除 | 条件を満たす操作を取り消し、不要なファイルを削除してやり直す |

案Cは、大きな音源の転送をやり直す負担をどこまで減らしたいかに応じて選ぶ。今回の状態確認と再開機能には、案A・Bで段階的に取り組める。

状態確認はJSONで表示する。アップロードの再開は`operation-resume upload ID`、RSS全体の続行は`publish-rss-import DIRECTORY`を使う。取消と削除は`operation-cancel`、`operation-cleanup-preview`、確認hash付きの`operation-cleanup`で分ける。

操作記録の費用と長期運用は、[無料枠の見積もり](sqlite_operation_record_storage_options.md#記録機能の費用は無料枠に収まるか)と[容量管理・保持方針](sqlite_operation_record_storage_options.md#6-容量管理と記録の保持)を参照する。R2上の不要ファイルの削除と、DB内の記録の整理は別の操作として扱う。

操作記録の構成は、`operation`と`request`を分け、各要求にクライアントIDと受信時刻を直接保存する。セッション表は設けない。未確認のPUTや変更要求は保留し、既知の成功応答から次の処理へ進める。

## 6. 実装時の要点

### 操作記録と再開条件

要求元は`client_id`、再開の対象となる作業は`operation_id`、その作業への個々の指示は`request_id`で識別する。各要求にクライアントIDとサーバーの受信時刻を直接記録し、セッション表は設けない。詳しくは[IDとDDL案](../sqlite_operation_records_schema.md)を参照する。

各操作には固有のIDを付け、サービス設定、Workerのバージョン、対象の番組・エピソード、下書き、元ファイルのハッシュ、操作開始時の公開済み版と更新番号を保存する。再開時にこれらを照合し、同じ操作の続きであることを確認する。

案A・Bでは、操作ごとに決めた保存先へ一度だけアップロードする。成功応答を記録できた場合は、保存済みファイルの検証から再開する。案Cでは、分割した部分ごとに送信結果を管理する。応答を失い、保存結果も通信の終了も確認できない場合は「結果不明」として記録を保持する。後からファイルが見つからなかったという情報だけでは、送信失敗の確定にはならない。

公開は、保存済みの要求ID・処理ID・要求内容を使って結果を問い合わせる。完了済みの結果を取り込みの進捗へ反映することで、GUID・公開日時・音源URL・改訂履歴を維持する。

### 同時実行と強制終了

同じ下書きを複数のCLIが同時に更新しないよう、ローカルの操作記録をロックする。新形式ではBun内蔵SQLiteの`BEGIN EXCLUSIVE`を使い、プロセス終了時にOSがロックを解放する。外部の`flock`コマンドや追加のランタイムは不要である。Linuxの子プロセスをSIGKILLし、排他が解放されることを確認した。

ローカルのロックとサーバーで実行中の処理は、それぞれ確認する。ロックを取得できても、結果不明のアップロードは引き続き確認待ちとなる。

### 既存の記録への対応

既存の操作記録も状態確認の対象とする。保存済みの情報が少ない場合は、判定できる範囲と不足している情報を表示する。

詳細な記録と再開機能は、新しい形式で開始する操作から提供する。既存の結果不明な記録や残存ロックは保持し、新旧CLIが同じ操作を異なる方法で更新することを防ぐため、記録形式の対応バージョンを確認する。案B・Cのサーバー側機能も、対応するCLIから利用する。

### 削除の対象と完了確認

削除するのは、対象操作に属し、送信の終了と未使用を確認できた未公開ファイルである。公開済みファイル、履歴、他の下書きが利用するファイル、元のローカル音源やTOMLは保持する。

削除操作にもIDを付け、対象・確認時点の更新番号・ファイルの識別情報・処理結果を保存する。実行直前に再照合し、古い確認結果を使った削除を防ぐ。応答が失われた場合は、同じ操作の結果を照会する。送信終了、同じ保存先への再書込み禁止、他操作からの利用禁止を確認できる場合に限り、ファイルの不在を削除完了の判断に使う。

取消・削除の記録は、後から結果を確認できるように保持する。新しくやり直す操作は、以前の操作が今後の公開や書込みと競合しないことを確認してから作成する。

## 7. 確認するテスト

| 観点 | 確認内容 |
| --- | --- |
| 状態表示 | 完了・中断・未着手・結果不明を区別し、表示前後で操作記録やロックが変わらない |
| アップロードの中断 | 送信前、送信中、成功応答の保存前後、読み戻し中、下書き登録前後で停止させ、再開地点を確認する |
| RSSの再開 | 複数エピソードの途中で停止し、公開済み分を再利用して残りを進められる |
| 同時操作 | 二つのCLI、入力ファイルの変更、別のWorkerバージョン、古い削除確認を検出する |
| 取消と削除 | 公開要求との競合、削除中の切断、一部だけ完了した状態を扱い、公開済みデータを保持する |
| 容量と記録保持 | 記録追加による読書き行数と容量増加、警告の表示、再開や結果照会に必要な記録の保持を確認する |

既存のファイル全体のハッシュ・サイズ検証と、MP3の300,000,000 bytes上限を含めて回帰テストを行う。ローカルテストに加え、別途承認された隔離環境で通信断と強制終了時の動作を確認する。
