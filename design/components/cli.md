# CLIの設計

CLIは、ローカルの編集元とCloudflare上の公開状態を結ぶ管理用プログラムである。利用者の環境では、Bun・Node.js・Wrangler・外部音声解析コマンドを必要としない単一バイナリとして動作する。

## 構成と入出力

| 領域 | 役割 |
| --- | --- |
| `packages/cli/src/index.ts` | 引数の解析、コマンド振り分け、人間向け表示とJSON応答 |
| `sqlite-commands.ts` | サービス設定を検証し、各管理処理を呼び出す |
| `packages/shared/src/` | CLIとWorkerで共有する入力・要求・応答スキーマと制約 |
| 管理HTTPクライアント | 管理オリジンへの要求、管理者キー、対象Show、応答の整合性検査 |
| Cloudflare RESTクライアント | R2へのPUT、Worker配備、DNS・独自ドメイン管理 |

入力はワークスペースのTOML、素材ファイル、引数。出力は処理結果、ローカル記録、明示的に指定したプレビューや取得ファイルである。ファイル配置は[保存構造](../data/storage.md)、形式は[スキーマ](../data/schemas.md)を参照する。

## 入力とプレビュー

新規入力には厳密なスキーマと項目別上限を適用し、不明なキーを拒否する。TOMLは通常1,000,000 bytesまで。ShowのCSSは隣接ファイルから読み、改行を正規化して公開用メタデータへ同梱する。ローカルTOMLに生成済み `site_css` を直接書くことは認めない。

`preview-show` / `preview-episode` は、ローカル入力、公開済み内容、項目別差分、素材の再利用可否を返す。ローカルだけの確認では、リモートの状態を「未確認」として区別し、公開可能と断定しない。

`--local` は通信せず、`--remote` は管理者キーとリモート照会を必須とする。既定では `.castloop/` がなければローカル確認、あればリモート確認を行う。キーの欠落や照会失敗を、暗黙にローカル確認へ切り替えない。

プレビューの `input_fingerprint` は次を結び付ける。

- サービス設定と対象Show/Episode
- メタデータ、指定素材のハッシュ・サイズ等、素材パス
- 公開可否、Show状態版、Episodeの更新元リビジョンと公開可否の版、Feed世代

実行時に `--expect-preview` が指定されていれば、この値と再取得したプレビューを照合する。同一公開内容の再実行を除き、入力または更新元が変わった場合は再プレビューが必要になる。

`--rss-output` を指定すると、認証付きで現在の公開Episodeを取得し、変更候補を反映したRSSをローカルの新規ファイルへ生成する。収集中のFeed世代・稼働版・件数を照合し、生成後も入力フィンガープリントを再確認する。指定がなければRSS全体の生成検証は未確認とする。これは公開処理ではなく、新しい音声URLも仮の値になり得るため、試聴用の公開URLとしては使わない。素材確認には手元のファイルを使い、非公開素材をプレビュー用に公開しない。

## メディア配置と公開

```text
入力読取・公開内容取得・差分確認
  → 必要な素材だけR2へPUT
  → メタデータが配置中に変わっていないことを確認
  → Show DOへメタデータと素材参照をPOST
  → changed / unchanged と revision_id を確認
```

通常の公開では素材のSHA-256を1回計算し、MP3を1回解析する。音声は最大300,000,000 bytes、カバーはJPEG/PNGで最大5,000,000 bytes。公開済み素材と同じSHA-256・サイズ等ならPUTしない。Episode更新で音声を指定しなければ公開済み音声を再利用する。初回公開には音声が必要である。

PUTは元ファイルを直接ストリーム送信し、送信バイト数とR2応答のキー・サイズを確認する。送信後の全量読戻しは行わない。処理中は入力ファイルを編集しないことを前提とする。

メディア用のCloudflare認証情報は、変更素材を配置するときに必要になる。メタデータのみの更新などは管理APIの管理者キーで実行する。公開の確定は[Show DO](show-do.md)が担う。

`published_at` が未来でも、通常の `publish-episode` は実行時点で公開する。CLIは警告し、対話確認または `--allow-future-published-at` を要求する。指定時刻まで公開を待つ場合は予約公開を使う。

## 承認対象を固定する操作

| 操作 | 固定・照合する内容 |
| --- | --- |
| 公開 | 入力フィンガープリント、設定、更新元、素材参照 |
| 非公開化・公開復元 | プレビュープラン、対象と更新元、プランのハッシュ、明示確認 |
| 過去版の採用 | 対象履歴、現在の更新元、プランのハッシュ、明示確認 |
| 予約の作成・変更・再承認 | 公開要求、解決済み時刻、予約の版、プランのハッシュ |

公開復元は公開可否の切り替え、過去版の採用は保存済み内容を現在の内容として採用する操作であり、別の処理である。`sync-local-metadata` は現在のリビジョンが指定値に一致することを確認し、メタデータを新規ファイルへ書き出す。既存ファイルを上書きせず、素材の取得や公開もしない。

## 初期化・配備

`init` は新規リソース用の設定を作り、バケット、設定オブジェクト、Workerを用意して稼働確認する。管理者キーと配備対象のハッシュをローカルへ保持する。別の入力や、無関係な既存リソースを継続対象として採用しない。

`deploy` は稼働中サービスとの設定一致、未完了のドメイン変更がないこと、既知のドメイン接続を確認する。その後Workerをアップロードし、配備証拠と名前空間を検査し、新版のhealthを確認する。専用のローカル配備ジャーナルは持たない。同じコード更新を再実行できるが、別設定への変更には使わない。

ビルド時に `src/sqlite-worker.ts` をバンドルしてCLIへ埋め込む。ソース実行時の `worker-payload.ts` は代替Workerを持たない。配備メタデータのバインディング名・DO名・キャッシュ設定は[全体構成](../architecture.md)と定義元に従う。

## 通信失敗とローカル記録

- 管理GETは許可した照会先だけに、期限・応答サイズ・有限回の再試行を適用する。応答形式やサービスの識別情報も照合する。
- 変更系HTTP要求は通信エラーだけを理由に自動再送しない。公開結果が不明なら現在内容を確認し、同じ承認済み入力で再実行する。
- 初期化、Show登録、独自ドメイン、RSS取り込みは各専用記録を使う。通常の公開は公開ジョブ台帳を持たない。
- 同じワークスペース、または同じ取り込みディレクトリを変更するCLIは1プロセスだけ実行する。記録の置換は一時ファイル・同期・renameで行うが、複数ファイル全体のトランザクションではない。

Cloudflare REST URLは、アカウントID・バケット名・Worker名等をパス要素ごとにエンコードする。R2キーは未エンコード文字列を `/` で分割して各要素をエンコードし、区切りは残す。応答のキーは元の文字列と照合する。URLエンコードを設定・対象の検証の代わりにはしない。

キーに文字列として含まれる `%2F` は `%252F` にエンコードし、既存のエスケープとして解釈しない。

独自ドメインの継続条件は[制御DOとドメイン変更](control-do.md)、RSSとバックアップはそれぞれの設計を参照する。

## エージェント向けインターフェースと診断

`schema`、`template`、`validate`、`describe`、`skill export` により、スキーマ・入力例・操作情報・Skillをバイナリから取得できる。`--json` は `contract_version = 1` の単一応答を返し、成功結果とエラーを分離する。失敗時は `outcome` を `not_started` または `unknown` として報告し、一般例外や入力全文をそのまま出力しない。

`help` と `describe` は [help.ts](../../packages/cli/src/help.ts) の説明と引数定義を共有する。`describe.recovery` は操作別の中断時案内であり、CLIの自動再送や変更操作の許可ではない。同梱Skillは [skills/castloop/](../../skills/castloop/SKILL.md) の本文と参照文書を埋め込み、既存の配置先を上書きせず出力する。動作の説明を変えるときは、これらと利用ガイドを同じ変更で照合する。

`doctor --local` はローカル確認、`diagnose` はローカル・リモート・相互整合性の確認、`verify` は公開配信の確認を担う。未確認を成功や0件へ置き換えない。これらの照会結果自体は、変更操作の承認にはならない。
