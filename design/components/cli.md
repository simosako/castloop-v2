# CLIの設計

CLIは、管理者が編集するローカルファイルと、Cloudflare上の公開内容を結ぶプログラムです。入力の検証、プレビュー、素材のアップロード、公開、サービス管理を担当します。配布物は、WorkerとSkillを埋め込んだ単一の実行ファイルです。

## コードの構成

| 領域 | 役割 |
| --- | --- |
| `packages/cli/src/index.ts` | 引数解析、コマンドの振り分け、表示とJSON出力 |
| `sqlite-commands.ts` | サービス設定の検証と各管理処理の呼び出し |
| `packages/shared/src/` | CLIとWorkerで共有するスキーマと制約 |
| 管理HTTPクライアント | 管理者キーを使った管理API呼び出しと、応答の検証 |
| Cloudflare RESTクライアント | R2へのアップロード、Worker配備、DNS・独自ドメイン管理 |

入力はTOML、素材ファイル、コマンド引数です。処理結果のほか、操作に応じて進捗記録やプレビューファイルを書き出します。ファイル配置は[保存構造](../data/storage.md)、形式は[スキーマ](../data/schemas.md)を参照してください。

## 入力の読み取り

TOMLは厳密なスキーマで検証し、不明なキーをエラーにします。Show/EpisodeのTOML上限は1,000,000バイトです。

Showの `site_css_path` は隣接するCSSファイルを指します。CLIはそのファイルを読み、改行を正規化して、公開用メタデータの `site_css` に格納します。編集用TOMLと公開用メタデータの違いは[スキーマ](../data/schemas.md)で説明しています。

## ワークスペースとShowの選択

管理コマンドと `backup-create` は、`--workspace` がなければカレントディレクトリと上位5階層の `castloop.toml` を順に探します。ファイルシステムのルートでは探索を終え、最も近い設定が不正・未対応の場合はエラーにします。設定が見つからない場合もエラーとし、`--workspace` の指定を案内します。明示指定があれば、そのディレクトリだけを使います。

Episodeコマンドでは、`--workspace` の明示指定時は `--show` が必要です。どちらも省略した場合、選択したワークスペース直下のShowディレクトリ内にいることと、ディレクトリ名が `show.toml` の `show_id` に一致することを確認します。`--show` が指定された場合はそのIDを使います。音声の相対パスはShowディレクトリ基準、lifecycle・revisionプランの相対パスはワークスペース基準です。

対話端末でワークスペースを自動選択した管理コマンドは、操作前に標準エラーへワークスペースとサービスID、分かる場合はShow IDを表示します。`--json` では対話文を出さず、応答の `target` に選択先を含めます。`init`、`doctor`、`preview-schedule-time` は既存どおりカレントディレクトリを使い、上位を探索しません。ワークスペース不要のコマンドも探索しません。

## プレビューと承認

`preview-show` と `preview-episode` は、ローカル入力、公開済み内容、項目ごとの差分、素材の再利用可否を返します。

| モード | 確認内容 |
| --- | --- |
| `--local` | ローカルファイルの形式と素材 |
| `--remote` | ローカル確認に加え、管理APIから取得した現在の公開内容との差分 |
| 既定 | `.castloop/` があればリモート確認、なければローカル確認 |

リモート確認には管理者キーが必要です。キーの欠落や通信失敗はエラーとして返し、ローカル確認ではリモートの状態を「未確認」として返します。

`publish-show --review` と `publish-episode --review` はリモートプレビューの対象、差分、素材の確認先、警告を端末に表示し、`publish` の入力を求めます。拒否・入力終了時は素材をアップロードせず公開しません。未来の `published_at` の即時公開には、既存の専用確認または明示指定も必要です。

すべての確認後、サービス設定を読み直して確認時と照合し、プレビューの `input_fingerprint` を使って入力とリモートの更新元を再照合してから素材を配置します。同じ内容がすでに公開済みの場合は既存の `unchanged` を維持します。`--review` は標準入力・出力が端末の場合に限り、`--json` や `--non-interactive` とは併用できません。従来のプレビューと `--expect-preview` による非対話操作も維持します。

### 入力フィンガープリント

`input_fingerprint` は、次の情報をまとめたハッシュです。

- サービス設定と対象Show/Episode
- メタデータ、素材のパス・ハッシュ・サイズ
- Showの状態版、Episodeの更新元リビジョンと公開状態の版、Feed世代

公開時に `--expect-preview` が指定されていれば、再取得したプレビューと照合します。入力や更新元が変わった場合は、再プレビューして承認し直します。すでに同じ内容が公開されている場合は、同一内容の再実行として扱います。

### RSSのプレビュー

`--rss-output` は、公開中のEpisode一覧に変更候補を反映したRSSを、新規ローカルファイルへ書き出します。一覧の取得中はFeed世代・Worker版・件数を照合し、生成後に入力フィンガープリントも再確認します。

この検査は `--rss-output` を指定した場合に行います。新しい音声URLは仮の値になる場合があるため、素材の試聴にはプレビューが示すローカルファイルを使います。

## 素材のアップロードと公開

1. 入力と現在の公開内容を読み、差分を確認します。
2. 必要な素材をR2へアップロードします。
3. アップロード中にメタデータが変わっていないことを確認します。
4. メタデータ、素材参照、更新元の版をShow DOへ送ります。
5. `changed` / `unchanged` と `revision_id` を結果として返します。

通常の公開では素材のSHA-256を1回計算し、MP3を1回解析します。音声上限は300,000,000バイト、JPEG/PNGカバーは5,000,000バイトです。公開済み素材とハッシュ・サイズなどが一致すれば再利用します。Episode更新で音声を指定しなければ、現在の音声を再利用します。

アップロードは元ファイルをストリーム送信し、送信バイト数と内容のSHA-256を事前検査の参照と照合し、R2応答のキー・サイズも確認します。入力ファイルは処理中に編集しない運用です。素材のアップロードにはCloudflare APIトークン、管理APIへの公開要求には管理者キーを使います。公開の確定処理は[Show DO](show-do.md)が担当します。

`published_at` はRSS上の公開日時です。未来の日時でも `publish-episode` は即時公開するため、CLIは確認または `--allow-future-published-at` を求めます。指定時刻に実行する処理は予約公開が担当します。

## 公開状態・履歴・予約の操作

変更前に確認した内容のハッシュや版を、実行要求に含めます。操作前の状態として指定する版を期待版と呼び、実行時の状態と照合します。

| 操作 | 主な照合内容 |
| --- | --- |
| 公開 | 入力フィンガープリント、設定、更新元、素材参照 |
| 非公開化・再公開 | プラン、対象、更新元、プランのハッシュ、明示確認 |
| 過去版の採用 | 採用する履歴、現在の更新元、プランのハッシュ、明示確認 |
| 予約の作成・変更・再承認 | 公開要求、解決済み時刻、予約の版、承認ハッシュ |

再公開は保存済み内容の公開状態を戻す操作、過去版の採用は履歴の内容を現在の内容にする操作です。

`sync-local-metadata` は、現在のリビジョンが指定値と一致することを確認し、メタデータを新規ローカルファイルへ書き出します。これは編集元を作るための操作です。

## 初期化とWorker配備

`init` は、新規サービスの設定・R2バケット・設定オブジェクト・Workerを作り、稼働を確認します。管理者キー、配備対象のハッシュ、進捗をローカルへ保存し、再実行では同じ初期化対象と照合します。

`deploy` は、サービス設定、ドメイン変更の完了状態、既知の接続を確認してWorkerを更新します。アップロード後は配備情報、DO名前空間、新版のhealthを確認します。中断後は現在の稼働状態を調べ、同じ設定で再実行できます。公開オリジンの変更は[独自ドメイン変更](control-do.md)で行います。

Workerはビルド時に `src/sqlite-worker.ts` からバンドルします。バインディングとキャッシュ設定は[全体アーキテクチャ](../architecture.md)を参照してください。

## Logpushの設定

`logpush setup --zone-id ID --bucket-name NAME`は、現在の独自ドメインを対象に、別の非公開ログR2・400日保持・バケット限定の保存先トークン・ゾーン単位ジョブを設定します。既存のWorker配信と統計は維持し、サービスTOMLやWorker配備は変更しません。`workers.dev`だけのサービスは設定対象になりません。

`logpush status --zone-id ID`は読取専用で、対象一致・非公開性・保持ルール・配送の状態を返します。`enable`・`disable`は保存済みジョブを変更し、中断情報を保持します。同じゾーンでsetupし直すと現在のホストを追加し、旧ホストと有効・無効の設定を維持します。ドメイン変更とLogpush設定は別操作として承認・実行します。

`.castloop/logpush/<service_id>/configuration.json`は、対象と操作UUID、リソースID、現在・直前の収集条件、収集元を保存します。再実行ではAPIの現在状態を照合します。トークン作成後に中断し、ジョブがまだなければ、その操作に属する未使用トークンを失効させて作り直します。秘密値は作成応答からしか取得できず、ローカルにも保持しないためです。ジョブがあれば保存した識別子・保存先・10フィールド・条件を照合して利用します。

実装は[設定とAPI](../../packages/cli/src/logpush.ts)、[Cloudflare REST](../../packages/cli/src/logpush-cloudflare.ts)、[保存形式](../../packages/cli/src/logpush-config.ts)、操作方法は[Logpush利用ガイド](../../docs/logpush.md)を参照してください。統計CLIとの接続は別工程です。

## 通信失敗とローカル記録

管理GETは許可した取得先に限定し、タイムアウト、応答サイズ上限、回数を限定した再試行を設定します。応答の形式とサービス識別情報も検証します。変更系HTTPの通信エラーでは結果が不明な場合があるため、現在の状態を確認してから、同じ承認済み入力で再実行します。

初期化、Show登録、独自ドメイン変更、RSS取り込みは、それぞれの進捗記録を使います。通常の公開は、公開済み内容との照合で結果を確認します。ローカル記録は一時ファイルへの書き込み・同期・renameで置き換えます。同じ保存先を変更するCLIは1プロセスで実行します。

Cloudflare REST APIのURLは、識別子をパス要素ごとにエンコードします。R2キーは `/` ごとに分割してエンコードし、応答キーを元の文字列と照合します。たとえば、キーに文字列として含まれる `%2F` は `%252F` になります。

## 機械向け出力と診断

`schema`、`template`、`validate`、`describe`、`skill export` から、スキーマ、入力例、操作情報、Skillを取得できます。`--json` は `contract_version = 1` の応答を返し、成功結果とエラーを分けます。エラー時は、実行前と分かる `not_started`、成否が分からない `unknown` を区別します。出力するエラー情報は[セキュリティ](../security.md)の規則に従います。

`help` と `describe` は [help.ts](../../packages/cli/src/help.ts) の説明と引数定義を共有します。同梱Skillは [skills/castloop/](../../skills/castloop/SKILL.md) から埋め込むため、操作案内の変更時はこれらと利用ガイドを合わせて確認します。

| 診断コマンド | 確認対象 |
| --- | --- |
| `doctor --local` | ローカル設定・素材・管理記録 |
| `diagnose` | ローカル、リモート、両者の整合性 |
| `verify` | 公開URLからの配信 |
