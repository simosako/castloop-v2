Serverless podcast hosting on Cloudflare, managed with a standalone CLI: one private R2 bucket and one public Worker per service, multiple Shows.

**Status: early beta (v0.7.x).** Commands, flags and service behavior may still change between releases. See the [changelog](CHANGELOG.md) for what each release changed.

**Issue #65 development (scheduled publication):** staged Show/Episode drafts can be frozen into a future UTC schedule without occupying the FIFO. Use `preview-episode-schedule`/`preview-show-schedule`, approve the returned hash, then `schedule-episode`/`schedule-show`. `schedule-list`, `schedule-status`, `schedule-reschedule`, `schedule-cancel` and `schedule-reapprove` observe or change the schedule. Due schedules are dispatched by the existing Show Alarm; Pause, admission stop, maintenance and changed bases require explicit reapproval. Scheduled time and `published_at` are separate. The integrated development version requires fresh internal queue/content formats **11/11**; earlier environments are not upgraded. A fresh isolated 9/9 environment published three scheduled Episodes only after their due times; see the [live verification](design/issue65_scheduled_publication_live_20261026.md) and [adopted design](design/episode_scheduled_publication_plan.md). Pause/reapproval, cancel/reschedule and Alarm redelivery remain untested in the live environment.

**Issue #70 development:** optional builtin Show websites with newest-first 20-Episode listings, automatically shortened Episode page URLs and inline browser-native audio. Includes one default design, optional Show CSS, plain-text excerpts and full descriptions with safe HTTP(S) links, without a copyright footer. Optional `site_timezone = "Asia/Tokyo"` in Show TOML controls website publication-date display (default UTC); it does not alter RSS dates or Episode identities. HTML is pre-generated by the Show DO, stored in private R2 and served through a separate HTML gateway/CDN entrypoint. Use `create-show ID --site-mode builtin`; external sites remain supported. Requires fresh internal queue/content formats **11/11** and `website="static-show-v2"`; earlier environments are not upgraded or migrated. See the [website guide](docs/show_website.md) and [private timezone trial results](design/show_website_timezone_trial_verification_20261027.md). The reviewer confirmed playback, full descriptions, short URLs, links, footer removal and Tokyo date display in the private 10/11 trial. Native Cloudflare Free performance measurements and mobile/keyboard checks remain pending; the combined scheduled-publication version has not been deployed.

**v0.7.5 (Issue #64):** authenticated published-content comparisons, Show/Episode revision history, explicit adoption of saved revisions without uploading media again, and locally generated RSS previews. Requires fresh internal queue/content formats **7/8** and `revision_history="sqlite-revisions-v1"`; older databases are not converted. `preview-*` defaults to remote reads in initialized workspaces; use `--local` for offline checks. Metadata/RSS export never overwrites existing files. See the [review guide](docs/published_content_review.md) and [v0.7.5 release notes](docs/release-v0.7.5.md).

**Show admission/delivery controls (Issue #66, released in v0.7.4):** `show-admission-pause SHOW UUID` stops publication and upload admission while keeping approved content delivery enabled. Existing `show-pause` still stops both. `show-delivery-resume SHOW UUID` enables only delivery after accepted jobs drain and runtime verification succeeds outside maintenance. `show-control-status SHOW UUID` reads a recorded stop/resume outcome without replaying it. The v0.7.4 release requires fresh internal queue/content formats **7/7**; v0.7.5 uses the **7/8** formats described above. Both require `availability_controls="show-admission-delivery-v1"`; older environments are not converted. Worker and domain updates still require every Show's explicit full Pause. See the [operator guide](docs/show_availability.md).

Issue #68 added one dedicated custom subdomain per fresh SQLite service, gated workers.dev redirects, and explicit add/list/status/continue/remove operations in v0.7.3 (internal formats **6/7**). The [two-Show native functional trial](design/sqlite_custom_domain_two_show_verification_20261024.md) passed publication, canonical delivery, redirects, individual Pause, updates/restore, connection-preserving deploy and domain removal. Both Shows finished paused/ready/drained. Those results do not validate Issue #66's new controls. See the [custom-domain guide](docs/sqlite_custom_domains.md) for limits; this is not a performance or full Free-compatibility claim.

A separately approved [logged zero-Show retest](design/sqlite_custom_domain_iterative_verification_20261024.md) identified an empty deprecated `environment` in the successful PUT response and a zero-length HTTP 200 DELETE response. The CLI durably saves a narrowly validated attachment acknowledgement before production-only GET verification, and accepts a completely read empty DELETE only with Content-Length zero. Configuration changes still require a complete verified connection. Earlier uncertain operations remain untouched; see the [safe CLI diagnostics](design/sqlite_domain_response_logging.md).

The corrected standalone CLI completed both zero-Show diagnostics and the two-Show functional trial, including workers.dev restoration and immutable history checks. Earlier uncertain operations and retained locks remain untouched. The prior 666 local tests pass; native RSS import, fault injection, internal cache hit/miss and performance remain outside this trial.

**v0.7.0 isolates each Show in its own Durable Object — with an independent SQLite FIFO, Alarm and Show-level Pause/Resume — and keeps committed Feeds, covers and approved audio readable during Episode additions/updates and Show metadata/cover updates.** `castloop init` creates a schema-version-2 service with `storage_layout = "show-v1"` only. Queue/R2 service support, its Worker bundle and commands have been removed. Service, content and request schema versions are unchanged. Installing this release does not deploy or change an existing Cloudflare service. See the [release notes](docs/release-v0.7.0.md).

Persisted formats are unchanged from v0.7.0. Small native functional checks passed; log-capture coverage remains incomplete. See the [v0.7.1 release notes](docs/release-v0.7.1.md).

**v0.7.2** adds agent-oriented CLI discovery, embedded input schemas, offline validation/templates/doctor, explicit targets, structured results, a bundled administrator Skill and reviewed-input publication fingerprints. The Worker and persisted formats are unchanged. Existing `--json` payloads move under `result`; see the [v0.7.2 release notes](docs/release-v0.7.2.md).

**v0.7.3** adds dedicated custom subdomains for fresh SQLite services, with separate management/public origins and explicit domain lifecycle commands. It requires internal queue/content schemas 6/7 and does not migrate existing services; see the [v0.7.3 release notes](docs/release-v0.7.3.md).

**v0.7.4** adds read-only observation commands (`diagnose`, `progress`, `verify`, `watch`) for AI-agent operation, separates Show admission from public delivery with three availability states (`open`/`admission_paused`/`paused`), adds an optional administrator timezone preference with offline schedule preview, distributes native macOS Apple Silicon and Windows x64 binaries, and updates Zod for CVE-2023-54404. Admission/delivery controls require fresh internal queue/content schemas 7/7; see the [v0.7.4 release notes](docs/release-v0.7.4.md).

**Compatibility boundary:** v0.7.x targets fresh `storage_layout = "show-v1"` services and is **incompatible with released v0.6.2 layouts**; there is no update or migration path between layouts. Do not add the layout field to an old workspace to bypass this boundary. See the [tagged v0.6.2 README](https://github.com/simosako/castloop-v2/blob/v0.6.2/README.md) for the previous service-wide layout.

The CLI uploads and verifies unique R2 objects, then explicitly submits a frozen request to the target Show's Durable Object. Each Show has its own SQLite FIFO, Alarm and Pause/Resume window; different Shows can progress independently. A small control DO stores membership and shared Worker-update progress. No Cloudflare Queues or D1 are used. Local TOML remains the editable source; R2 holds published files and SQLite holds control state.

**Feed read continuity:** Episode additions/updates and published Show metadata/cover updates keep the committed Feed, cover and approved audio readable. Feed and cover use immutable private R2 snapshots; new metadata, cover references and Feed generations commit atomically after verified writes and required cache purges. Cover URLs remain stable: separate requests spanning a commit may fetch an old Feed and a new image, and a cover-only edit may leave Feed bytes/ETag unchanged (304). Published cover extension changes remain unsupported. Old snapshots, audio and revision history are retained without automatic cleanup. Matching persisted guards allow old content during isolated blocked jobs, but later jobs, Resume and shared deployment remain blocked. Initial Show publication and lifecycle execution have no continuity exception; full Pause/readiness/maintenance checks remain enforced. Released v0.7.0–v0.7.2 uses internal queue/content schemas **5/6**, v0.7.3 uses **6/7**, and v0.7.4 uses **7/7** with the `availability_controls="show-admission-delivery-v1"` capability. All require health `feed_storage` and `cover_storage` set to `immutable-generation-v1`, and `publication_read_boundary="show-episode-v1"`. Only fresh matching services are supported, without migration. See the [Show update design](design/show_update_feed_availability_plan.md) and [usage guide](docs/sqlite_sequential_development.md).

The v0.6.0 trial published 36 full-size Episodes (1.50GB) in **485.53 seconds**, plus three short Episodes. All 39 audio hashes and delivery checks passed, including preservation after a Worker update. Saved logs showed outer/cache HTTP CPU maxima of **3/5ms**, below the Workers Free 10ms target for the captured requests. This is not proof of complete log capture, every workload's Free compatibility, or permanent resolution of [Issue #13](https://github.com/simosako/castloop-v2/issues/13). See the [acceptance and CPU record](design/archive/schema_v1_removal_live_test.md).

## Supported service configuration

Development supports only fresh `schema_version = 2`, `publication_protocol = "sqlite-sequential-v1"`, `storage_layout = "show-v1"` services with the current internal formats. Missing/other layouts are rejected before management IO or local state changes. Publication, listings, RSS import, unpublish/restore and same-config/schema/namespace code-only updates are available. Custom-domain support released in v0.7.3 is limited to one dedicated subdomain in the same account's active/full Cloudflare DNS zone and is not a migration path for earlier services. Physical deletion and blocked-job retry/release are not supported.

Service schema version 1 is rejected before management requests, deployment or administrator-key/journal creation. There is **no schema-version-1 migration feature**: do not edit schema/protocol fields, adopt old resources or convert retained journals. Existing Queue services require a compatible **v0.5.x CLI and Worker**, maintained separately; see the [v0.5.x-only Queue guide](docs/queue_service.md). Installing this CLI does not change, pause, delete or harden an existing deployed Worker. Shared Show/Episode metadata still uses its independent `schema_version = 1`.

## Install

Download the binary for your platform plus `SHA256SUMS`, `LICENSE`, and `THIRD_PARTY_NOTICES.md` from the [latest release](https://github.com/simosako/castloop-v2/releases/latest):

| Platform | Artifact | Minimum OS |
| --- | --- | --- |
| Linux x86-64 | `castloop-linux-x64` | glibc-based 64-bit Linux |
| macOS Apple Silicon (arm64) | `castloop-macos-arm64` | macOS 11+ |
| Windows x64 | `castloop-windows-x64.exe` | 64-bit Windows 10+ |

macOS Intel (x64), Windows ARM, and Linux ARM builds are not distributed. All three artifacts are built and smoke-checked natively on GitHub-hosted runners of the same OS/architecture by the [release workflow](.github/workflows/build-binaries.yml). The binaries are **unsigned** (no code signing, notarization, or Authenticode): macOS Gatekeeper and Microsoft Defender SmartScreen may warn on first launch, and no certificate purchase or warning disabling is assumed. See the [distribution guide](docs/cli_binary_distribution.md) for per-OS setup, verification scope and limits.

Linux and macOS (Apple Silicon):

```sh
grep 'castloop-linux-x64$' SHA256SUMS | sha256sum -c -   # on macOS: ... | shasum -a 256 -c -
chmod +x castloop-linux-x64
./castloop-linux-x64 --version
```

Windows (PowerShell):

```powershell
Get-FileHash castloop-windows-x64.exe -Algorithm SHA256  # compare with the SHA256SUMS entry
.\castloop-windows-x64.exe --version
```

Keep the matching old CLI/source for frozen initialization/update journals. Existing Queue services need [v0.5.x](https://github.com/simosako/castloop-v2/blob/v0.5.2/README.md), not this release; there is no automatic migration.

Keep `LICENSE` and `THIRD_PARTY_NOTICES.md` with the executable.

The administrator's machine needs no Bun, Node.js, Wrangler, source tree, `ffprobe`, or separate R2 S3 credentials. Enable the required Cloudflare products and supply `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`. SQLite initialization needs Worker/R2 resource and deployment permissions and access to SQLite-backed Durable Objects; it does not need Queues Edit. The CLI never expands token permissions or changes billing/CPU limits automatically.

### Build from source

Use Bun 1.4.2 and Node.js 24/npm on the build machine:

```sh
npm ci
npm run check
bun test
npm run build:cli -- linux-x64
```

`build:cli` accepts `linux-x64`, `macos-x64`, `macos-arm64`, and `windows-x64` (Bun cross-compiles, so no target machine is needed; the release workflow builds `linux-x64`, `macos-arm64`, and `windows-x64` natively on matching runners). The executable is `dist/castloop-linux-x64` and embeds only `src/sqlite-worker.ts`. Source mode is `bun packages/cli/src/index.ts`. See `castloop help COMMAND` for syntax.

## Agent support

Since v0.7.2, the CLI embeds input schemas, offline validation/templates, a compact local doctor and the administrator Skill. Export it with `castloop skill export castloop --output /path/to/project/.agents/skills/castloop`; no additional runtime or MCP is required. Use explicit `--workspace`, Episode `--show`, `--non-interactive` and versioned `--json` results. Review staged inputs with `preview-show`/`preview-episode`, then bind publication to `--expect-preview HASH`. Use `preview-episode-schedule`/`preview-show-schedule` and the same `--expect-preview` binding for scheduled publication; `schedule-status` observes the schedule and resulting publication job separately. See the [agent usage guide](docs/agent_usage.md) for installation, approval boundaries, JSON changes and verification limits.

**Issue #65 scheduled publication:** optional workspace `castloop-admin.toml` can hold a CLI `timezone` preference; missing preferences use the server basis, UTC. `preview-schedule-time DATETIME [--timezone IANA_ZONE]` remains an offline conversion helper with explicit offset/DST validation. Scheduling is separate: `preview-episode-schedule`/`preview-show-schedule` reads the staged draft and returns an approval hash; `schedule-episode`/`schedule-show --expect-preview HASH` submits a future schedule; `schedule-list`/`schedule-status` observe it. The Show DO stores the schedule outside the FIFO and dispatches it through the existing Alarm. Pause, admission stop, maintenance, runtime changes and changed bases suspend it as `needs_approval`; `schedule-reapprove` freezes current conditions explicitly. `schedule-reschedule` and `schedule-cancel` work only before dispatch. A scheduled time is not `published_at`; the latter is never changed by scheduling. See the [administrator configuration guide](docs/admin_configuration.md), [agent usage guide](docs/agent_usage.md) and [adopted design](design/episode_scheduled_publication_plan.md).

## Initialize a new SQLite service

Use a new workspace and unused resource names. Substitute your Cloudflare account's workers.dev subdomain and a fresh UUID for each operation/window:

```sh
export CLOUDFLARE_ACCOUNT_ID=... CLOUDFLARE_API_TOKEN=...
castloop init /path/to/workspace \
  --service-id my-service --bucket-name my-private-bucket \
  --workers-subdomain my-account-subdomain --operation-id INIT_UUID
cd /path/to/workspace
castloop service-status
```

Initialization creates schema version 2 with `storage_layout = "show-v1"`; the protocol flag remains optional. It verifies the actual Worker/version/namespace and control-DO Alarm/R2/cache/purge readiness. Each newly registered Show starts **paused** and requires its own explicit Resume with a new window UUID. There is no service-wide Pause/Resume. Existing resources are never adopted.

Keep `castloop.toml` and private, git-ignored `.castloop/` state together and backed up. The latter contains the administrator key and journals: TOML alone is not a complete workspace. Never commit credentials, journals or unpublished audio. Since v0.5.1 `castloop.toml` must be a regular file of 1–16,384 bytes; a symlinked, FIFO, oversized or non-UTF-8 configuration is rejected before any management request or local state is created.

## Publish a Show and Episode

```sh
castloop create-show my-show --site-url https://your-real-site.example/podcast
castloop show-status my-show
castloop show-resume my-show NEW_WINDOW_UUID
# Edit my-show/show.toml and provide the JPEG/PNG named in image_path.
castloop update-show my-show
castloop publish-show my-show
cd my-show
castloop create-episode first
# Edit episode-first.toml and prepare audio.mp3.
castloop update-episode first
castloop update-episode-audio first audio.mp3
castloop publish-episode first
cd ..
castloop job-status EPISODE_JOB_UUID
```

Use a real external website URL, or explicitly select `--site-mode builtin` without `--site-url` in the Issue #70 development build. Use the returned job ID. Show commands run at the service root; Episode commands run in the Show directory. `create-*` never publishes. `update-*` uploads verified inputs without publication. **Only `publish-*` submits**, then waits for the exact job's `succeeded` status. A queued/accepted response is not success. `job-status` returns `status.state`; `succeeded` proves that operation's writes, purge and SQL completion, not global quiescence.

For a metadata-only update, edit the TOML, run `update-episode ID`, then `publish-episode ID`. For audio-only, run `update-episode-audio ID new.mp3`, then `publish-episode ID`. Publication does not need an MP3 argument after staging; an optional argument must match the staged source. Preserve GUID and `published_at`; published media and revision history are immutable during normal updates.

The feed is `<public_base_url>/podcasts/my-show/feed.xml`. Covers must be JPEG/PNG; a published cover's extension cannot change. MP3 input is limited to **300,000,000 bytes** and is fully read back to verify size/hash before submission. The new SQLite route's native 300MB publication remains untested; earlier Queue-path acceptance is not a substitute. Staging/audio has no automatic retention cleanup.

## List, unpublish and restore

```sh
castloop list-shows
castloop list-episodes my-show --json
castloop list-episodes my-show --cursor 'TOKEN_FROM_PREVIOUS_PAGE'
castloop preview-episode-lifecycle my-show first unpublish > plan.json
# Review plan.json and copy its request_sha256.
castloop lifecycle-execute plan.json REQUEST_SHA256 confirm
castloop job-status JOB_UUID
```

Listings return up to 20 entries per page; follow `next_cursor`. Local-only drafts are not listed. Snapshot listings do not authorize changes or recovery.

## Delivery statistics

```sh
castloop stats my-show                              # per-Episode totals (default: last 30 UTC days)
castloop stats my-show --episode first --by-revision # daily rows and per-audio-revision totals
castloop stats-retention my-show 180                 # change the daily retention window (default 400 days)
```

`stats` reads server-side counters for approved public Episode audio only. It counts full GETs, initial range downloads, served bytes and separates HEAD, 304, small range probes and known bots; no IP addresses or User-Agent strings are stored. Days before measurement started (`unmeasured`) and pruned days (`pruned`, beyond the retention window) never render as zero, and `lifetime` keeps totals across pruning. `stats-retention` applies from the next UTC-day pruning without redeploying; see the [statistics guide](docs/delivery_statistics.md). Requires internal content schema 9 (`delivery_statistics="episode-daily-v1"`); older environments are not migrated.

Use `restore` instead of `unpublish`, or `preview-show-lifecycle my-show ACTION` for a Show. Preview is read-only; execution queues the reviewed request and requires the same job's `succeeded` status. Restore uses saved snapshots, not local edits, and preserves GUID/date/audio. Restoring a Show does not revive individually unpublished Episodes. Unpublish retains payloads and does not reduce storage. **SQLite physical deletion is not implemented.** Custom-domain changes use the [separate maintenance procedure](docs/sqlite_custom_domains.md), not lifecycle deletion or code-only deploy.

## RSS import

```sh
castloop import-rss imported-show https://old-host.example/feed.xml --dry-run
castloop import-rss imported-show https://old-host.example/feed.xml --output /path/to/import
# Review the downloaded TOML, cover, MP3s and warnings before publishing.
castloop publish-rss-import /path/to/import
```

Run publication from the service root. Imports create a new Show, preserve GUIDs/dates and publish sequentially; completed Episodes become public before the entire import finishes. Subscriber migration, recurring sync, adoption of existing Shows and removal of the old host are not performed. See [RSS usage](docs/rss_migration.md).

## Update an existing SQLite Worker

This applies only within the new layout, not to an upgrade from a legacy service. Back up the workspace and explicitly pause and drain **every Show** before a same-config/schema/namespace code-only update:

```sh
castloop show-pause my-show PAUSE_OPERATION_UUID
# Repeat for every other Show with a fresh UUID.
castloop service-status
# Confirm all Shows are paused, drained and ready.
castloop deploy --operation-id UPDATE_UUID
castloop service-status
castloop show-resume my-show NEW_WINDOW_UUID
```

An already paused Show does not need another pause request. Update pins membership, atomically prepares and locks each Show, then verifies all targets' exact runtime and Alarm/R2/cache/purge readiness before releasing maintenance. Every Show remains paused and can be resumed separately. Partial/unknown preparation, activation or release is retained without replay or automatic rollback. See [update/recovery details](docs/sqlite_sequential_development.md#互換worker更新).

**Recovery continuation (since v0.5.2):** `castloop update-service-verify UPDATE_UUID` also continues REST verification from an acknowledged PUT or a pinned deployment after a GET failure, not only from `verified`. It requires the exact frozen inputs and rechecks the acknowledged ETag, deployment/version, namespace and server maintenance request before the first activation/probe. It never repeats PUT/preparation or a previously requested activation. Older receipt-free `deploy_requested` journals remain blocked; see the [recovery contract](design/sqlite_worker_update_recovery.md).

## Errors and recovery

Use `castloop operation-list --show my-show --incomplete` and `castloop operation-status upload OPERATION_UUID --show my-show --remote` to inspect server-side operation records. Remote operation commands require `--show`; local-only diagnosis does not. See the [operation recovery guide](docs/sqlite_operation_recovery.md) for receipt-based continuation, cancellation and reviewed staging cleanup. Published Show/Episode deletion remains unsupported.

- Preserve `.castloop/`, frozen requests and uploads. Inspect the same `job-status` and `service-status`; never replace unknown jobs or remove locks because time elapsed.
- SQLite management GETs retry transient transport/body failures and selected transient HTTP statuses up to three attempts. Publication polling counts actual GETs toward 300 and starts none after five minutes. POST/PUT mutations are **never automatically retried**.
- `failed` means a deterministic pre-write input/base failure; `blocked` preserves uncertain execution and stops only that Show's FIFO/delivery. Other Shows can operate, Pause/Resume and register independently. A blocked Show still prevents shared Worker updates. An empty queue does not prove unregistered uploads ended.
- `init-reconcile` and `update-service-reconcile` only reconcile exact, already-completed server evidence. Limited explicit verification continuations exist for acknowledged deployment journals; they do not repeat resource creation/deploy or adopt unknown versions.

See the [changelog](CHANGELOG.md), the [SQLite operations guide](docs/sqlite_sequential_development.md), the [release notes](docs/release-v0.7.5.md), and the [design index](design/README.md). Existing Queue environments must keep v0.5.x and use its [separate guide](docs/queue_service.md). No release, install or test completion automatically deploys, resumes, cleans up or deletes Cloudflare resources. The deep-dive design and operations documents are currently written in Japanese.
